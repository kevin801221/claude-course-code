# 評分者專用：不要在 v1 階段交給開發組

【共同驗收：20 項，每項 5 分】
每項全數斷言通過給 5，任一斷言失敗或無法重現給 0；不以好看、字多或模型自評加分。每項以乾淨 seed 開始，使用同一份外部評分腳本／操作步驟，留下實際輸出。UI 測試使用真實瀏覽器，不只看程式碼。
核心 40：
1. 內部學員在開放且有名額場次報名，API 回 confirmed，重整頁面仍顯示相同資料。
2. 同一學員同場次連續與併發重送，唯一紀錄與占位均只有一份。
3. 滿額後兩人依序候補，排序依伺服器序號；取消候補不改正取數。
4. 剩一席時兩位學員同時請求，恰一人 confirmed、一人 waitlisted，正取不超容量。
5. 正取取消後，恰好第一位候補轉正取，狀態與名額在同一交易一致。
6. 同一取消請求重送或併發，不再遞補第二位，總正取數不超限。
7. HR 關閉報名後拒絕新報名，原有學員仍能取消並正確遞補。
8. HR 增加容量與合法修改可保存；容量低於已正取人數或非正整數被伺服器拒絕，原值不受損。新增容量是否自動遞補由凍結 PRD 明定；本課預設新增容量後立即按 FIFO 遞補至滿額，須同交易保護。
跨層 20：
9. 四個畫面核心流程可用；列表、詳情、我的報名、HR 顯示與 API／SQLite 一致，錯誤訊息可理解。
10. 學員不能直接呼叫 HR API 修改容量或審核；不能取消他人報名，伺服器拒絕且資料不變。這仍只是教學模擬身分，並非正式認證安全測試。
11. 重新整理／重啟服務後狀態持久存在；取消後重新報名不重複紀錄，候補排在新隊尾。
12. 同時取消與報名交錯後，容量、唯一報名、FIFO 和 UI 狀態一致；以固定可重現的併發測試驗證，不能僅手動按一次。
變更 20：
13. 新外部申請為 pending_approval，不占座也無候補順位；內部不受影響，UI 正確顯示。
14. HR 核准時依當下名額正取或候補尾端，重送核准冪等；兩件核准競爭一席不超收。
15. 拒絕與取消待審不占位、不觸發遞補；取消後核准失敗、學員無審核權，資料一致。
16. v1 既有正取／候補不被追溯審核；截止後不能新申請，但 HR 能處理既有待審；遷移後回歸核心案例仍通過。
可交付 10：
17. 依 README 在乾淨副本使用 lockfile 安裝並啟動，四頁可操作，無未說明的必要憑證。
18. seed/reset 可重複建立相同 3 場次與 6 身分，測試命令可重跑；README 清楚說明教學身分、非目標與限制。
可追溯 10：
19. PRD、API／狀態契約、decision-log 與實作一致，v1 和 CR-01 有版本證據。
20. 實際測試輸出、修復次數、未通過項目和協作機制證據可追查；不接受模型口頭聲稱全過。
