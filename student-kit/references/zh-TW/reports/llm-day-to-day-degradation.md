# 🔥 Claude Code Ops 4.6 分析：高推理

當 Anthropic 推出像 Opus 4.6 這樣的模型時，**模型權重**（數十億個學習而來的參數）是凍結的。訓練極其昂貴（數百萬美元、數週運算），沒有人會一夜之間重新訓練模型。

但權重只是一個更大系統中的一層。研究揭示至少 **7 種不同機制**可能造成真實或感知上的品質變化，即使模型權重凍結也一樣。

| 問題 | 答案 |
|----------|--------|
| 模型權重在發布後會改變嗎？ | **不會** —— 所有供應商都確認 |
| 模型的行為會逐日不同嗎？ | **會** —— 已證實有 ±8-14% 的變異 |
| 這是刻意「削弱」嗎？ | **不是** —— 沒有刻意降級的證據 |
| 基礎設施 bug 是真的嗎？ | **是** —— Anthropic 確認有 3 個 bug 影響多達 16% 的請求 |
| 有部分是心理作用嗎？ | **有** —— 確認偏誤與蜜月期效應是真實存在的 |
| system prompt／後訓練會改變嗎？ | **會** —— 各家供應商都有紀錄 |
| 使用者該相信自己的感受嗎？ | **部分可以** —— 真實成因存在，但感知會放大它們 |

## 完整的推論堆疊

模型權重是凍結的，但**它上面的九層**都能獨立影響你的體驗：

```
┌──────────────────────────────────────────────┐
│  你的 SESSION 脈絡                            │  ← session 內會劣化
│  （累積的錯誤、過長的對話）                     │
├──────────────────────────────────────────────┤
│  SYSTEM PROMPT                               │  ← 定期更新
│  （安全規則、行為指令）                         │
├──────────────────────────────────────────────┤
│  後訓練（RLHF / Fine-tuning）                 │  ← 可以悄悄更新
│  （指令遵循、安全對齊）                         │
├──────────────────────────────────────────────┤
│  取樣參數                                     │  ← 可在伺服器端調整
│  （temperature、top-p、top-k）                │
├──────────────────────────────────────────────┤
│  推測解碼（Speculative decoding）              │  ← 草稿模型品質浮動
│  （草稿模型預測 + 驗證）                        │
├──────────────────────────────────────────────┤
│  MoE 路由 / 批次組成                           │  ← 已證實 ±8-14% 變異
│  （每個請求啟動哪些專家）                       │
├──────────────────────────────────────────────┤
│  硬體路由                                     │  ← TPU vs GPU vs Trainium
│  （由哪個叢集處理你的請求）                      │
├──────────────────────────────────────────────┤
│  量化等級                                     │  ← 高負載時可能變動
│  （FP16 vs INT8 vs INT4 精度）                │
├──────────────────────────────────────────────┤
│  編譯器與執行期                                │  ← XLA bug 已證實為真
│  （XLA:TPU、CUDA、硬體專屬程式碼）              │
├──────────────────────────────────────────────┤
│  模型權重（凍結）                              │  ← 這些不會變
│  （數十億個學習而來的參數）                      │
└──────────────────────────────────────────────┘
```

關鍵心智模型：**凍結的權重 ≠ 凍結的行為**。這就像說「同一具引擎 = 同樣的駕駛體驗」，卻忽略了輪胎、路況、燃油品質與駕駛疲勞。

## 已證實的成因：基礎設施 bug

### Anthropic 2025 年 9 月的事後檢討

2025 年 9 月，Anthropic 發布了一份詳細的事後檢討，揭露**三個獨立的基礎設施 bug** 在 2025 年 8 月至 9 月間使 Claude 品質下降。他們的官方聲明：

> 「我們從不因需求、時段或伺服器負載而降低模型品質。使用者回報的問題完全是基礎設施 bug 造成的。」

### Bug #1 —— 脈絡視窗路由錯誤

Sonnet 4 的請求被誤導向設定為 1M token 脈絡視窗的伺服器，而非標準伺服器。

- **時間線**：8 月 5 日引入，8 月 29 日一次負載平衡變更後惡化
- **尖峰影響**：最糟的那小時（8 月 31 日）有 16% 的 Sonnet 4 請求受影響
- **使用者影響**：約 30% 的 Claude Code 使用者至少收到一則劣化訊息
- **陰險的細節**：路由是「黏著的」—— 一旦碰上壞伺服器，後續請求會一直導向那裡
- **修復**：9 月 4–18 日（跨平台逐步推出）

### Bug #2 —— TPU 輸出損壞

TPU 伺服器上的一項設定錯誤導致 token 生成時出錯，把高機率分配給本該極少出現的 token。

- **症狀**：英文回覆中途冒出泰文或中文字、明顯的程式碼語法錯誤
- **受影響**：Opus 4.1 與 Opus 4（8 月 25–28 日）、Sonnet 4（8 月 25 日–9 月 2 日）
- **範圍**：僅 Claude API；第三方平台未受影響
- **修復**：9 月 2 日回滾

### Bug #3 —— XLA:TPU 編譯器誤編譯（最棘手的一個）

一項為修正精度問題的程式碼變更，意外引爆了 Google XLA:TPU 中一個**潛伏的編譯器 bug**。

- **根本原因**：近似 top-k 運算（用來挑選最可能的下一個 token）「有時會回傳完全錯誤的結果，但只在特定批次大小與模型設定下發生」
- **為什麼很難找**：它的行為會依前後執行了什麼運算、以及是否啟用除錯工具而改變
- **隱藏數月**：2024 年 12 月的一個早期權宜修正，意外遮蔽了這個更深層的 bug
- **受影響**：確認 Haiku 3.5；疑似影響部分 Sonnet 4 與 Opus 3
- **解法**：從近似 top-k 改為精確 top-k；接受「輕微效率影響」，因為「模型品質沒有商量餘地」

### 為什麼偵測這麼困難

Anthropic 自己的自動化評測沒有抓到使用者回報的劣化，「部分原因是 Claude 通常能從孤立的錯誤中順利恢復」。每個 bug 在不同平台以不同比率產生不同症狀，形成「一團混亂、指不向任何單一成因的回報」。

關鍵背景：Claude 跑在**三種不同的硬體平台**（AWS Trainium、NVIDIA GPU、Google TPU）上，各有不同的失效模式、編譯器與精度行為。你的請求在不同日子可能打到不同硬體。

## 已證實的成因：MoE 路由變異

現代大型模型常採用 **Mixture-of-Experts（MoE）** 架構，每個輸入只會啟動模型參數的一個子集（「專家」）。由一個學習而來的路由器決定要用哪些專家。

Scale AI 的研究揭露了一個關鍵發現：

> 「稀疏 MoE 與批次推論的結合會產生不可預測的結果，因為一個批次的組成可以決定你的查詢被路由到哪個專家，而同一批次中其他使用者的查詢組合並不是確定性的。」

### 各供應商實測的逐日變異

| 供應商 | 逐日分數變異 |
|----------|--------------------------|
| OpenAI（GPT-4 系列） | ±10–12% |
| Anthropic（Claude 系列） | ±8–11% |
| Google（Gemini 系列） | ±9–14% |

具體例子：同一個模型在**某天的 jailbreak 抵抗力拿 77%，隔天只拿 63%**。同樣的模型、同樣的權重、同樣的測試 —— 單憑基礎設施就有 14 個百分點的擺盪。

這表示即使零 bug、零變更，同一個模型在不同日子也可能純因請求如何批次與路由而產生明顯不同的輸出品質。當逐日雜訊有 10–15% 時，A/B 測試無法可靠地偵測 5% 的品質訊號。

## 已證實的成因：System Prompt 與後訓練更新

### System Prompt 變更

模型權重不變，但包覆那些權重的 **system prompt** 隨時可以更新。對 Claude system prompt 演進的分析顯示有數十次迭代，其中「hot-fix」（為修補不良行為而加入的簡短指令）經常被加入與移除。

Claude 3.7 的 system prompt 含有多條針對常見 LLM「陷阱」的 hot-fix 指令。Claude 4.0 的 system prompt 把它們全部移除，改為在後訓練階段透過強化學習處理那些行為。

### 後訓練理論

對於無法解釋的品質變化，最合理的理論是：公司可以在不改動基礎模型權重的情況下更新 **fine-tuning 與 RLHF**（人類回饋強化學習）。這在技術上讓「模型沒有改變」這句話仍然成立，同時又透過更新的安全護欄與指令遵循調整改變了行為。

## 已證實的成因：悄悄換模型

OpenAI 已多次被記錄到悄悄更換使用者互動的模型：

- 一夜之間移除模型選擇器，強迫使用者從 GPT-4o 轉到 GPT-5
- 把 GPT-4o 變成隱藏的「legacy model」，需在設定中手動切換，且 App 內沒有通知
- 一個「autoswitcher」bug 把使用者導到錯誤的模型
- 另外有付費訂閱者回報模型在未經同意下切換到「受限版本」

Sam Altman 承認這次推出「比我們預期的更顛簸一些」。Reddit 討論串獲得數千個讚，稱新模型是「災難」與「降級」。

這顯示模型更換在業界**確實會發生** —— 有時是刻意的（產品決策），有時是意外的（路由 bug）。

## 其他促成因素

### 高負載下的量化

為了以合理成本服務數百萬使用者，公司可能提供**量化後**的模型版本 —— 把精度從 FP16 降到 INT8 或 INT4。這能減少 2–4 倍記憶體用量並加速推論，但會引入細微的品質損失。供應商是否會在高負載下動態切換量化等級仍有爭議，但技術能力確實存在，且在 vLLM 與 TensorRT 這類服務框架中有完整記載。

### 推測解碼（Speculative Decoding）

現代服務堆疊會用較小的「草稿」模型預測接下來多個 token，再讓真正的模型驗證。理論上這能保持相同的輸出分布，但實務上接受率會依領域與脈絡而異。現成的草稿模型在某些情況下運作良好，但面對領域專屬任務或極長脈絡時常常吃力。

### 脈絡視窗污染

在長時間的寫程式 session 中，早期的錯誤會累積在脈絡裡。模型看到自己的錯誤，可能把它們延續下去。這是單一 session 內「Claude 變笨了」最常見的成因 —— 不是模型退化，是脈絡被污染。

**實用技巧**：覺得品質不對勁時用 `/compact` 或開新 session。這是你能做的最有實效的一件事。

## 史丹佛研究 —— 以及它為什麼沒那麼單純

史丹佛與 UC Berkeley（Chen、Zaharia、Zou）2023 年的指標性研究 ——「How is ChatGPT's Behavior Changing Over Time?」—— 經常被引為 LLM 會退化的證據。主要發現：

> GPT-4 在「這個數字是質數嗎？一步步想」的準確率，從 2023 年 3 月到 6 月由 **97.6% 掉到 2.4%**。

### 這項研究證明了什麼

- 「同一個」LLM 服務的行為**可以在短期內大幅改變**
- 不同能力可能往相反方向移動（GPT-4 數學變差，GPT-3.5 變好）
- 程式碼生成品質下滑（GPT-4 可執行程式碼：52% → 10%）
- 這項研究創造了 **「LLM drift」** 一詞

### 方法論上的批評

- 3 月版本使用 **temperature 0.0**，6 月版本使用 **temperature 1.0** —— 這是一個增加隨機性的根本性混淆變數
- 每個任務只有 **500 筆查詢** —— 對確定性的統計主張來說太少
- 所謂的「數學題」其實是是／非題，改變的是模型的猜測模式，不是它的數學能力
- 這些變化很可能反映的是刻意的**後訓練安全更新**，而非退化

這項研究證明了一件重要的事 —— LLM 行為會隨時間改變 —— 但其機制很可能是刻意的更新，不是非刻意的退化。

## 心理因素

### 確認偏誤

一旦有人發推說「Claude 今天很笨」，你就開始注意到每一個錯誤。沒人抱怨的日子裡，同樣的錯誤你會一笑置之。社群媒體放大了這個效應。

### 蜜月期效應

使用者對新模型會先經歷一段蜜月期，然後逐漸發現限制。模型沒有改變 —— 是期待上升的速度超過了能力該有的幅度。

### 任務難度的變異

你的任務每天都不一樣。碰到一整天硬題目，感覺就像模型變差了，即使它根本沒變。

### 「週末 Claude」迷思

儘管許多使用者相信有星期幾的規律，嚴謹的分析**沒有找到一致的證據**支持星期幾與品質的關聯。一篇標題為「AI is Dumber on Mondays」的分析最後是空手而回。

### LLM 的隨機本質

LLM 是機率性的。同一個 prompt 每次可能產生不同輸出。運氣差的時候，你可能連續拿到好幾個糟糕的回覆 —— 純粹是隨機性，不是退化。

---

## 結論

使用者描述的現象是**真實的，但歸因錯了**：

- **正確的**：他們的體驗在某些日子確實變差
- **不正確的**：模型被刻意「削弱」

真正的成因是以下的組合：

1. **基礎設施 bug** —— 由 Anthropic 的事後檢討證實（多達 16% 的請求受影響）
2. **MoE 路由變異** —— Scale AI 實測到 ±8-14% 的品質擺盪，即使零變更
3. **System prompt 與後訓練更新** —— 各供應商都有紀錄
4. **硬體異質性** —— TPU vs GPU vs Trainium，各有不同失效模式
5. **脈絡污染** —— 長 session 會在 session 內劣化品質
6. **確認偏誤** —— 社群媒體放大了感知到的規律
7. **隨機變異** —— 同樣的模型、同樣的 prompt，每次輸出都不同

測量問題很嚴重：±8-14% 的逐日變異代表你無法把真實的 5% 品質變化與雜訊區分開來。這就是為什麼「都是你的錯覺」和「他們把模型削弱了」兩派都覺得自己很有把握 —— 訊噪比讓人不可能單憑個人經驗判斷。

# 🔥 Codex 5.3 高推理與發現

### 報告範圍

本節說明為什麼使用者可能經歷一個短暫時段，Claude 輸出品質下降，而 Codex 5.3 在寫程式任務上感覺穩定或更強。焦點不在永久性的模型品質排名，而在真實服務條件下的短期生產行為。

報告日期：2026 年 3 月 5 日。

### 觀察到的模式

回報的模式是：

1. 模型品質在一段期間內是可接受的。
2. 品質看似連續數天下降。
3. 品質回到接近先前的基準。

這種形狀通常是服務堆疊或推出（rollout）的模式，不是永久性的基礎模型能力改變。永久性的能力衰退通常不會在沒有明確回滾或修復的情況下這麼快恢復。

### 高推理：為什麼 Codex 5.3 在壞時段看起來更好

Codex 5.3 可能在另一家供應商的劣化期間顯得明顯更強，有幾個技術原因，而且可能同時發生：

1. 產品目標契合度。Codex 5.3 為程式碼生成與 agentic 寫程式工作流最佳化，所以即使原始模型強度相同，也會因工具編排、repository 推理與以程式碼為核心的指令微調而產生更好的寫程式結果。
2. 推論政策差異。各供應商獨立調整延遲、推理深度與解碼預設值。同一天內，某一方較保守的政策看起來可能比另一方積極追求速度的政策「更聰明」。
3. 服務路徑分離。即使兩家供應商都託管最先進模型，它們跑的是不同的路由層、編譯器／執行期堆疊與推出管線。一方堆疊的事故不代表另一方有相關聯的劣化。
4. 推出與回滾時機。若一方正在推出中而另一方穩定，使用者會看到很大的暫時性品質分歧，而底層模型權重並無長期改變。
5. Session 層級的污染效應。在長時間的寫程式對話中，錯誤累積會放大感知到的下滑。另一個助理感覺更好，可能只是因為失敗的 session 被重設了，或因為它的工具迴圈恢復得更快。

### 詳細發現

對於「Claude 大概弱了四天，然後又回來了」這類回報，最可能的解釋是：

1. 供應商端的事故、路由問題、解碼／執行期 bug 或推出回歸影響了部分請求。
2. 問題持續夠久，在真實工作流中被反覆注意到。
3. 問題被修復或回滾。
4. 感知品質很快回復。

在同一期間，Codex 5.3 可能感覺好很多，因為它不共用同一條事故路徑，而且寫程式任務的最佳化放大了實務結果上的差距。

### 此模式的假說排序

| 假說 | 可能性 | 理由 |
|------------|------------|-----------|
| 供應商事故加回滾 | 高 | 最符合「多日下滑後快速恢復」的形狀 |
| 服務設定變更（取樣／延遲／推理預算） | 高 | 不需重新訓練就造成突然行為轉變的常見來源 |
| 悄悄移動別名或快照 | 中高 | 可以在使用者沒有任何動作下改變行為 |
| 僅 prompt 漂移與脈絡污染 | 中 | 能使 session 劣化，但較難單獨解釋廣泛的多日回報 |
| 永久性基礎模型退化 | 低 | 與快速回到先前品質的現象不一致 |

### 什麼能證實或推翻這個發現

要把這從高信心推論變成確鑿證據，需要跨日針對同一組任務收集請求層級的遙測資料：

1. 請求當下的確切模型識別碼與快照／別名。
2. 供應商暴露的任何後端指紋或版本標記。
3. 解碼參數（temperature、top_p、top_k、max tokens）。
4. 延遲、逾時與錯誤率軌跡。
5. 在固定的寫程式基準 prompt 集上的結構化品質分數。
6. 失敗點的 session 長度與 token 脈絡深度。

若品質下降與事故時段、設定變更或後端指紋變動相關，則事故／設定假說成立。若沒有這類變動，且劣化只出現在長 session 中，那脈絡污染就是主要解釋。

### 實務工程指引

要降低生產環境的逐日變異：

1. 可用時鎖定模型快照，不要用浮動別名。
2. 儲存請求的中介資料（model ID、參數、延遲、錯誤、回應品質標籤）。
3. 針對寫程式任務跑固定的每日金絲雀測試組，並在回歸時告警。
4. 連續數個回合失敗後，重設或壓縮長時間執行的 session。
5. 為事故時段保留備援的供應商／模型路徑。
6. 在內部儀表板上把「模型品質」與「服務可靠度」分開。

### 最終結論

在 Claude 短暫劣化的時段裡 Codex 5.3 看起來更好，在現代 LLM 維運中是技術上合理且可預期的結果。最強的解釋不是永久性的模型崩壞，而是某一方暫時性的服務路徑劣化，加上另一方在同期的寫程式專屬最佳化與穩定運作。
