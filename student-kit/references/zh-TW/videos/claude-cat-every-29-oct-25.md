## 逐字稿

[`0:02`](https://youtu.be/IDSAMqip6ms?t=2) 讓它運作得這麼好的關鍵是：**Claude Code 能存取工程師在終端機裡能存取的一切**。你能做的每件事，Claude Code 都能做，中間沒有任何隔閡。

[`0:10`](https://youtu.be/IDSAMqip6ms?t=10) Anthropic 內部用掉大量額度的人越來越多 —— 每個月花超過一千美元。我們看到這種超級使用者行為。

這是 YC 教的事：如果你能解決自己的問題，你解決別人問題的機率就高得多。

產品上有個很老的概念叫**潛在需求**：你用一種「可被 hack、夠開放」的方式打造產品，讓人們能把它濫用在它本來沒設計的用途上，然後你為那個用途而建 —— 因為你知道那裡有需求。

你覺得 CLI 是最終形態嗎？一年後、三年後我們還會主要在 CLI 裡用 Claude Code 嗎？

[`1:32`](https://youtu.be/IDSAMqip6ms?t=92) 對不認識你們的人說明，你們是 Claude Code 的創造者。我打從心底感謝你們，我愛 Claude Code。

[`1:42`](https://youtu.be/IDSAMqip6ms?t=102) 聽到這個太棒了。

我想從我第一次用它開始講起。大概是 Sonnet 3.7 出來的時候，我用了之後想：天啊，這是個全新典範，是思考程式碼的全新方式。

而最大的差別是：**你們走到底、直接消滅了文字編輯器**，你做的就只是跟終端機說話，就這樣。而先前 AI 編程的典範、先前的 harness 都是：你有個文字編輯器，AI 在旁邊，或者是 tab 補全。

帶我走過那個決策過程、那個architecting 新典範的過程。你們是怎麼想的？

[`2:36`](https://youtu.be/IDSAMqip6ms?t=156) 最重要的一點是：**那完全不是刻意的**。（笑）

[`2:42`](https://youtu.be/IDSAMqip6ms?t=162) 我們就是這樣走到這裡的。

我加入 Anthropic 時我們還在不同團隊。當時有個 Claude Code 的前身叫 **Clyde**。那是個研究專案，啟動要一分鐘，是個相當重的 Python 東西，得跑一堆索引之類的。

我加入後想送出我的第一個 PR，我像個菜鳥一樣手寫它 —— 我不知道有這些工具、我不懂更好的做法。我把 PR 開出來，而 Adam Wolff（當時我們團隊的 manager，也是我的上手夥伴）直接把 PR 打回來，說：「你是手寫的？你在幹嘛？用 Clyde 啊。」因為他當時也在大量 hack Clyde。

所以我試了 Clyde。我給它任務描述，它就一次搞定了。

[`3:39`](https://youtu.be/IDSAMqip6ms?t=219) 那是 Sonnet 3.5 的時代，所以即使是這種基本任務我還是得修一下，而且 harness 超舊，吐出東西要五分鐘、慢得要命。但它**成功了**，而我完全被震撼 —— 這居然是可能的。那開始讓齒輪轉動：也許你其實不需要 IDE。

[`4:02`](https://youtu.be/IDSAMqip6ms?t=242) 後來我在用 Anthropic API 做原型，而最容易的方式就是在終端機裡做個小 App，因為那樣我不必做 UI。

我開始做一個小聊天 App，然後開始想：也許我們能做點像 Clyde 的東西。所以讓我做個小 Clyde 吧。結果它在沒花多少工夫的情況下，變得有用得多。

而對我來說最大的啟示是我們開始**給模型工具**的時候。它就開始使用工具，那是個瘋狂的時刻 —— **模型就是想用工具**。我們給了它 bash，它就開始用 bash、寫 AppleScript 去自動化東西來回答問題。我想：這太誇張了，我從沒看過這種東西。

因為當時我只用過 IDE 的文字編輯、一行自動補全、多行自動補全之類的。

所以這就是它的來源：原型製作，加上以一種很粗糙的方式看到什麼是可能的。

[`5:03`](https://youtu.be/IDSAMqip6ms?t=303) 而這東西結果出乎意料地有用。我想對我們也一樣 —— 對我來說魔法時刻大概是 Sonnet 4、Opus 4，那時我想：天啊，這東西真的行。

[`5:17`](https://youtu.be/IDSAMqip6ms?t=317) 有意思。談談那個「工具時刻」，因為我覺得那是 Claude Code 很特別的地方之一：它就是寫 bash，而且寫得非常好。

我想很多先前的代理架構、甚至今天任何在做代理的人，第一直覺會是：好，我們給它一個 find file 工具、一個 open file 工具，為代理可能要做的各種動作建一堆自訂包裝。但 Claude Code 就是用 bash，而且用得超好。你從中學到什麼？

我想我們現在這個時點，Claude Code 其實有一堆工具，大概十幾個。我們**幾乎每週都在增刪工具**，變動相當頻繁。

今天確實有一個搜尋工具。我們這樣做有兩個理由：

一是 **UX** —— 我們能把結果更漂亮地呈現給使用者，因為目前大多數任務仍然有人在迴圈裡。

二是**權限** —— 如果你在 `settings.json` 裡說某個檔案不能讀，我們得強制執行。我們對 bash 有強制機制，但如果有專門的搜尋工具，我們能更有效率地做到。

但我們肯定想**下架工具、為模型保持簡單**。例如上週或兩週前我們下架了 `ls` 工具，因為過去需要它，但後來我們建了一套能對 bash 強制這種權限系統的方法。所以在 bash 裡，如果我們知道你不被允許讀某個目錄，Claude 就不被允許 `ls` 那個目錄。而因為我們能一致地強制這點，我們就不再需要那個工具了。

這很好，因為**對 Claude 來說選擇少了一點、脈絡裡的東西少了一點**。

[`7:01`](https://youtu.be/IDSAMqip6ms?t=421) 你們在團隊裡怎麼分工？

[`7:06`](https://youtu.be/IDSAMqip6ms?t=426) 我會說 Boris 設定技術方向，也是我們推出的許多功能的產品願景者。我把自己看成比較支援性的角色：一是確保我們的定價與包裝能打中使用者；二是確保我們把所有功能護送過發布流程 —— 從決定哪些原型該進內部試用（ant-fooding），到設定內部試用的品質門檻，再到對終端使用者溝通。

我們也在做一些新計畫。歷史上 Claude Code 很多是**由下而上**建起來的 —— Boris 和很多核心成員就是有了這些好點子：待辦清單、子代理、hooks，全都是由下而上。

而當我們思考擴展到更多服務、把 Claude Code 帶到更多地方時，我想那些比較像是：好，我們來跟客戶聊，把工程師帶進那些對話，為那些服務排優先序，然後一個個解決。

[`8:08`](https://youtu.be/IDSAMqip6ms?t=488) 什麼是 ant-fooding？

[`8:14`](https://youtu.be/IDSAMqip6ms?t=494) 就是 dog-fooding（自家試吃）的意思。

[`8:19`](https://youtu.be/IDSAMqip6ms?t=499) Anthropic → ant（螞蟻）。懂了。

[`8:22`](https://youtu.be/IDSAMqip6ms?t=502) 對，我們內部員工的暱稱是 ant，所以 ant-fooding 就是我們版本的 dog-fooding。

內部大概 70% 到 80% 的技術員工每天都用 Claude Code。所以每次我們在想一個新功能，就推給內部的人用，然後拿到超多回饋。我們有個回饋頻道，我想大概每五分鐘就有一則貼文。所以你能很快知道人們喜不喜歡、有沒有 bug、或者它不好、我們該下架它。

[`8:57`](https://youtu.be/IDSAMqip6ms?t=537) 你看得出來，做這東西的人一直在用它來做東西 —— 因為它的人體工學只有在你真的在做東西時才會合理，而那只有在你 ant-food 時才會發生。

我覺得那是個很有意思的打造新東西的典範：由下而上、我為自己做一個東西。談談那個。

[`9:23`](https://youtu.be/IDSAMqip6ms?t=563) Cat 太謙虛了。我覺得 Cat 在產品方向上也有很大的角色。而這些想法來自團隊上每一個人 —— 待辦清單與子代理是 Sid 做的、hooks 是 Dixon 出貨的、外掛是 Daisy 出貨的。

[`9:38`](https://youtu.be/IDSAMqip6ms?t=578) 這些點子來自團隊上每個人。所以我想對我們來說：我們建了這個核心代理迴圈與核心體驗，然後團隊上每個人一直在用這個產品，團隊外每個人也一直在用。於是就有各種機會去建出服務這些需求的東西。

例如 **bash 模式** —— 驚嘆號，你可以直接輸入 bash 命令。那是好幾個月前，我在用 Claude Code，一直在兩個終端機之間切換，覺得有點煩。我一時興起叫 Claude 想點子，它想出了這個驚嘆號 bash 模式。然後我說：很好，把它弄成粉紅色，然後出貨。（笑）它就做了。而那個東西一直留到現在。你現在也看到其他人開始跟進了。

[`10:24`](https://youtu.be/IDSAMqip6ms?t=624) 好笑，我其實不知道這個。那超有用的，因為我老是得開新分頁去跑 bash 命令。所以你就打驚嘆號，它就直接跑，而不用經過所有 Claude 的東西過濾？

[`10:38`](https://youtu.be/IDSAMqip6ms?t=638) 對。而且 **Claude Code 也看得到完整輸出**。

[`10:42`](https://youtu.be/IDSAMqip6ms?t=642) 所以任何你在 Claude Code 畫面裡看到的東西，Claude Code 也看得到。

[`10:46`](https://youtu.be/IDSAMqip6ms?t=646) 這是我們一直在思考的 UX 問題。以前工具是為工程師而建的，但現在是**工程師與模型各佔一半**。

[`10:53`](https://youtu.be/IDSAMqip6ms?t=653) 身為工程師你能看到輸出，但那對模型其實也相當有用。這也是哲學的一部分：**一切都是雙用途的**。

例如模型也能呼叫 slash command。我有個 `/commit` 命令，會走過幾個步驟 —— 做 diff、產生合理的 commit 訊息之類的。我會手動執行它，但 Claude 也能幫我執行。這相當有用，因為我們共享了這段邏輯：我們定義這個工具，然後我們兩邊都能用。

[`11:24`](https://youtu.be/IDSAMqip6ms?t=684) 設計「雙用途」工具跟設計「只給其中一方用」的工具，差別是什麼？

出乎意料地，**一樣**。

[`11:34`](https://youtu.be/IDSAMqip6ms?t=694) 至少目前為止是。

[`11:36`](https://youtu.be/IDSAMqip6ms?t=696) 我有種感覺：為人類設計的這種優雅設計，轉譯到模型上也非常好。

[`11:41`](https://youtu.be/IDSAMqip6ms?t=701) 所以你就想「什麼對我合理」，而通常**如果對你合理，對模型也合理**。

[`11:49`](https://youtu.be/IDSAMqip6ms?t=709) 我想 Claude Code 作為終端機 UI 很酷的一點、也是讓它運作得這麼好的原因是：**Claude Code 能存取工程師在終端機裡能存取的一切**。

至於工具該不該是雙用途 —— 我認為把它們做成雙用途其實讓工具**容易理解得多**。它的意思就是：你能做的每件事，Claude Code 都能做，中間沒有任何隔閡。

[`12:14`](https://youtu.be/IDSAMqip6ms?t=734) 有幾個這樣的決策：沒有程式碼編輯器、在終端機裡所以能存取你的檔案；而且它在你的電腦上而不是雲端虛擬機裡，所以你能反覆地用它 —— 你能累積你的 CLAUDE.md、建立 slash command 等等，從一個非常簡單的起點變得非常可組合、可擴充。

我好奇：對那些想「我要做一個代理 —— 大概不是 Claude Code，而是別的東西」的人，你們怎麼想「如何得到那個簡單的核心包裝，然後隨時間擴展並變得非常強大」？

[`13:07`](https://youtu.be/IDSAMqip6ms?t=787) 對我來說，我會先把它當成開發任何產品那樣想：**你得先為自己解決問題，才能為別人解決**。

這是 YC 教的事：你得從自己開始。如果你能解決自己的問題，你解決別人問題的機率就高得多。

對寫程式來說，**從本機開始**是合理的。而現在我們也有網頁版 Claude Code，你能用虛擬機、能在遠端環境用它，當你在移動中、想用手機處理時超級有用。

[`13:43`](https://youtu.be/IDSAMqip6ms?t=823) 我們是一步步驗證這件事的 —— 你能在 GitHub 上 @claude。我每天都在用，像是上班途中紅燈時（我大概不該這樣做）我就在 GitHub 上說「@claude 修這個 issue」。能從手機控制它真的很有用，而這驗證了這個體驗。

我不確定這對每種使用情境都合理。對寫程式來說，從本機開始是對的。但我不確定這對所有東西都成立。

[`14:07`](https://youtu.be/IDSAMqip6ms?t=847) 你們用哪些 slash command？

[`14:11`](https://youtu.be/IDSAMqip6ms?t=851) `/commit`。

[`14:15`](https://youtu.be/IDSAMqip6ms?t=855) 我想 commit 命令讓 Claude 快得多地知道該跑哪些 bash 命令來做 commit。

[`14:24`](https://youtu.be/IDSAMqip6ms?t=864) 對不熟的人說明，commit 這個 slash command 做什麼？

就是明確告訴它怎麼做 commit。

[`14:33`](https://youtu.be/IDSAMqip6ms?t=873) 你可以說：好，這是需要跑的三個 bash 命令。

[`14:37`](https://youtu.be/IDSAMqip6ms?t=877) 而很酷的是我們在 slash command 裡內建了一套**樣板系統**：我們會**預先執行**那些 bash 命令，它們等於嵌進了 slash command 裡。

你也可以**預先允許特定工具呼叫**。所以那個 slash command 我們寫：允許 `git commit`、`git push`、`gh`。這樣你跑完 slash command 後就不會被問權限，因為我們有基於權限的安全系統。

而且它還用 **Haiku**，這很酷 —— 比較便宜也比較快的模型。

對我來說我用 commit、commit PR，還有 **feature-dev** 我們用很多。那是 Sid 做的，很酷：它會一步步帶你建東西。我們會提示 Claude 先問我到底想要什麼、建立規格，

[`15:27`](https://youtu.be/IDSAMqip6ms?t=927) 然後做出詳細計畫，再做一份待辦清單、一步步走過。算是更結構化的功能開發。

[`15:35`](https://youtu.be/IDSAMqip6ms?t=935) 然後最後一個我們大概用很多的是 **security review**，我們所有 PR 都跑；還有 **code review**。Anthropic 內部所有 code review 都是 Claude 做的 —— 還是有人類核准，但 Claude 做 code review 的第一步。那就只是一個 `/code-review` 命令。

[`15:51`](https://youtu.be/IDSAMqip6ms?t=951) 我想深入談「怎麼做出好的計畫」，也就是 feature-dev 那件事。因為我開始發現、Every 的人也開始發現一些有效的小技巧，我好奇我們漏了什麼。

例如計畫開發流程中一個不直覺的步驟：即使我還不確切知道要建什麼、腦中只有一句「我想要功能 X」，我就讓 Claude 直接去實作，不給它別的東西，然後看它做了什麼。這幫我理解「我真正的意思是什麼」—— 因為它犯了那些錯、或做了我沒預期的事（而那可能是對的）。

然後我把那次拋棄式開發學到的東西拿來用，清掉它，然後寫出一份更好的計畫規格給真正的功能開發。

這是以前你絕對不會做的事，因為「把一位工程師直接丟上一個你還沒規格化的功能」太貴了。但因為你有 Claude 走過你的 codebase 做事，你能從中學到東西，而那能為你真正要做的計畫提供資訊。

[`17:04`](https://youtu.be/IDSAMqip6ms?t=1024) 我先講，也好奇你怎麼用。

[`17:07`](https://youtu.be/IDSAMqip6ms?t=1027) 對我來說大概有幾種不同模式。一是**原型模式**。

[`17:12`](https://youtu.be/IDSAMqip6ms?t=1032) 傳統工程的原型製作，你會想建出「碰到所有系統的最簡單東西」，好讓你大致感覺到有哪些系統、有哪些未知、把整條路走一遍。

[`17:24`](https://youtu.be/IDSAMqip6ms?t=1044) 所以我做的跟你完全一樣，Dan —— 讓 Claude 直接做，然後看它在哪裡搞砸，然後叫它丟掉重做。就按兩下 Esc 回到舊的檢查點再試一次。

另外大概還有兩種任務。一是**Claude 能一次搞定、而我相當有信心它做得到的事**。那我就跟它說，然後切到另一個分頁，shift+tab 開 auto accept，去做別的事，或去照顧我另一個 Claude。

[`17:54`](https://youtu.be/IDSAMqip6ms?t=1074) 另外是**比較難的功能開發** —— 那些過去可能要花幾小時工程時間的事。這種我通常會 shift+tab 進 **plan 模式**，在它寫任何程式碼之前先對齊計畫。

[`56:42`](https://youtu.be/IDSAMqip6ms?t=3402) 現在要榨出那個「感覺」太容易了。以前你能視覺上看到它、或用文字描述它，但你永遠抓不到那個 vibe。現在 vibe 很容易取得。

[`56:53`](https://youtu.be/IDSAMqip6ms?t=3413) 而你把 plan 模式建了三次。

[`56:57`](https://youtu.be/IDSAMqip6ms?t=3417) 你建了它、丟掉、重建、再丟掉、再重建。

[`57:02`](https://youtu.be/IDSAMqip6ms?t=3422) 對。或像待辦清單，Sid 做了原始版本，他做了三四個原型，然後我在一天內又做了大概 20 個版本。

我想我們釋出的幾乎每樣東西，背後都至少有幾個原型。

**問：你們怎麼追蹤並把原型之間學到的東西帶下去？特別是如果某人做了原型，然後你接手再做 20 個。怎麼榨出最大價值？**

大概有幾個元素。

一是**風格指南**。我們會發現一些風格元素 —— 很多是關於「為終端機而建」，我們等於在發現終端機的新設計語言、邊做邊建。其中有些你可以編碼進風格指南，也就是我們的 CLAUDE.md。

但另一部分是**產品直覺**，我不認為模型完全懂這個。也許我們該想辦法教模型這種產品直覺 —— 什麼有效、什麼無效。因為在產品上，你想用最簡單的方式解決那個人的問題，然後把其他不是那個的東西全部刪掉、讓一切讓路。你盡可能乾淨地把產品對齊到意圖。而模型大概還不完全懂那件事。

[`58:24`](https://youtu.be/IDSAMqip6ms?t=3504) 它從來沒有「使用 Claude Code 是什麼感覺」的體驗 —— 模型不會用 Claude Code。

[`58:31`](https://youtu.be/IDSAMqip6ms?t=3511) 對。不過 Claude Code 能測試自己、能用自己 —— 我們開發時就這樣做，它能看到 UI bug 之類的。我不知道，也許我們就該試著 prompt 它看看。老實說很多事就這麼簡單：有新想法時你通常就 prompt 它，而它常常就成了。也許我們就該試試。

[`58:57`](https://youtu.be/IDSAMqip6ms?t=3537) 很多原型其實是 **UX 互動**。所以一旦我們發現一個新的 UX 互動 —— 例如 shift+tab 開 auto accept —— 我以為是 Boris 想出來的……

[`59:11`](https://youtu.be/IDSAMqip6ms?t=3551) 其實是 Eigor。

[`59:16`](https://youtu.be/IDSAMqip6ms?t=3556) 我們做了大概一週的「對決原型」。（笑）

[`59:20`](https://youtu.be/IDSAMqip6ms?t=3560) shift+tab 感覺真的很好。而現在這一版的 plan 模式也用 shift+tab，因為那其實就是另一種告訴模型「它該多 agentic」的方式。

[`59:35`](https://youtu.be/IDSAMqip6ms?t=3575) 我想當越多功能使用同一個互動，你就形成越強的心智模型，知道什麼該放哪裡。

[`59:42`](https://youtu.be/IDSAMqip6ms?t=3582) **thinking** 也是個很好的例子。在我們發布 Claude Code 之前、或者說第一個 thinking 模型（3.7 吧？）出來時，

[`59:54`](https://youtu.be/IDSAMqip6ms?t=3594) 它能思考了，我們在腦力激盪「我們要怎麼切換思考？」然後有人說：**如果就用自然語言叫模型思考呢？它知道怎麼思考啊。** 我們說：好耶，就這樣做。

所以我們這樣做了一陣子，然後發現人們會不小心觸發它 —— 他們說「don't think（不要想）」，而模型想「喔我該思考」，就開始思考了。（笑）

[`1:00:15`](https://youtu.be/IDSAMqip6ms?t=3615) 所以我們得把它調校掉，讓「don't think」不會觸發。但那仍然不夠明顯，所以我們做了 UX 改進把思考高亮出來。

[`1:00:23`](https://youtu.be/IDSAMqip6ms?t=3623) 那超好玩，感覺很魔幻。

[`1:00:25`](https://youtu.be/IDSAMqip6ms?t=3625) 你打 ultrathink 時它會變彩虹色之類的。（笑）

然後在 Sonnet 4.5 上，我們發現開啟延伸思考時有**非常非常大的效能提升**。所以我們讓切換它變得很容易，因為有時你要、有時你不要 —— 對非常簡單的任務你不會想讓模型想五分鐘，你要它直接做。所以我們用 tab 作為切換的互動。然後我們下架了一堆 thinking 關鍵字，不過 ultrathink 我們留著，純粹是為了情感因素。（笑）那個 UX 太酷了。

[`1:01:02`](https://youtu.be/IDSAMqip6ms?t=3662) 你覺得會不會有一個關於「你刪掉了什麼」的新指標？程式設計師一直覺得刪掉一堆程式碼很爽，但因為現在能這麼快建東西，**刪東西也變得更重要**。

我最愛看到的 diff 就是**紅色的 diff**。（笑）每次我都想：來吧，再來一個，再來一個。

但這很難，因為你出貨的任何東西都有人在用，你得讓人們開心。所以我們的原則大致是：**如果我們要下架某樣東西，我們得出貨更好的東西** —— 能更好地匹配那個意圖、讓人們能受益的東西。

這也回到「怎麼衡量 Claude Code 的影響」—— 每家公司、每個客戶都問我們這個。在 Anthropic 內部，我們大概從一月以來人數翻倍，但同期每位工程師的生產力提升了將近 70%。

[`1:02:03`](https://youtu.be/IDSAMqip6ms?t=3723) 我們用幾種方式衡量，而 PR 是最簡單也是主要的那個。

但就像你說的，**這沒有捕捉到全貌**，因為其中很多是「讓做原型更容易、讓嘗試新東西更容易」—— 那些你本來永遠不會去試、因為遠在取捨線以下的東西。你在推出一個功能，有一份願望清單，而現在你全部都做了，因為太容易了。

[`1:02:25`](https://youtu.be/IDSAMqip6ms?t=3745) 而你本來根本不會去做。

[`1:02:27`](https://youtu.be/IDSAMqip6ms?t=3747) 所以真的很難談。而反面是：**更多程式碼被寫出來，所以你得刪更多程式碼、得更仔細做 code review、得盡可能自動化 code review。**

還有一個有趣的新產品管理挑戰：因為你能出貨這麼多，最後東西會**不夠有凝聚力** —— 你在這裡加個按鈕、那裡加個分頁、這裡加個小東西。建出「有你想要的所有功能、但沒有任何組織原則」的產品變容易多了，因為你一直在大量出貨。

我們試著對這件事相當有紀律，確保所有抽象都很容易理解 —— 即使別人只聽到功能的名字也懂。

我們有個原則（我相信是 Boris 帶進團隊的）我很喜歡：**我們不要有「新使用者體驗」**。一切都該直覺到你一進來它就能動。我想那把「確保每個功能都很直覺」的標準拉得很高。

**問：在對話式 UI 上怎麼做到這件事？因為沒有一堆按鈕和旋鈕，一開始就只是個空白文字框。**

[`1:03:37`](https://youtu.be/IDSAMqip6ms?t=3817) 我們做了很多小事：我們教人們可以用問號看提示；Claude Code 工作時我們會顯示提示；側邊有 changelog；我們會告訴你有新模型；底部有個思考的通知區。就是用各種細微的方式告訴使用者有哪些功能。

另一件很重要的事是：**確保所有原語都定義得非常清楚**。hooks 在開發者生態系有共同的意義、plugins 也有共同的意義。要確保我們建的東西，符合一般開發者聽到那個詞時立刻會想到的東西。

[`1:04:25`](https://youtu.be/IDSAMqip6ms?t=3865) 還有**漸進式揭露**。在 Claude Code 裡任何時候你都能按 Ctrl+O 看到完整原始逐字稿 —— 跟模型看到的一樣。但我們不會在它真正相關之前就顯示給你：當有個工具結果被收合時，我們才會說「用 Ctrl+O 可以看它」。我們不想一開始就把太多複雜度丟給你，因為這東西什麼都能做。

還有一個我們才剛開始探索的新原則：**模型教你怎麼用這個東西**。你可以問 Claude Code 關於它自己的事，它知道要去查自己的文件來告訴你。而我們還能更深：例如 slash command 是人們能用的東西，但模型也能呼叫 slash command —— 也許你看到模型呼叫它，然後想「喔，原來我也可以這樣做」。

[`1:05:13`](https://youtu.be/IDSAMqip6ms?t=3913) **問：你們剛開始做時，Claude Code 是獨特的東西、是透過 CLI 用 AI 的獨特方式。現在整個版圖上每個人都在做 CLI。這怎麼改變你們的思考、打造的感覺？你們怎麼應對這場競賽的壓力？**

[`1:05:39`](https://youtu.be/IDSAMqip6ms?t=3939) 對我來說，**模仿是最大的恭維**。看到其他人受此啟發做出各種東西很棒、很酷。而我想終極目標就是啟發人們為這項即將到來的驚人技術打造下一個東西，那真的很令人興奮。

我個人不太用其他工具。通常有新東西出來我可能會試一下抓個 vibe，但除此之外，我想我們相當專注在解決我們自己與客戶的問題、以及打造下一個東西。

[`1:06:25`](https://youtu.be/IDSAMqip6ms?t=3985) **（主持人被反問「下架」問題）**

我問那個問題是因為我覺得我們做得不好。我有種感覺，我們有些產品因此有點混亂。

特別是 Kora，它的產品面很大、能做很多不同的事：有 email 助理，你能問它「告訴我我要去的那趟旅行」，它會翻過你所有信件摘要那趟旅程；我們有個功能會自動封存你不需要立刻回覆的信；然後一天兩次你會收到一份簡報，摘要那些你大概需要看、但不需要實際處理的東西，你捲過去就完成了。

而圍繞著「信件怎麼分類」有一堆複雜度 —— 現在我們有整個分類規則的檢視、可以排序等等。但它就是複雜、難以溝通。我想保留所有的威力與彈性，但你也不能讓人看著一個畫面想「我完全不知道發生什麼事，這太複雜了」。

所以「刪除／下架」這個想法對我來說是個有趣、我們還沒真正探索的文化原則。

[`1:08:14`](https://youtu.be/IDSAMqip6ms?t=4094) 很難。我想那也有社交成本 —— 你得當那個叫同事下架他東西的人。（笑）

[`1:08:24`](https://youtu.be/IDSAMqip6ms?t=4104) 確實棘手，不只是程式碼的問題。

老實說我是在 Instagram 學到這件事的，因為我覺得 Facebook 在下架這件事上做得很糟。我們有這個問題：

[`1:08:34`](https://youtu.be/IDSAMqip6ms?t=4114) 連下架「戳一下（pokes）」都超辛辣，因為有一群老鳥說「不行，pokes 你們永遠別想拿走」。但看資料，根本沒人在用了。

[`1:08:44`](https://youtu.be/IDSAMqip6ms?t=4124) 但基於情感因素，他們就是放不下。

[`1:08:47`](https://youtu.be/IDSAMqip6ms?t=4127) 所以在 Facebook，幾乎沒有東西真的被下架，它們總是被搬到次要位置 —— 某個沒人看的溢出選單，像個墳場。

[`1:08:57`](https://youtu.be/IDSAMqip6ms?t=4137) 而 Instagram 就非常有原則。產品與設計的觀點非常強硬：**如果這東西沒被一半的人使用（例如 50% 週活），我們就刪掉它、面對後果，然後再想出更多人會用的下一個東西。**

[`1:09:13`](https://youtu.be/IDSAMqip6ms?t=4153) 我很喜歡。謝謝你們，這太棒了，很高興能跟你們聊，繼續打造吧。

[`1:09:18`](https://youtu.be/IDSAMqip6ms?t=4158) 謝謝邀請。
