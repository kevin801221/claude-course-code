## 逐字稿

[`0:01`](https://youtu.be/PQU9o_5rHC4?t=1) 在 Anthropic，我們的思考方式是：我們不為今天的模型而建，我們為六個月後的模型而建。這其實仍然是我給在 LLM 上開發的創辦人的建議 —— 試著想：模型今天還不太擅長的前沿在哪裡？因為它將會變得擅長。

Claude Code 的每一部分都被寫了又重寫、重寫、再重寫，一次又一次。六個月前存在的 Claude Code，現在沒有任何一部分還在。你試一個東西、把它給使用者、跟使用者聊、學習，最後可能會得到一個好點子。有時不會。

[`0:36`](https://youtu.be/PQU9o_5rHC4?t=36) 你心裡會不會也想著：也許六個月後你就不需要那樣明確下 prompt 了？模型會好到能自己搞清楚？

也許一個月後就是了。

[`0:38`](https://youtu.be/PQU9o_5rHC4?t=38) 一個月後就不再需要 plan 模式了。

（主持人開場）歡迎來到新一集的 The Light Cone，今天我們有位非常特別的來賓：Claude Code 的創造工程師 Boris Cherny。Boris，謝謝你來。

[`0:59`](https://youtu.be/PQU9o_5rHC4?t=59) 謝謝邀請。

[`1:00`](https://youtu.be/PQU9o_5rHC4?t=60) 謝謝你創造了一個讓我連續三週睡不著的東西。

[`1:07`](https://youtu.be/PQU9o_5rHC4?t=67) 我對 Claude Code 非常上癮，感覺像裝了火箭推進器。對你來說這種感覺持續好幾個月了吧？我朋友們大概是十一月底開始說「有什麼東西變了」。

[`1:21`](https://youtu.be/PQU9o_5rHC4?t=81) 我記得我第一次做出 Claude Code 時就是這種感覺 —— 當時我還不知道自己是不是抓到了什麼，但我覺得我抓到了。那時我就不睡了。

[`1:29`](https://youtu.be/PQU9o_5rHC4?t=89) 那整整持續了三個月。

[`1:33`](https://youtu.be/PQU9o_5rHC4?t=93) 那是 2024 年九月。整整三個月，我一天假都沒休，週末在工作，每個晚上都在工作。我就想：「天啊，我覺得這會成為一個東西。我還不知道它有沒有用，因為它那時還不會寫程式。」

[`1:48`](https://youtu.be/PQU9o_5rHC4?t=108) 從那些時刻回望到現在，最令你意外的是什麼？

[`1:54`](https://youtu.be/PQU9o_5rHC4?t=114) 難以置信的是我們還在用終端機。那本來只該是起點，我沒想到它會是終點。

第二個是它居然有用。一開始它根本不太寫程式；即使二月我們正式上線時，它大概只寫我 10% 的程式碼。我沒真的用它寫程式，它不太行，我大部分程式碼還是手寫。

所以我們的賭注居然兌現了 —— 它在我們押注的那件事上變強了，而那當時並不顯然。在 Anthropic，我們的思考方式是：我們不為今天的模型而建，我們為六個月後的模型而建。這仍然是我給在 LLM 上開發的創辦人的建議：試著想模型今天還不太擅長的前沿在哪裡，因為它將會變得擅長，你只需要等。

[`2:39`](https://youtu.be/PQU9o_5rHC4?t=159) 回頭說，你記得最初有這個想法是什麼時候嗎？是某個火花，還是你腦中最初的版本是什麼？

[`2:47`](https://youtu.be/PQU9o_5rHC4?t=167) 好笑的是，它完全是意外演化成這樣的。

對 Anthropic 來說，長期以來的賭注一直是寫程式 —— 通往安全 AGI 的路徑要經過寫程式。

[`3:03`](https://youtu.be/PQU9o_5rHC4?t=183) 這一直是那個想法，而達成的方式是：你教模型怎麼寫程式，然後教它怎麼用工具，然後教它怎麼用電腦。你可以從我在 Anthropic 加入的第一個團隊看出這點 —— 那叫 Anthropic Labs team，它產出了三個產品：Claude Code、MCP 與桌面 App。你可以看到這些怎麼交織在一起。

至於我們建的那個特定產品 —— 沒有人要我做一個 CLI。我們大致知道也許是時候做某種寫程式的產品了，因為模型看起來準備好了，但還沒有人真正做出駕馭這個能力的產品。所以那時有種瘋狂的「產品過剩（product overhang）」感 —— 而當時更誇張，因為根本還沒人建過。

所以我開始 hack，想：好，我們要做寫程式的產品，我得先做什麼？我得理解怎麼用 API，因為那時我還沒用過 Anthropic API。所以我做了一個小小的終端機 App 來用 API，就這樣。那是個小聊天 App，因為想想當時的 AI 應用 —— 今天對非寫程式的人來說，大多數人用的也就是聊天 App。所以我就做了那個，在終端機裡，我能問問題、它給答案。

然後 tool use 推出了。我只是想試試 tool use，因為我不太懂那是什麼。我想：tool use 很酷，但真的有用嗎？大概沒有吧，試試看好了。

[`4:25`](https://youtu.be/PQU9o_5rHC4?t=265) 你在終端機裡做，只是因為那是最容易把東西跑起來的方式？

[`4:29`](https://youtu.be/PQU9o_5rHC4?t=269) 對，因為我不必做 UI。

[`4:31`](https://youtu.be/PQU9o_5rHC4?t=271) 當時只有我一個人。

[`4:32`](https://youtu.be/PQU9o_5rHC4?t=272) 那時正是 IDE、Cursor、Windsurf 起飛的時候。你有感受到壓力嗎？有很多人建議「嘿，我們該做成外掛，或做成功能完整的 IDE」嗎？

沒有壓力，因為我們根本不知道要建什麼。團隊就在探索模式 —— 我們隱約知道想在寫程式這塊做點什麼，但不清楚是什麼，沒人有足夠信心。那就是我的工作：去搞清楚。

所以我給了模型 bash 工具 —— 那是我給它的第一個工具，純粹因為那字面上就是我們文件裡的範例。我就把範例拿來，它是 Python，我移植成 TypeScript，因為我是那樣寫的。

我不知道模型能用 bash 做什麼，所以我請它讀一個檔案，它就能 cat 那個檔案，那很酷。然後我想：好，你實際上能做什麼？我就問它：「我在聽什麼音樂？」它寫了一段 AppleScript 去操作我的 Mac，查我的音樂播放器在放什麼。

[`5:26`](https://youtu.be/PQU9o_5rHC4?t=326) 那是 Sonnet 3.5。

[`5:28`](https://youtu.be/PQU9o_5rHC4?t=328) 我不覺得模型做得到那個。那是我第一個「fuel the AGI」時刻。

[`5:34`](https://youtu.be/PQU9o_5rHC4?t=334) 我就想：天啊，**模型就是想用工具**，它只想做這件事。

[`5:39`](https://youtu.be/PQU9o_5rHC4?t=339) 這滿迷人的。Claude Code 用這麼優雅簡單的形態運作得這麼好，是相當反直覺的。終端機存在非常久了，而那似乎是個好的設計約束，造就了很多有趣的開發者體驗 —— 用起來不像在工作，身為開發者就只覺得好玩。我不用去想檔案在哪。而這幾乎是意外來的。

[`6:09`](https://youtu.be/PQU9o_5rHC4?t=369) 對，那是個意外。

我記得在終端機版開始在內部起飛後 —— 老實說，做出這東西大概兩天後，我就把第一個原型給團隊 dogfood，因為當你有個點子而且它看起來有用，第一件想做的事就是把它給別人看他們怎麼用。

隔天我進辦公室，坐我對面的另一位工程師 Robert 電腦上就開著 Claude Code 在用它寫程式。我說：「你在幹嘛？這東西還沒準備好，只是個原型。」但它在那個形態下就已經有用了。

我記得我們做發布審查、要對外發布 Claude Code 時 —— 那是 2024 年十一、十二月 —— Dario 問：內部的 DAU 圖是垂直的，你是不是在逼工程師用？為什麼你要強制他們？

[`7:00`](https://youtu.be/PQU9o_5rHC4?t=420) 我說：沒有啊，我只是發了篇貼文，然後他們就互相告訴彼此。老實說那就是意外。我們從 CLI 開始是因為那是最便宜的做法，然後它就在那裡待了一陣子。

[`7:13`](https://youtu.be/PQU9o_5rHC4?t=433) 在 2024 那段期間，工程師怎麼用它？他們已經在用它出貨程式碼了嗎？還是用在別的地方？

[`7:19`](https://youtu.be/PQU9o_5rHC4?t=439) 模型那時還不太會寫程式。我個人用它來自動化 git。我想到現在我大概已經忘了大部分的 git，因為 Claude Code 做這件事做太久了。

自動化 bash 命令是很早期的使用情境，還有操作 Kubernetes 之類的。人們也用它寫程式，有些早期跡象。我想第一個使用情境其實是寫單元測試，因為風險低一點，而模型當時還相當糟。

[`7:46`](https://youtu.be/PQU9o_5rHC4?t=466) 但人們在摸索，在搞懂怎麼用這東西。

[`7:51`](https://youtu.be/PQU9o_5rHC4?t=471) 而我們看到的一件事是：人們開始為自己寫這些 markdown 檔，然後讓模型去讀那個檔案。**CLAUDE.md 就是從這裡來的。**

對我來說產品上最大的單一原則大概就是潛在需求。在最初的 CLI 之後，這個產品的每一部分都是透過潛在需求建起來的。CLAUDE.md 就是一個例子。

還有另一個我覺得有趣的一般原則：你可以為模型而建，也可以在模型周圍建鷹架來稍微提升表現。依領域不同，鷹架大概能提升 10%、20%，然後這個增益基本上會被下一個模型抹平。所以你要嘛建鷹架、拿到一點表現增益、然後再重建一次；要嘛就等下一個模型，然後免費拿到。

CLAUDE.md 和那些鷹架就是這類例子。而我真的認為，這就是我們待在 CLI 的原因：我們覺得沒有任何我們能建的 UI 能在六個月後還相關，因為模型進步太快了。

[`8:50`](https://youtu.be/PQU9o_5rHC4?t=530) 我們剛剛說要比較彼此的 CLAUDE.md，但你說了件很深刻的事：你的其實非常短，這幾乎跟人們預期的相反。為什麼？你的 CLAUDE.md 裡有什麼？

[`9:03`](https://youtu.be/PQU9o_5rHC4?t=543) 我來之前查了一下。我的只有兩行。

第一行是：每當你開一個 PR，就啟用 automerge。這樣只要有人核准，它就被合併。這純粹是為了讓我能一直寫程式，不用跟 code review 來回。

第二行是：每當我開一個 PR，就把它發到我們內部團隊的 stamps 頻道，好讓有人蓋章、讓我解除阻塞。

概念是：其他所有指令都在我們 commit 進 codebase 的那份 CLAUDE.md 裡，而那是我們整個團隊每週貢獻好幾次的東西。我常常看到某人的 PR 犯了完全可以預防的錯，我就直接在那個 PR 上標記 Claude，說「把這個加進 CLAUDE.md」。我一週會這樣做很多次。

[`9:52`](https://youtu.be/PQU9o_5rHC4?t=592) 你們需要「壓縮」CLAUDE.md 嗎？我確實碰過上面出現訊息說「你的 CLAUDE.md 已經好幾千個 token」。碰到那個你們怎麼做？

[`10:03`](https://youtu.be/PQU9o_5rHC4?t=603) 我們的 CLAUDE.md 其實相當短，大概兩千個 token 左右吧。如果你碰到這個，我的建議是：**刪掉你的 CLAUDE.md，重新開始**。

[`10:12`](https://youtu.be/PQU9o_5rHC4?t=612) 我想很多人會過度工程化這件事。而能力隨每個模型在變。所以你想要的是：做最小可能的事，讓模型回到軌道上。

所以如果你刪掉 CLAUDE.md，然後模型開始走偏、做錯事，那時你再一點一點加回去。而你大概會發現：每出一個新模型，你要加的東西就越來越少。

對我來說，老實說我覺得自己是個相當普通的工程師。我不用很多花俏的工具。我不用 Vim，我用 VS Code，因為它比較簡單。

[`10:44`](https://youtu.be/PQU9o_5rHC4?t=644) 等等，真的嗎？我以為因為你是在終端機裡做這東西，你會是那種死忠終端機、只用 Vim、瞧不起 VS Code 的人。

[`10:53`](https://youtu.be/PQU9o_5rHC4?t=653) 團隊上有那種人。例如 Adam Wolff，他就是「你要從我冰冷的手裡才能奪走 Vim」那型。團隊上確實有很多那樣的人。

這是我很早學到的一件事：每位工程師拿開發工具的方式都不同、喜歡用不同工具，沒有一個工具適合所有人。但我想這也是 Claude Code 能這麼好的原因之一 —— 我是從「我自己會用、對我有道理的產品是什麼」去想的。所以要用 Claude Code，你不必懂 Vim、不必懂 tmux、不必知道怎麼 SSH，你不需要知道那些東西。你只要打開這個工具，它會引導你、會幫你做這些事。

[`11:30`](https://youtu.be/PQU9o_5rHC4?t=690) 你們怎麼決定終端機要多詳細？有時你得按 Ctrl+O 去看。團隊內部會為「更長還是更短」吵架嗎？每個使用者大概都有意見，你們怎麼做這類決定？

[`11:47`](https://youtu.be/PQU9o_5rHC4?t=707) 你的意見是什麼？現在太囉嗦嗎？

[`11:50`](https://youtu.be/PQU9o_5rHC4?t=710) 我超愛那個囉嗦度，因為有時它會走偏，而我在看，就能很快讀到「喔不不不，不是那樣」，然後按 Esc 停掉它，當場就擋下一整個 bug 農場。不過那通常是我 plan 模式沒做好的時候。

[`12:07`](https://youtu.be/PQU9o_5rHC4?t=727) 這是我們相當常改的東西。

我記得早期 —— 大概六個月前 —— 我試著在內部把 bash 輸出拿掉、改成摘要，因為我覺得那些超長的 bash 命令我其實不在乎。然後我把它給 Anthropic 員工用了一天，所有人都造反了：我要看我的 bash！因為它其實相當有用。對 git 輸出也許沒用，但如果你在跑 Kubernetes job 之類的，你真的會想看。

最近我們把檔案讀取與檔案搜尋收合了 —— 你會注意到它不再說「讀了 foo.md」，而是說「讀了一個檔案」、「搜尋了一個樣式」。這是六個月前我們不可能出貨的，因為模型還沒準備好 —— 它還是相當常讀錯東西，身為使用者你還是得在旁邊抓、去除錯。但現在我注意到它幾乎每次都在正軌上，而且因為它大量使用工具，摘要起來其實好得多。

我們出貨後 dogfood 了大概一個月，然後 GitHub 上有人不喜歡。有個很大的 issue：不，我要看細節。那是非常棒的回饋。所以我們加了新的 verbose 模式 —— 在 `/config` 裡啟用 verbose 模式，想看所有檔案輸出就能繼續看。然後我在那個 issue 上回覆，人們還是不喜歡，這同樣很棒，因為我最愛的事就是聽人們的回饋、聽他們實際想怎麼用。所以我們就一再迭代，把它做到真的好、做成人們想要的樣子。

我很驚訝我現在有多享受修 bug。你要做的就是有很好的 logging，然後說「嘿，看一下這個特定物件，它在這方面搞砸了」，它就會搜 log、把一切搞清楚。它甚至能進你的 production tunnel 幫你看 production DB。這太誇張了。修 bug 變成「去 Sentry 複製 markdown」，而且很快就會直接變成 MCP 了。

[`14:10`](https://youtu.be/PQU9o_5rHC4?t=850) 現在有各種概念說「不必審查程式碼」。我比較老派，我喜歡那個囉嗦度，我喜歡說「喔你在做這個，但我要你做那個」。但現在有完全不同的學派說：任何時候只要真人得去看程式碼，那就是壞事。

[`14:32`](https://youtu.be/PQU9o_5rHC4?t=872) 我想 Dan Shipper 很常談這個：每當你看到模型犯錯，就試著把它放進 CLAUDE.md、放進 skills 之類的地方，讓它可重複使用。

但我想這裡有個我自己也很掙扎的後設問題：人們說「代理能做這個、能做那個」，但代理實際能做什麼，每出一個模型就會變。所以有時團隊來了新人，他們用 Claude Code 的方式比我會用的更進階。

[`14:58`](https://youtu.be/PQU9o_5rHC4?t=898) 我不斷被這件事驚訝。例如我們有個記憶體洩漏要除錯。（順帶一提 Jared Sumar 一直在進行一場消滅所有記憶體洩漏的聖戰，很驚人。）但在 Jared 進團隊之前，這得我來做。
