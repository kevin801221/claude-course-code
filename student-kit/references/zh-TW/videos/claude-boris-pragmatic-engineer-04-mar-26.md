## 逐字稿

[`0:01`](https://youtu.be/julbw1JuAz0?t=1) 你寫了 O'Reilly 有史以來第一本 TypeScript 書。

[`0:04`](https://youtu.be/julbw1JuAz0?t=4) 對。我在日本一個小鎮發現了那本書的日文版，那是最酷的一刻。然後我才意識到我完全不記得 TypeScript 了。現在我們走到了 Claude Code 在 Anthropic 平均寫掉大約 80% 程式碼的地步。我每天大概寫 10 到 20 個 pull request，而 Opus 4.5 加 Claude Code 寫了其中每一個的 100%，我沒有手動編輯過任何一行。

[`0:22`](https://youtu.be/julbw1JuAz0?t=22) Andrej Karpathy 發文說他從未如此覺得自己身為程式設計師是落後的。

[`0:26`](https://youtu.be/julbw1JuAz0?t=26) 這是我真的很掙扎的一點。模型進步太快，對舊模型有效的點子，對新模型可能無效。我對這個時刻的一個比喻是 1400 年代的印刷術 —— 當時有一群會寫字的抄寫員。

[`0:42`](https://youtu.be/julbw1JuAz0?t=42) 而雇用這些抄寫員的某些國王自己是文盲。

[`0:45`](https://youtu.be/julbw1JuAz0?t=45) 想想抄寫員後來怎麼了：他們不再是抄寫員，但現在出現了「寫作者」與「作者」這個類別。這些人之所以存在，是因為文學的市場……

（主持人開場）當你加入世界頂尖 AI 實驗室之一，而你的第一個 pull request 被打回來 —— 不是因為程式碼不好，而是因為你是手寫的 —— 會發生什麼事？這正是 Boris Cherny 加入 Anthropic 時發生的事。

Boris 是 Claude Code 的創造者與工程主導。加入 Anthropic 之前，他在 Meta 待了七年，負責 Instagram、Facebook、WhatsApp 與 Messenger 的程式碼品質，是公司裡最多產的程式碼作者與審查者之一。

今天這集我們談：Claude Code 怎麼從一個副專案變成成長最快的開發者工具之一，以及 Anthropic 內部關於要不要發布它的辯論；Boris 每天出貨 20、30 個 pull request 且零手寫程式碼的工作流，以及當 AI 寫所有東西時 code review 怎麼運作；為什麼 Boris 相信我們正活在一個如印刷術般有轉變性的時代；以及哪些工程技能現在更重要、哪些不再重要。

如果你想理解最接近 AI coding agent 的人今天實際怎麼打造軟體、以及那對我們其他工程師意味著什麼，這集就是為你準備的。

（贊助商：Statsig、Sonar、WorkOS。）

你是怎麼進入科技、軟體工程與寫程式的？

[`2:14`](https://youtu.be/julbw1JuAz0?t=134) 這要回溯一陣子。我想有兩條平行的路徑交會了。

大概 13 歲時，我開始在 eBay 上賣舊的寶可夢卡。我發現在 eBay 上你其實可以寫 HTML。我看別人的寶可夢卡刊登，發現有些有大字、有顏色、有字型之類的。然後我發現了 blink 標籤。

[`2:41`](https://youtu.be/julbw1JuAz0?t=161) 如果我加上 blink 標籤，我就能把卡賣 99 美分而不是 49 美分。我就這樣學會了 HTML，然後買了本 HTML 書繼續學。

第二件事也是在國中。我們有那種老的 TI-83 繪圖計算機，用在數學課上。我發現如果我把數學考試的答案寫進計算機，就能在考試拿到更好的成績。所以我寫了這些小程式把答案寫進去。後來考試變難了，我就得寫解題器而不是直接寫答案，因為我事先不知道係數之類的會是什麼。然後隔年數學更進階了，我得從 BASIC 降到組合語言，讓程式跑快一點。

[`3:28`](https://youtu.be/julbw1JuAz0?t=208) 哇，所以高中時你就降到組合語言。

[`3:30`](https://youtu.be/julbw1JuAz0?t=210) 大概是國中或高中，八年級或九年級吧。然後我發現班上每個人都開始知道我有解題器，他們有點嫉妒，所以我買了條小的串列傳輸線分給他們。下一次數學考試全班都拿 A。老師說「這是怎麼回事？」最後她想通了，說「好，這次放過你們，別再鬧了」。

但對我來說這非常實用。我在學校念經濟，其實輟學去做新創了，而且我從沒想過寫程式會是個職業。對我來說它一直很實用：寫程式是建造東西、做出有用東西的手段。

第一個新創 —— 我和朋友想弄到大麻，所以我們做了個大麻評論新創。我們做了個網站，打電話給不同的藥局，然後試著拿樣品來幫他們評論。它其實還滿紅的。後來我對這個更有興趣了，因為當時沒人在檢驗這些東西，所以我進入了化學檢驗、化學分析的領域。之後我做了一堆其他新創，然後相當早就加入了 YC，後來我是帕羅奧圖一家 YC 新創的第一號員工。

[`4:54`](https://youtu.be/julbw1JuAz0?t=294) 你怎麼決定一家接一家地做新創？

[`4:57`](https://youtu.be/julbw1JuAz0?t=297) 算是憑感覺吧。你知道新創從來不是線性路徑，你總是在轉向、轉向、再轉向。你得搞清楚市場要什麼、使用者要什麼，而那從來不是你以為的那個。你總是試一個東西，但點子永遠只是個假說，而幾乎總是你得轉向一次、兩次、三次。

在一家叫 Agile Diagnosis 的醫療軟體公司 —— 那是早期的 YC 公司，大概 2011、2012 年 —— 做的是給醫生用的醫療軟體。概念是：有這些臨床決策流程，各醫院差異很大。我們的想法是芝加哥有家醫院對心臟症狀有一套很棒的流程，那如果全美每家醫院都用同一套流程，結果不是會很好嗎？所以我們試著標準化它，做了給醫生用的決策樹軟體。

我寫了一部分軟體，團隊就我們幾個人，很小。那是在瀏覽器裡跑的。我記得那是 Internet Explorer 6 的時代 —— 那是醫院在用的東西。

[`6:06`](https://youtu.be/julbw1JuAz0?t=366) 我寫了一個 SVG 渲染器，因為那是個視覺化決策樹。我們上線了，做了 DAU 圖表，然後 DAU 是平的。我們搞不懂為什麼。當時我們跟幾家醫院做試點，包括 UCSF。我那時騎機車，就騎去 UCSF，跟在醫生旁邊觀察了幾天，看他們實際怎麼用。

我發現醫生其實沒時間坐下來用電腦。你看完一位病人，

[`6:42`](https://youtu.be/julbw1JuAz0?t=402) 到下一位病人之間大概只有 5 分鐘。這 5 分鐘裡你得走過走廊、走到電腦站、打開那台老舊電腦 —— 光開機就三分鐘，再打開 IE6 要 30 秒，再打開我們做的 App、還得登入，你的 5 分鐘就沒了，你根本沒時間用。

所以我們把一切重寫成在 Android 上跑，他們還是不用。然後我們發現：醫生走動時後面跟著一群住院醫師。在那種場合，那是個社交情境 —— 重要的是他們被視為權威，他們不想被看到在滑手機。

於是我們又轉向。那時我們想：也許醫生不是目標使用者，也許該給護理師或 X 光技師用。那個時點我離開了，因為我覺得這離我想做的事已經滿遠的。

對我來說最好玩的就是找到 product-market fit，因為它永遠出人意料。你不能有一個大點子，因為那個點子大概是錯的。你形成假說、追下去、看看什麼是對的。

我覺得你講這個故事的方式很有意思。很多新創成功故事我們只聽到成功的部分、聽到事情怎麼走到那裡。但首先，很多新創都是這樣；其次，讓我印象深刻的是：你是以軟體工程師身分被雇用的，而那還是在「產品工程師」這個詞存在之前。但你就是騎上機車去現場、跟在人旁邊觀察、理解他們怎麼用、為什麼不用、從中得到想法。我覺得這就是當時、甚至今天，成就一位優秀軟體工程師的東西 —— 你不是聚焦在技術上，你聚焦在結果上。

[`8:31`](https://youtu.be/julbw1JuAz0?t=511) 對。不過工程師有很多種，做法也有很多種。就算在我們現在的團隊，我看像 Jared Sumar 這樣的工程師，他有不可思議的技術頭腦，他對系統的理解超過我見過的任何人。你需要這樣的人，需要這種深度。

對我來說，工程一直是件實用的事。我一直是通才，不管我在做設計、工程、使用者研究還是什麼都無所謂。

（贊助商段落：Sonar / SonarQube 與 SonarQube MCP server。）

我的第一份工作大概 16 歲，我只是想買把電吉他。所以我開始接案，想說「好吧那我來做網站」。那時還沒有 Fiverr，有其他接案網站。我架了個網站、開始競標案子，第一筆收入全部拿去買電吉他了。但那非常實用 —— 因為在那種狀況下你得做工程、做會計、做設計、跟客戶談。對我來說一直都是那樣。

做了幾家新創之後，你去了 Facebook（現在的 Meta），待了七年。你能談談在那裡做了什麼、學到什麼嗎？你在七年內升了四次，職涯成長相當驚人。你從那段經驗帶走了什麼？

[`11:39`](https://youtu.be/julbw1JuAz0?t=699) 我從 Facebook 社團開始。Vlad Klesnikov 雇用了我，我想他現在還在 Facebook，大概在別的團隊。很酷的是，我合作的一大群人也是早期的 JavaScript 人。我一直跟這些人交會 —— Vlad 做過 Bolt.js，那個驅動廣告管理員的框架，後來變成 React.js。

我在 Facebook 社團工作，我對它很興奮，因為那個「把人連結到他們的社群」的使命。那是吸引我的東西。當時我是重度 Reddit 使用者，我青少年時就開始用 Reddit，因為我不認識任何其他會寫程式的人。甚至上大學時我也不太認識會寫程式的人。

[`12:37`](https://youtu.be/julbw1JuAz0?t=757) 老實說我一直有點為此難為情，因為我覺得那是很宅的事。那是我會做的事，但我想當個酷小孩，我沒辦法告訴別人我會寫程式 —— 那太宅了。然後某個時點我發現 Reddit 上有個程式社群，我超震驚：還有其他人也喜歡這個東西。這嗜好這麼怪、這麼小眾，而能找到這樣志同道合的人、建立這種連結，實在太令人興奮了。所以我就想做這件事、想以某種方式貢獻。

我在 Facebook 社團做了一陣子，中間有一堆不同專案。最後我成了 Facebook 社團的 tech lead，一路成長，而部門也成長了，工作性質真的變了 —— 從建造變成大量寫文件、協調與委派給別人。

當時文化也在變。早期的 Facebook 文化正在消失，文件進來了、對齊會議進來了，隱私、安全這類基礎工作也多了很多。老實說早期為了成長砍了很多角，但某個時點你就是得還那筆債，而那就是還債的時候。

之後我在 Instagram 待了幾年，那也是個好笑的故事。我太太拿到一個工作邀約，她非常興奮，來跟我說：「嘿，我拿到這個 offer，但我們得搬家，可以嗎？」我說：「可以啊，我在科技業，我們可以遠距工作。工作在哪？」她說：「在 Nagano（長野）。」我說：「那在哪？」那是日本鄉下。

[`14:17`](https://youtu.be/julbw1JuAz0?t=857) 時區也不同。

[`14:19`](https://youtu.be/julbw1JuAz0?t=859) 時區不同，對。

[`14:20`](https://youtu.be/julbw1JuAz0?t=860) 差 12 小時之類的。

[`14:22`](https://youtu.be/julbw1JuAz0?t=862) 差不多。那大概是 2021 年。

[`14:25`](https://youtu.be/julbw1JuAz0?t=865) 然後我試著找一個願意「贊助」我的團隊，因為有些很神祕的 HR 規定，關於你得在哪個時區、得跟哪個團隊同地辦公之類的。當時 Instagram 在東京有個剛起步的小團隊，由 Will Bailey 帶 —— 他也是做 Instagram Stories 的人 —— 他當了我一陣子的 manager，我們決定一起把那個團隊做大。我從長野遠距工作，團隊大部分在東京。

這段期間我開始 hack Instagram，而那個技術堆疊真是瘋狂。Facebook 有全世界最好的 web serving stack —— 從 Hack 語言、HHVM 執行期、作為傳輸層的 GraphQL，到 Relay 這些客戶端函式庫，再加上 React，全部完全最佳化過。世界上沒有其他開發堆疊這麼好。

然後我去了 Instagram，那裡是 Python，型別檢查器不能用、點擊跳到定義不能用，是一個拼湊起來的 Django 加上 Cython 執行期，什麼都不太能用。

所以我加入了日本的 labs 團隊，想法是為 Instagram 找到下一個大東西。我們試了一些，但我很快發現我在那個堆疊上根本沒有效能，因為堆疊太糟了。所以我就跑去做 Dev Infra，因為我們得先修好它。

我們做了幾個專案：一個是從 Python 遷移到 Facebook 的大 monolith，另一個是從 REST 遷移到 GraphQL。這些專案現在還在進行 —— 這種事要上百個工程師做好幾年，codebase 很大、遷移很大。不過現在快多了。

[`16:16`](https://youtu.be/julbw1JuAz0?t=976) 而有了現在這些 AI 工具，遷移其實是相當好的使用情境。

[`16:21`](https://youtu.be/julbw1JuAz0?t=981) 對，那是完美的使用情境。然後我就越鑽越深。等我離開 Instagram 時，我在做 dev infra、主導一堆這類遷移。那也是我跟 Fiona Fun 交會的地方 —— 她現在是 Claude Code 團隊的 manager。我跟她共事過，她是個超棒的領導者，有不可思議的深度與科技界資歷。我就想：沒有比她更適合帶這個團隊的 manager 了。

我也開始做程式碼品質，Instagram 的工作範圍慢慢擴大。等我離開時，我主導整個 Meta 的程式碼品質 —— 負責 Instagram、Facebook、Messenger、WhatsApp、Reality Labs 所有 codebase 的品質。

在 Meta 這個計畫叫 Better Engineering。大概 2016 或 2018 年，Zuck 下令公司每位工程師必須把 20% 時間用在修技術債上。

[`17:17`](https://youtu.be/julbw1JuAz0?t=1037) 有意思。

[`17:19`](https://youtu.be/julbw1JuAz0?t=1039) 我們叫它 better engineering。

[`17:22`](https://youtu.be/julbw1JuAz0?t=1042) 其中有些是由下而上的 —— 團隊最清楚自己得修哪些技術債；有些是由上而下的 —— 你得做非常大的遷移、遷到新語言特性、新框架之類的。在 Facebook 的規模下，每年有數萬個這類遷移。

我開始主導這一切，很快就發現它需要多一點秩序：沒有目標、沒人知道結果是什麼、沒有追蹤。所以我們做了一堆東西。一個是用集中化的方式為不同的程式碼品質工作排優先序。第二是搞清楚程式碼品質對工程生產力的影響 —— 結果影響相當顯著。

[`18:04`](https://youtu.be/julbw1JuAz0?t=1084) 你怎麼衡量？你發現了什麼？

[`18:06`](https://youtu.be/julbw1JuAz0?t=1086) 有一堆東西，我想有些已經發表了，不確定是不是全部。方法上基本是做因果分析與因果推論 —— 試著找出讓工程師更有生產力的因素有哪些。有些是程式碼品質，有些不是。例如 Meta 後來從在家工作改回到辦公室上班，那部分就是受此驅動，因為我們發現了一些我們認為是因果的相當強的相關性。

[`18:32`](https://youtu.be/julbw1JuAz0?t=1112) 而品質確實對生產力貢獻了兩位數的百分比。即使在最大的規模下也是如此。

聽到這個滿令人安慰的，因為我想很少有地方真的去衡量這件事。但我們感受得到 —— 當你有乾淨、模組化的 codebase，就比較容易上手。而且推論起來，對 LLM 來說應該也更容易處理，我猜答案是肯定的，只是資料很少，但那是我的感覺。

對，我想很多大公司都發表過。Facebook 發表過，微軟發表很多，Google 也是。但完全正確：如果每次你要做一個功能，都得想「我該用框架 X、Y 還是 Z」—— 因為 codebase 處在部分遷移狀態，這些東西在程式碼各處都有 —— 身為工程師你會很痛苦，身為新人你會很痛苦，而身為模型，它可能就挑錯那個，然後使用者得來糾正你。

[`1:20:00`](https://youtu.be/julbw1JuAz0?t=4800) 對，「你該學到教訓啊」。那有點像守門，但以前某種程度上是有效的 —— 架構上有人說「我們為什麼不做微服務」，有人說「我們試過，不行」。如果你一年、兩年、三年前試過，那是有道理的，因為沒什麼變。

沒錯。而微服務好笑的是它大概每十年就流行／退流行一次。但現在我想是史上第一次，每隔幾個月重試同一個點子其實不是瘋狂的事，因為模型進步了，它就能動了。

我在團隊的工程師身上也看到這個。比較新進團隊的人、比較新進工程領域的人，有時做事方式比我更好。我就得看著他們、學習、調整我的期待。

舉個例子：我們發布功能時，我有時會截圖自己在用它、發到 X 或 Threads 上談它。但最近我們的 DevRel Tar —— 他其實寫很多程式，他很厲害 —— 他開始把這件事自動化了。他讓 Claude Code 為自己的發布產生影片。他就這樣做了。這是我會覺得「也許可行」但不會去試的事，因為我不覺得模型準備好了。但他就去做了，而且就這樣成功了。

[`1:21:18`](https://youtu.be/julbw1JuAz0?t=4878) 有件事讓我覺得有點怪，我想很多開發者能共鳴：從 Opus 4.5 開始（GPT-5.2 也給我類似感覺），模型真的很會寫程式。而我意識到：當我想把事情做完時，我大概不會再手寫程式碼了 —— 如果我想要享受寫作的樂趣我仍然可以，但……

我反思的一點是：要把寫程式練好花了太多力氣。我記得我從亂弄開始、進大學、學 C 和 C++，真的非常難。而在我最初幾份工作中我才開始變好、變得更會除錯。有一個時期我的認同很大一部分綁在「寫程式很強」上面。那是我們以前找到工作、找到高薪工作的方式。

我當工程經理時，我們在 Uber 設計面試流程，跟經理們討論該篩什麼訊號，我們說：開發者大部分時間在做什麼？大概 50% 時間在寫程式。所以我們把大約 50% 的訊號放在寫程式上。

所以有很多東西綁在寫程式上，因為它就是難。我想我們都知道那需要毅力、需要某種程度的智力。

而現在有一種失落感：一方面模型能做到很棒；但另一方面感覺有某個東西被很快拿走了，而我個人沒想到會這麼快發生。我想很多人也有這種感覺 —— 有些人比較容易放下，但確實有某種哀悼感。

你怎麼想這件事？你也是個例子 —— 你在 Facebook 內外都寫了超多程式碼。我知道對你而言那只是完成事情的工具，但沒多少人能做到你做到的事。而現在模型也能做得跟你一樣好，甚至更好。

[`1:23:16`](https://youtu.be/julbw1JuAz0?t=4996) 這就是挑戰。我想那原本是我們身為軟體工程師在做的事，現在正變成每個人都能做的事。

有一個時刻 —— 我開始寫程式時那非常實用，是把事情做完的方式。然後某個時點我愛上了寫程式這門藝術、愛上語言、愛上工具本身，掉進了那個兔子洞。我寫了一本關於程式語言的書。

[`1:23:44`](https://youtu.be/julbw1JuAz0?t=5024) TypeScript —— 你寫了 O'Reilly 有史以來第一本 TypeScript 書。

[`1:23:50`](https://youtu.be/julbw1JuAz0?t=5030) 對。好笑的是，我在日本那個小鎮有個很棒的時刻：我去書店，發現那本書的日文譯本。

[`1:24:00`](https://youtu.be/julbw1JuAz0?t=5040) 在那個小鎮裡，那是最酷的一刻。然後我才發現我完全不記得 TypeScript 了，因為那時我已經只寫 Python 寫了好幾年。

某個時點我辦了當時世界最大的 TypeScript 聚會，在舊金山，我見到很多我的偶像 —— 寫《General Theory of Reactivity》的 Chris Cowell、做 Node 的 Ryan Dahl。那是我第一次真正深入這個社群、深入語言本身與工具本身。

TypeScript 的型別系統有一種美，因為 Anders Hejlsberg 真的很厲害 —— 像條件型別、任何東西都能是字面型別，這些非常深的想法，連最硬派的函數式語言都沒有。即使 Haskell 也沒走這麼遠，而 Anders 把它推得遠得多。Joe Pamer 和一群人探索了很多這些想法。我想對他們來說那也非常實用：他們有大型未標註型別的 JavaScript codebase，要怎麼漸進遷移到有型別的世界？你得想出這些非常美的想法才能做到。

Scala 是我掉進的另一個兔子洞，在函數式編程那個世界。到現在我寫程式、或模型寫程式時，我永遠先用型別思考 —— 重要的是型別簽章是什麼，那比程式碼本身更重要，把它弄對最重要。

所以它確實有美、確實有藝術。但終究它是實用的東西，終究它是我們用來建造東西的工具，是手段，不是目的本身。

我對我們所處這個時刻的一個比喻是 1400 年代的印刷術。

[`1:25:57`](https://youtu.be/julbw1JuAz0?t=5157) 因為那個時刻其實相當類似 —— 有一群會寫字的抄寫員。

[`1:26:03`](https://youtu.be/julbw1JuAz0?t=5163) 而據我想像（我們當然沒活在那時），那是門需要學的藝術。你得學習、得取得設備，大概還需要贊助或被選中去練習，因為你得一次又一次產出同樣的東西，而很少人做得到。我猜那要嘛高聲望、要嘛高報酬。

[`1:26:24`](https://youtu.be/julbw1JuAz0?t=5184) 然後印刷術來了。

[`1:26:27`](https://youtu.be/julbw1JuAz0?t=5187) 對。至少在歐洲，你得被某個領主或國王雇用，然後經過多年訓練。有這麼一個會寫字的抄寫員階級，被這樣的人雇用，而國王或王后自己往往不識字。那是非常小眾的技能，當時歐洲識字率不到 1%。

然後印刷術出現。接下來大概 30 到 50 年，印刷品成本降了約 100 倍；接下來 50 到 100 年，印刷品數量上升了約 10,000 倍。這是第一波效應。

識字率追上來則花了一段時間。全球識字率上升到大約 70%，但那又花了 200、300 年，因為學讀寫真的很難、很費力，需要教育系統，需要有紙和墨水的基礎設施，也需要你不必在農場工作而有閒暇。所以實際上得等到工業化早期才真的達成。

但「原本鎖在象牙塔裡的東西變得人人可及」這個效應 —— 我們周遭的一切沒有它都不會存在。如果我們不識字、如果做這支麥克風的人不識字，要有現代經濟會非常困難，這些東西都不會存在。

而我想，如果當時要人們預測印刷術出現後會怎樣，沒人會預測到麥克風會成為一個東西。所以我覺得這是我們當下這個時刻最好的類比。

[`1:28:13`](https://youtu.be/julbw1JuAz0?t=5293) 你說「雇用抄寫員的某些國王自己是文盲」很有意思，因為老實說，我們也有知道自己想建什麼的企業主，他們雇用軟體工程師，因為他們自己不會寫程式。

我們喜歡嘲笑那些跑來團隊、甚至帶著手繪原型或白板說「這應該很簡單」的 CEO —— 當然他們不懂這有多難。這裡有點類比：有一個人知道自己要什麼，但到現在為止他需要雇用一位能把它建出來的專家，而點子與人之間永遠有那個斷層。就像印刷術一樣 —— 如果國王真的能自己讀寫自己的信，他就不需要那個中間人，事情會更有效率。當然對抄寫員來說那不一定是好消息，但聰明的抄寫員也能轉型 —— 總得有人寫書、有人operating 印刷機。

沒錯。而想想抄寫員後來怎麼了：他們不再是抄寫員，但現在出現了「寫作者」與「作者」這個類別。這些人之所以存在，是因為文學的市場大幅擴張了。

[`1:29:30`](https://youtu.be/julbw1JuAz0?t=5370) 而且當時一位抄寫員的作品只有少數人讀到；有了印刷術和作者，作者多得多，有些沒什麼人讀，但有些的觸及遠超過他們能想像。因為這樣出現了新的職業。

[`1:29:47`](https://youtu.be/julbw1JuAz0?t=5387) 對我來說最令人興奮的是：今天根本不可能說出這個轉變之後會發生什麼。我們所知的經濟沒有它就不會存在。那麼接下來是什麼？有什麼是我們今天甚至無法預測、但會因為「任何人都能做這件事」而出現的東西？

[`1:30:13`](https://youtu.be/julbw1JuAz0?t=5413) 我們無法預測，但我想我們可以看什麼現在有效。看看你周遭的環境 —— 不管是 Anthropic 裡的軟體工程師、建造者、member of technical staff，不管我們怎麼稱呼他們 —— 誰對你來說是傑出的？他們在做什麼？他們建立了什麼技能？他們怎麼改變了工作方式？

很難點名個人，因為老實說這些是我職涯中共事過最強的人。有各種不同的原型：有些人是很棒的原型製作者，把東西從 0 推到 0.5 —— 搞清楚有哪些酷點子、技術的邊界在哪。有些人極擅長找到 product-market fit，也就是 0.5 到 1、或 0 到 1。還有些人橫跨不同學科 —— 我看到越來越多這樣的人：橫跨產品工程與基礎設施工程，或橫跨產品與設計、設計與工程。我看到多很多這樣的混合型人才。

[`1:31:15`](https://youtu.be/julbw1JuAz0?t=5475) 有什麼信念從去年到今年改變了？某個你曾相信或堅信、後來修正或完全丟棄的東西？

老實說，我原本不確定安全是多大的問題。我加入 Anthropic 是因為我讀很多科幻，我知道這件事壞掉時能壞到什麼程度。但那不是我當時確定的事。

而從內部看、看到過去一年出現的新風險，讓我擔心得多很多。所以對我來說那原本是件重要的事，現在它是最重要的事：我們要怎麼確保這件事走好。

[`1:31:59`](https://youtu.be/julbw1JuAz0?t=5519) 可以說在所有 AI 這些事開始之前，你就是個很好的軟體工程師，而且是非常多產的工程師。在「成為軟體工程師」這件事上，有哪些技能現在仍然一樣有價值、甚至更有價值？又有哪些大概沒那麼重要、最好放下？

最好放下的，大概是對程式碼風格與語言之類的強烈意見。我等不及要跳過那些沒完沒了的語言辯論、框架辯論，因為模型可以用任何語言和框架，如果你不喜歡它還能幫你重寫。所以那已經不重要了。

今天仍然很重要的，是**有方法、以假說驅動**。這在產品設計上重要 —— 在這個一切被顛覆、我們得搞清楚接下來要建什麼的世界裡，每個人都在想這件事；在日常工程上也重要，例如除錯，你就是得非常有方法。模型能做這件事、也能幫很多忙，但我想我們仍處在過渡點，你還是需要具備這個技能。我不知道六個月後你是否還需要它。

我認為更有價值的其他技能是：**好奇**、以及**願意做自己泳道之外的事**。如果你做工程但真的懂商業面，你就能做出非常棒的產品。我想下一個十億美元產品 —— 在 Claude Code 之後，不管下一個成為兆元新創的是什麼 —— 可能就是一個有酷點子、而大腦能橫跨工程、產品與商業（或設計、財務與別的東西）的人。人們會變得越來越多學科，而這會越來越被獎勵。所以某種程度上，我覺得今年會是通才之年。

另一個其實正在被獎勵的技能是：**注意力持續時間短**。

[`1:34:11`](https://youtu.be/julbw1JuAz0?t=5651) 青少年在用 TikTok 之類的東西，我想某種程度上那對社會有點危險，因為你會想要人們能深度思考、能沉思想法，而不是很快跳到下一個想法。但某種程度上我覺得今年會是獎勵這個的一年 —— 像是 ADHD 之年。因為對我來說工作已經變成在多個 Claude 之間跳來跳去、變成管理 Claude。所以它不太是關於深度工作，而是關於我多擅長切換脈絡、多快在多個不同脈絡之間跳躍。

[`1:34:52`](https://youtu.be/julbw1JuAz0?t=5692) 我想補充一點：也許可以加上「適應力」。因為你說 ADHD、能跳來跳去，但你早先也非常擅長深度專注於一件事。讓我印象深刻的是（也許其他人也是）：你非常願意調整自己的工作風格，看什麼在這個階段有效，特別是當事情在變的時候。我想唯一能確定的是：下一個模型出來時，它又會改變。而你需要好奇、願意調整工作方式，對吧？

[`1:35:25`](https://youtu.be/julbw1JuAz0?t=5725) 最後，你會推薦什麼書？

我掉進了劉慈欣的兔子洞 —— 他是寫《三體》的人，但他還有很多很棒的書。我真的很愛他的短篇，他有好幾本短篇集，我是大粉絲。

對科幻新手、又想要稍微硬一點的科幻，我很推薦 Charles Stross 的《Accelerando》。這本我完全推薦，它本質上是未來 50 年的產品路線圖。它從起飛開始、AI 奇點開始，最後是一群環繞木星的龍蝦意識，太驚人了。我覺得它真正捕捉到的是那個節奏 —— 越來越快、越來越快的感覺，非常符合現在的感受。

技術面我強烈推薦《Functional Programming in Scala》。即使語言選擇已經沒那麼重要，我認為函數式編程有一種藝術，能教你更好地寫程式、教你用型別思考。如果你讀這本書，很重要的是也要做習題。我整本做過，大概全部做了三遍，真的很棒。它會把函數式型別的概念敲進你腦袋，讓你停不下來思考它。

[`1:36:45`](https://youtu.be/julbw1JuAz0?t=5805) Boris，非常感謝，這太棒了。

[`1:36:48`](https://youtu.be/julbw1JuAz0?t=5808) 謝謝。

（主持人結語）這是場非常有意思的對話，而我一直回想的是 Boris 的印刷術類比：中世紀抄寫員是一小群能寫字的菁英，被往往自己不識字的國王雇用；而我們軟體工程師今天可能處在類似的位置。我們就是抄寫員。我們花了多年精通這門工藝。而現在印刷術來了。

但 Boris 告訴我：抄寫員並沒有消失，他們變成了寫作者與作者，而整個書面作品的市場擴張到超出任何人能預測的程度。我覺得這很有希望，也感謝 Boris 沒有粉飾太平。
