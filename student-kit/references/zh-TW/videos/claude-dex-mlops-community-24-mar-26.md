## 逐字稿

[`0:04`](https://youtu.be/YwZR6tc7qYg?t=4) 好，在我請 Dex 上台之前，我得說我認識了 James。James，你能快速站起來一下嗎？James 今天早上告訴我他今晚要吃晚餐，歡迎大家參加。所以如果你想去，快掃那個 QR code，去跟 James 聚一聚。太棒了，這正是我們想要的氛圍。

[`0:33`](https://youtu.be/YwZR6tc7qYg?t=33) 好，我請 Dex 上來。剛剛有人說我們該辦個鬍子比賽，我想那不會發生，但我要說他給了我們 200 張投影片要講。

[`0:48`](https://youtu.be/YwZR6tc7qYg?t=48) 喔喔，158 張。158。我們會盯著他的時間。好，大家開始計時。

[`0:57`](https://youtu.be/YwZR6tc7qYg?t=57) 來吧。大家好，我是 Dex。這場演講的標題非常長，我不會念它，因為我們在趕時間。我談 coding agent 已經談了好一陣子，大概從八月開始，十一月做過一場長演講。我們一直在談一套方法論叫 research-plan-implement（研究－計畫－實作，RPI）。在 Hacker News 上有很多讚。大概有一萬人去我們的開源專案抓了我們的 prompt，在內部使用 —— 從小新創到大企業都有。

[`1:29`](https://youtu.be/YwZR6tc7qYg?t=89) 這一切都從這個人開始。有人看過這場演講嗎？有。好，Eigor 說：我們用了大量 token、花了大量錢去換 AI 開發生產力。但他發現這其實往往導致大量返工。你出貨多了 50%，但其中一半只是在清理上週的 slop（劣質產出）。他們還發現 —— 這是去年的數字，所以沒算進 Opus 4.5，我會稍微往上調整 —— 它對低複雜度的全新專案任務很棒，對高複雜度的既有專案任務則不太行。

[`2:02`](https://youtu.be/YwZR6tc7qYg?t=122) 我可以講一場關於 RPI 有多好的演講，但那會很無聊，而且已經有其他演講了，沒看過的話去看，能補更多脈絡。今天我要告訴你的是：我們對 RPI 的所有誤解。我們以為我們把 AI 這件事搞懂了。我夠謙虛，願意承認我錯了。

[`2:22`](https://youtu.be/YwZR6tc7qYg?t=142) 我們錯了幾件事。其中一件如果你今天上過 Twitter 會覺得很相關：我不認為「不讀程式碼」是可以的。我也不認為你該讀很長的計畫檔。這兩件事是相關的。還有不行 —— 如果你在寫使用者會用的 production 程式碼、而且它壞掉你會在凌晨三點被 call 起來，那就不能有 slop。現在是 2026 年，不要再有 slop 了。

[`2:46`](https://youtu.be/YwZR6tc7qYg?t=166) 我們都在這趟旅程上，我們都在摸索，我們一直都在犯錯。我們也做對了幾件事：沒有魔法 prompt；不要外包思考 —— 你這位工程師是這個流程中重要的一環；還有尋找槓桿 —— 現在有大量程式碼被寫出來，要找方法確保它是對的，而不必全部讀過一遍再事後重新導正。

[`3:05`](https://youtu.be/YwZR6tc7qYg?t=185) 很多人應該聽過 research-plan-implement。有人實際跑過這個 Claude 命令嗎？`research codebase`？好，很好。如果你是像這樣跑的，請繼續舉手：「告訴我這套系統怎麼運作。」有人像這樣跑嗎：「嘿，我想做這個東西，去做研究。」好。或者是去抓一張票之類的。那 `create plan` 這個 prompt 呢？好，有幾隻手。

[`3:28`](https://youtu.be/YwZR6tc7qYg?t=208) 你們有多少人是這樣跑的：「嘿，我們要做這個東西。」有。那有人像這樣跑嗎：「在寫計畫之前，先從你的未決問題與大綱開始跟我來回討論。」好，有些人發現了這組魔法咒語，但很多人沒有。我們等下會談為什麼那是個問題。

[`3:44`](https://youtu.be/YwZR6tc7qYg?t=224) 從十月以來，我們大概跟數千位工程師合作過，從小新創到財星 500 大。我們一再發現：我們把這些工具給一位專家，他會得到很棒的結果，他會坐著跟 Claude 聊一週 70 小時，然後開始瘋狂出貨。然後他把工具給他的團隊，結果就沒那麼好了。

[`4:03`](https://youtu.be/YwZR6tc7qYg?t=243) 大家沒拿到好結果。所以我們跟使用者一起蹲壕溝，去找出哪裡出錯。第一件出錯的事是：大家沒有得到好的研究。

我們十一月談過這個。這是我唯一重用的投影片之一。你會挑 codebase 的一個區域，說「我們要在這裡做個東西」，然後啟動一個 coding agent session，派這些子代理穿過 codebase 做深度垂直切片，只為了取得脈絡 —— 關於「我們即將要做的東西」的壓縮脈絡。

[`4:32`](https://youtu.be/YwZR6tc7qYg?t=272) 我們說：保持客觀、抑制意見、不要放任何實作細節進去。你只是想壓縮「真相」—— 關於今天程式碼怎麼運作的事實是什麼。

一位熟練的工程師很擅長這件事：好，這是我的票，讓我寫一些問題，逼模型去碰到所有重要的程式碼部分。如果任務是「新增一個跨租戶的 reticulate splines 端點」，我們會說：好，告訴我端點怎麼運作、追蹤所有碰到 splines 的邏輯流程、去找出做 reticulation 的 worker。

[`5:03`](https://youtu.be/YwZR6tc7qYg?t=303) 如果這是你的票，很多人會這樣跑：「嘿，研究 codebase，這是我要做的東西。」問題是：好的研究全部都是事實。但如果你告訴模型你要做什麼，你拿到的就是意見。至於為什麼模型不該有意見，我們等下會談。這回到 Netflix 的 Jake 提出的那句話：不要外包思考。

[`5:22`](https://youtu.be/YwZR6tc7qYg?t=322) 另一件沒運作的事是：大家沒拿到很好的計畫。基本上這個規劃 prompt 裡內建了一些步驟，它是個單一巨大的、有 85 條以上指令的龐然大物。裡面有這些步驟：好，向使用者呈現設計選項、在真正寫計畫前先取得對結構的回饋。

[`5:43`](https://youtu.be/YwZR6tc7qYg?t=343) 一次好的規劃 session 大概長這樣：你有你的 Claude 系統工具與 prompt，然後你說「嘿，create plan」，它載入 skill、看你的票、載入你的研究文件、啟動一批子代理去確認一些關於 codebase 的事實 —— 有些可能不在研究裡。順帶一提這全都在同一個脈絡視窗裡。我通常用這些欄位表示不同脈絡視窗，但今天這全都是同一個 session，只是投影片是橫的，我只好把它們並排放。

[`6:11`](https://youtu.be/YwZR6tc7qYg?t=371) 然後代理會來問問題。好，這是問題一的選項，使用者選一個；再選一個。最後它會說：好，這是我們要做的順序，你覺得如何？使用者可以說：我們得在前面加一個測試步驟，而且我想把第三階段跟第四階段對調。助理給出新的階段大綱，使用者核准，然後我們才寫計畫檔。

[`6:33`](https://youtu.be/YwZR6tc7qYg?t=393) 這是一個跟使用者對齊「要建什麼」的複雜流程。但對大約 50% 的人（也許更多）來說，如果你沒有用「跟我來回討論」來提示它，或者 Opus 那個小時剛好在耍笨，它就會直接拿了東西立刻把計畫寫出來。於是你拿到的是：好，我寫好計畫了，沒問我任何問題，替我做了所有決定。糟糕。

[`6:58`](https://youtu.be/YwZR6tc7qYg?t=418) 所以我們把工具給大家，有些人拿到好結果，有些人沒有。我們深入挖掘，想知道差別在哪。然後真的有人對我說：「欸，你得講出那組魔法咒語。」我發現自己在滿是企業工程師的工作坊裡說：「各位各位，這是軟體，但別忘了要講魔法咒語。」老實說，那很尷尬。

[`7:16`](https://youtu.be/YwZR6tc7qYg?t=436) 但如果你說了這句「在寫計畫之前，先從你的未決問題與大綱開始跟我來回討論」，代理就會問你問題。這不是使用者的錯。如果你做了一個需要花好幾小時訓練與反覆練習才能有好結果的工具，那就去修好那個工具。我等下會講我們怎麼做的。

[`7:35`](https://youtu.be/YwZR6tc7qYg?t=455) 至於為什麼這些步驟會被跳過，今天我要給你的一個重要結論是：**你有「指令預算」**。我的共同創辦人 Kyle 在這附近，他十二月（嚴格說是十一月）寫了一篇很好的部落格文章，引用了一篇 arXiv 論文 —— 同樣是去年的，所以現在數字應該高一點 —— 前沿 LLM 大概只能以良好一致性遵循 150 到 200 條指令。超過那個數量，它就是半心半意地注意全部，你等於在擲骰子。

[`8:04`](https://youtu.be/YwZR6tc7qYg?t=484) 所以如果你有一個 85 條指令的 prompt，再加上你的 CLAUDE.md、system prompt、工具、MCP，那你不太可能得到對工作流的完整遵循。我等下會講我們怎麼修的。

[`8:16`](https://youtu.be/YwZR6tc7qYg?t=496) 另一件對大家真的沒用的事是：我們提倡要讀產出的計畫。十一月我在台上告訴大家「你必須讀計畫，否則它不會成功」。有些人甚至會把計畫開成 PR 一起做 code review。但一份一千行的計畫，產出的程式碼差不多也是一千行上下（誤差 10% 左右）。而且計畫會有意外。

[`8:38`](https://youtu.be/YwZR6tc7qYg?t=518) 所以你去審查計畫，然後去寫程式碼，結果不一樣。你等於是在叫同事「好，花一小時讀這個，告訴我哪裡不對」，然後你去實作，結果不一樣，他們又得再讀一次程式碼看有哪些意外、哪裡變了。這不是槓桿。槓桿是做更少的工、得到更多的產出。

[`9:01`](https://youtu.be/YwZR6tc7qYg?t=541) 所以新的建議是：**不要讀計畫，請讀程式碼。** 既然工作量一樣，那就去別處找槓桿。我等下會講我們找到的更好槓桿。

[`9:10`](https://youtu.be/YwZR6tc7qYg?t=550) 你可能會說：「嘿 Dex，你八月說不要讀程式碼，你說計畫就夠了，直接出貨讓 Claude 去做。」我錯了。我夠謙虛，願意承認我錯了。這其實現在是個很大的爭論。請讀程式碼。我們試過六個月不讀程式碼，結局不好，我們得把那套系統很大一部分拆掉重做。

[`9:32`](https://youtu.be/YwZR6tc7qYg?t=572) 你可能會說：「嘿 Dex，但別人就不讀程式碼啊。」Beads，30 萬行還在增加，據說沒人讀過那些程式碼。OpenClaw 的 Pete 說：「我知道結構、知道各部分怎麼拼起來，但我不會讀每個 PR 的每一行。」這些是開源專案，它們不收錢。

[`9:58`](https://youtu.be/YwZR6tc7qYg?t=598) 它們是非常酷的專案，我對維護者的成就深感敬佩，而且風險仍然很高 —— 如果你把 OpenClaw 弄壞，很多人會不爽。但那跟你在受監管產業出貨 production SaaS 程式碼不一樣。所以如果有人依賴你的程式碼，拜託我求你，請讀它。我們有一份專業要守護。2026 年應該是「不再有 slop」的一年。

[`10:25`](https://youtu.be/YwZR6tc7qYg?t=625) 現在字面上每個人都在談 slop 與 craft（工藝）的差別。這也是為什麼我對 agent swarm、對整個「gas town」那套有點冷感 —— 因為你仍然必須能確保品質，而如果你六個月後要把它全部丟掉，快 10 倍一點意義都沒有。

[`10:40`](https://youtu.be/YwZR6tc7qYg?t=640) 所以目標設在 2 到 3 倍。怎麼衡量、怎麼達到並維持接近人類水準的品質，那其實是另一場演講。但關於目標、關於你想達到那裡該思考什麼：你應該要有高槓桿的規劃、不要外包思考、讀並擁有你的程式碼，而且理想上我們要避免魔法咒語。

[`11:02`](https://youtu.be/YwZR6tc7qYg?t=662) 所以：我們有了更好的研究、更好的計畫、更好的槓桿。我會分別談每一項 —— 整體上我們做了什麼、具體怎麼做，以及當你在圍繞 coding agent 建構工作流與系統時可以用的一般概念。

[`11:15`](https://youtu.be/YwZR6tc7qYg?t=675) 我們談過一位熟練工程師能把「票 → 問題 → 研究」拆解開來，而研究會非常客觀。基本上我們就是**把票從做研究的那個脈絡視窗裡藏起來**，而且是用確定性的方式做。所以你用一個脈絡視窗產生問題，再用一個對「我們要做什麼」一無所知的全新脈絡視窗去做研究文件。

[`11:38`](https://youtu.be/YwZR6tc7qYg?t=698) 如果你熟悉 query planning 的概念，這相當直觀。概念類似，只是對象是 LLM 讀 codebase。

[`11:48`](https://youtu.be/YwZR6tc7qYg?t=708) 我 hack 代理有一陣子了。在做 coding agent 之前，我寫過一篇叫《12 factor agents》的文章，據說那是第一次有人大量談「脈絡工程」。脈絡工程有兩種讀法，大多數人跳進的是第一種。有人在做 RAG pipeline 嗎？有建過 RAG pipeline 的舉手？好，有些人今天不太想舉手。

[`12:10`](https://youtu.be/YwZR6tc7qYg?t=730) 那種讀法是「放更多資訊進去」。你放太多資訊，模型就理不出頭緒。我其實覺得脈絡工程更有趣的讀法是：**更好的指令、更簡單的任務、更小的脈絡視窗**。

[`12:22`](https://youtu.be/YwZR6tc7qYg?t=742) 當然現在大家都認識 Jeff 了，我不用再介紹他。我們談過脈絡視窗這件事，概念是「笨蛋區間」：你大概有 16.8 萬 token 可用（總共 20 萬，但有些保留給輸出）。平均大約在 40% 左右 —— 依你在做什麼、脈絡中有多少是使用者訊息而非檔案等等而異 —— 你就會碰到結果開始劣化的那個點。

[`12:48`](https://youtu.be/YwZR6tc7qYg?t=768) 當然有時你在 60% 仍然能拿到「對你來說夠好」的結果，但你用掉越少脈絡視窗，結果就越好。我們在 Databricks 的朋友剛好在談：你裝了太多 MCP，整個脈絡視窗塞滿了「怎麼用一堆你根本不在乎的工具」的指令，然後等你要寫程式時，模型已經不太擅長遵循你的指令了。所以你不只給模型太多資訊，大概也給了它太多指令。

[`13:12`](https://youtu.be/YwZR6tc7qYg?t=792) 所以我們在做的事情背後的想法很有道理：**用 prompt 做控制流**。這是個客服的例子：如果是客訴，做這個；如果是產品回饋，做那個；如果是帳務問題，做另一個。

[`13:27`](https://youtu.be/YwZR6tc7qYg?t=807) 你可以改成：不要用 prompt 做控制流，而是先對輸入做分類，再把它餵給一系列更小、更聚焦的 prompt，那裡指令少得多、可選的動作也少得多。我相信我們很多人已經做過這類事來改善 pipeline 的表現。

[`13:43`](https://youtu.be/YwZR6tc7qYg?t=823) 所以原本這是一個有 85 條指令的巨型 prompt。如果你做對了，你會走過所有這些不同步驟、所有這些階段。但只要任何一條指令沒被遵循，你就會跳過那些讓它真正高槓桿的環節。

[`13:54`](https://youtu.be/YwZR6tc7qYg?t=834) 所以我們把它拆成好幾個 prompt。以前是 research、plan、implement，現在是 questions、research、design、structure、plan、work、implement、PR。今天其實沒時間談 implement 那一側，但我們把規劃拆成「設計討論」、「大綱」與「計畫」。以前是 85 條指令，現在每個都少於 40 條，這很令人興奮。我覺得其中有些甚至還能更小，我們還在迭代。

[`14:18`](https://youtu.be/YwZR6tc7qYg?t=858) 教訓是：**如果你能用控制流做控制流，就不要用 prompt 做控制流。** if 判斷式非常非常強大，而 LLM 非常擅長分類。這不只對 coding agent 成立，對你在建的任何 AI/LLM 系統都成立。

[`14:31`](https://youtu.be/YwZR6tc7qYg?t=871) 很好笑的是，我們寫完這些東西、站上台說「全脂代理行不通、不要只是在迴圈裡呼叫工具、要做脈絡工程、要建工作流與圖與微代理」。我們告訴大家不要那樣做。然後八月我們回頭說「好吧，但這個 Claude Code 滿不錯的」，接著我們就寫了一個巨大的 monolithic prompt。所以我們覺得是時候喝自己賣的那杯飲料了：**管好你的指令預算**。

[`14:56`](https://youtu.be/YwZR6tc7qYg?t=896) 我們怎麼得到更好的槓桿？我們把東西拆開以改善指令遵循，對吧，拆成三個不同階段。但我們也得到了更多槓桿。我來講為什麼。因為即使計畫是一千行、程式碼是一千行，你的「設計討論」可能只有 200 行。而且在那個時刻你有很多重新導正的機會。

[`15:12`](https://youtu.be/YwZR6tc7qYg?t=912) 它長這樣：我們要去哪裡？最終解法長什麼樣？它包含目前狀態、期望的最終狀態、要遵循的模式。你們有多少人曾經派出一個 coding agent，結果它在你的 codebase 裡找到錯誤的做法、照著壞模式做？有吧。

[`15:29`](https://youtu.be/YwZR6tc7qYg?t=929) 這就是你的機會：去讀它找到、而且它認為相關的所有模式，然後說「不，我們不是那樣做原子 SQL 更新的。那是某個已經離職的工程師寫的，很瘋狂，大家都討厭它。去找我們在那邊的做法」。

[`15:40`](https://youtu.be/YwZR6tc7qYg?t=940) 它會追蹤我們已經做出的設計決定，也會提出未決問題。這有點像是把 Claude Code 的 plan 模式與 AskUserQuestion 工具，全部傾倒進一份你可以互動、可塑、靈活的文件裡。

[`15:54`](https://youtu.be/YwZR6tc7qYg?t=954) Matt Pocock 有個想法，他叫它「設計概念（design concept）」—— 就是那個鎖在脈絡視窗裡、代表你與代理之間「要建什麼、怎麼建」的共同理解的東西。我們把它放進一份 200 行的 markdown 產物裡。

[`16:07`](https://youtu.be/YwZR6tc7qYg?t=967) 於是我們現在有了「人與代理的對齊」。這裡的想法是：你逼代理把它找到的所有東西、它想做的所有事、它認為你想要的所有東西，全部傾倒出來，並對它不知道的事向你提問。這樣你就能在往下游走之前對代理做腦部手術。

[`16:24`](https://youtu.be/YwZR6tc7qYg?t=984) 這一切都是為了「不要外包思考」。在你去寫兩千行程式碼之前，你要給代理每一個機會把它搞錯的地方攤開給你看。

[`16:35`](https://youtu.be/YwZR6tc7qYg?t=995) 所以 200 行取代一千行，多一點槓桿。我們也從「大綱」拿到更好的槓桿。如果設計是「我們要去哪裡」，那結構大綱就是「我們怎麼過去」。或者，如果你是那種整天坐在會議裡很痛苦的工程師：一個是架構審查會，另一個是 sprint 規劃會 —— 我們要建什麼，以及我們要怎麼把它拆成任務。

[`16:56`](https://youtu.be/YwZR6tc7qYg?t=1016) 所以我們拿設計、拿票、拿研究，建立一個新的脈絡視窗，產出結構大綱。這基本上是階段的高層次概觀 —— 不是我們要寫的確切程式碼，而是它大概會長什麼樣、我們要以什麼順序做這些變更、以及過程中怎麼測試。

[`17:12`](https://youtu.be/YwZR6tc7qYg?t=1032) 我其實不會在每個階段之間都測試我建的每樣東西，但如果它敏感、困難或複雜，我希望能在它去寫完所有程式碼之前就抓到問題。我希望確保每個兩三百、四百行的區塊都是對的。

[`17:23`](https://youtu.be/YwZR6tc7qYg?t=1043) 而且這些文件意味著更輕量的審查。這兩份是同一個功能：計畫八頁，結構大綱大約兩頁，短得多。

[`17:33`](https://youtu.be/YwZR6tc7qYg?t=1053) 我喜歡這樣想：有人寫過 C 的標頭檔（.h）嗎？有。好，如果計畫是實作，那大綱就是 C 標頭檔 —— 只有簽章與我們要改的新型別，足夠讓你看見代理在想什麼，錯了就糾正它。

[`17:50`](https://youtu.be/YwZR6tc7qYg?t=1070) 我們這樣做的原因是：儘管試過每一個模型、試著用 prompt 把這件事壓下去、把它 eval 到死，我們就是沒辦法讓模型停止寫「橫向計畫」。這是修正它們寫橫向計畫這個傾向的最好方法。

我說的橫向計畫是指：模型很愛先做完所有資料庫，然後做完所有服務層，然後做完所有 API，然後做完所有前端。等你回過神來，你已經在 1,200 行程式碼的另一端，而且它不能動，現在你得去搞清楚哪一部分壞了 —— 因為過程中根本沒有東西可以測。

[`18:24`](https://youtu.be/YwZR6tc7qYg?t=1104) 不管是模型在驗證，還是你這個人跳進去檢查它是否正確。我們在各種規模的組織都看到效果非常好的是我稱為「**縱向計畫**」的做法。這就是我在 AI 之前建東西的方式：我會先做一個假的 API 端點，讓前端能跑起來，接起來，再把服務層做成假的，然後做資料庫遷移，最後把一切組起來。

[`18:46`](https://youtu.be/YwZR6tc7qYg?t=1126) 所以即使程式碼量一樣，你有這些檢查點可以看它有沒有在動；如果沒有，你可以暫停並修好，再去做其餘的。這些也只是 markdown 文件，你可以也應該要求更多細節。它們一開始是高層次的，但例如你可以說「我不覺得你會做對這個，告訴我你在想什麼」，它就會把型別與簽章傾倒出來。

[`19:04`](https://youtu.be/YwZR6tc7qYg?t=1144) 然後是從計畫本身拿到更好的槓桿。跟平常一樣，我們拿那份產物、把先前所有產物疊上去，然後就能建計畫了。如果你用 `create plan` 也一樣，完全相同的範本、設定與 prompt，但這是給代理看的戰術文件。我們已經對齊得夠多，所以我只會抽查它，把深度審查留給真正的程式碼。

[`19:28`](https://youtu.be/YwZR6tc7qYg?t=1168) 如果你用過任何 RPI 計畫，它們長這樣：模型說「嘿，這是我要做的所有變更」。

[`19:35`](https://youtu.be/YwZR6tc7qYg?t=1175) 不過這個槓桿最重要的部分不只是你與代理之間。人與代理的對齊很重要、知道代理要做什麼並糾正它很好，但如果你跟一群工程師合作，我們發現把這些設計討論、結構大綱拿去給人審查非常有價值 —— 我說過不要審查計畫，但這些較短的文件真的非常好。

[`19:57`](https://youtu.be/YwZR6tc7qYg?t=1197) 我不是 HumanLayer 大部分程式碼的 code owner，我的共同創辦人才是。我會刻意把我的設計討論寄給他。我們沒有強制這個步驟，但我想知道：等我們真的做 code review 時，他只會說「對，那就是我要的，就這樣」。所以我所有的壞決定都在一份 200 行的文件上就被攔截了 —— 在我去寫完程式碼、讓它能跑、並且對它產生感情之前。這真的非常強大。

[`20:22`](https://youtu.be/YwZR6tc7qYg?t=1222) 在 AI 之前 —— 換個角度想，這是時間節省的問題。你會說：好，這是個兩天的功能，我得做這些事，寫程式大概兩到四小時。如果你只是拿起 Claude Code 讓它幫你出貨，你確實會得到一些加速，因為現在寫程式只要 20 分鐘。但它仍然是個兩天的功能，因為我還是得跟團隊對齊要做什麼，還是得做 code review 並修東西，也許我在跨我不擁有的 repo 工作，然後我們還是得驗證與測試。

[`20:47`](https://youtu.be/YwZR6tc7qYg?t=1247) 但如果你用 AI 幫你做規劃與對齊，那你在那裡也省了時間，而且我認為你得到好得多的對齊。於是你的 code review 與返工也短得多，因為你已經知道會發生什麼，審查的團隊也已經有過重新導正你的機會。真正好的團隊會這樣做 —— 他們有個叫架構審查的會議，在那裡決定技術設計文件、決定我們要怎麼建這個東西。

[`21:12`](https://youtu.be/YwZR6tc7qYg?t=1272) 至於測試與驗證，抱歉，我沒有好答案給你，那是另一整場演講。如果你去聽了樓下 Drew 的演講，結束後去找 Drew Brun，他會告訴你所有關於測試與驗證的事。

[`21:21`](https://youtu.be/YwZR6tc7qYg?t=1281) 把這些串起來。我們有研究與規劃的五個階段。流程基本上是：questions、research、design、structure outline、plan、worktree、implement，最後是 pull request。不過那拼不出好聽的縮寫，所以我們挑了喜歡的幾個字母，把它叫做 **crispy**。從 RPI 到 crispy。

[`21:43`](https://youtu.be/YwZR6tc7qYg?t=1303) 接下來呢？今天沒時間談的有什麼？三個步驟對某些人來說已經很多要學了，現在變成七個。我以為我們該讓團隊更容易學會並採用才對。我們可以談談我們怎麼想這件事。

[`21:57`](https://youtu.be/YwZR6tc7qYg?t=1317) 還有「怎麼衡量這樣做對工程團隊的影響」。我想我們試著衡量開發者生產力已經 50 年了，到現在還是不太會衡量。

[`22:06`](https://youtu.be/YwZR6tc7qYg?t=1326) 然後是：如果你是中央平台團隊，要把變更推給組織裡所有人，你要怎麼讓這些 prompt 變更好？怎麼讓這套工程系統變更好？我們剛剛還在聊「現在每個團隊都有一個 skill」，我們想整併、共享，讓大家從彼此的學習中受益。那你要怎麼在不打斷某人工作流、不讓某個團隊退步的情況下把那些東西改好？

[`22:31`](https://youtu.be/YwZR6tc7qYg?t=1351) 如果你想幫我們 —— 如果你在舊金山、在做關鍵系統，而且想搞清楚怎麼讓 coding agent 做更多事 —— 來聊聊。我們也在徵人。不管哪種都歡迎來信：founders@humanlayer.dev。

[`22:43`](https://youtu.be/YwZR6tc7qYg?t=1363) 我們在做一個會幫你編排這些東西的 IDE。你不需要它也能從這套方法得到價值，但那是我們在做的東西。

[`22:52`](https://youtu.be/YwZR6tc7qYg?t=1372) 想一起玩的話，我週六要辦一場 sandbox 研究黑客松。我們會找一群很酷的開發者聚在一起，一起測試所有 sandbox 供應商，看哪個最好，然後分享我們學到的。我也會去 Daytona Compute Conference。如果你想來邁阿密，AI Engineer Miami 會很好玩，我會講這場演講的更新版，加上今天沒時間講的東西。

[`23:15`](https://youtu.be/YwZR6tc7qYg?t=1395) 非常感謝各位的熱情，感謝 Demetrios 與整個籌辦團隊。祝好運。

[`23:22`](https://youtu.be/YwZR6tc7qYg?t=1402) 問答時間。誰要問 Dex 問題？講超快的，我喜歡。我本來很懷疑你講得完，但我喜歡。

[`23:32`](https://youtu.be/YwZR6tc7qYg?t=1412) 好，我對「讀程式碼」很好奇。那不可規模化吧？你六個月後還會說同樣的話嗎？

我是說，六個月前我說不要讀它。我想現在所有說「不要讀程式碼」的人，六個月後都會說「對啦，我們後來得把那些丟掉」。中間一定有個平衡點吧 —— 我們正在對「該讀多少程式碼」這個空間做二分搜尋。

[`23:55`](https://youtu.be/YwZR6tc7qYg?t=1435) 我想，概念是：如果你還是讀程式碼，你仍然能得到 2 到 3 倍的加速。而那其實是比「快 10 倍、出一堆 slop、然後期望 GPT-7 會幫你修好」更好的商業結果。

[`24:12`](https://youtu.be/YwZR6tc7qYg?t=1452) 很棒的演講。我好奇你對「軟體工廠」的看法。我想 StrongDM 說的正好相反 —— 兩邊都不要讓人讀。那會把我們更推向 eval。你怎麼看？

[`24:35`](https://youtu.be/YwZR6tc7qYg?t=1475) 對，有一整類東西 —— 你可以一路鑽進形式化驗證、TLA+ 那個兔子洞。我跟一個正在做新版 TLA+（他叫它 TLA++）的人聊過，概念是：如果我們不讀程式碼呢？我們要怎麼真正形式化地驗證一切都在運作？

[`24:52`](https://youtu.be/YwZR6tc7qYg?t=1492) 我想還有很多東西要建，而現在有很多人需要更快把程式碼送上 production 系統。所以也許某天吧。我以前常引用 Sean Grove 的演講，他說「那就是規格 —— 寫出描述期望行為的文件，把程式碼當組合語言，你再也不讀它」。我不背書那個說法，就這樣講吧。

[`25:17`](https://youtu.be/YwZR6tc7qYg?t=1517) 還有一個問題。你有張投影片提到脈絡視窗與「笨蛋區間」。我知道你深入研究過 —— 你有回頭再看過，確認在有了自動壓縮與其他方法之後，那件事還有多真嗎？

[`25:41`](https://youtu.be/YwZR6tc7qYg?t=1541) 我想，如果你已經用 AI coding agent 六到九個月、而且一週用 60 小時，那「笨蛋區間」對你不是個有用的概念。我常常會開到 60%，也常常積極地把它壓在 30% 以下。這取決於你任務的複雜度、以及指令與資訊的比例。

[`26:06`](https://youtu.be/YwZR6tc7qYg?t=1566) 所以因人而異。如果你是第一次用 coding agent，我們教人的是：如果你不知道該怎麼做、還沒培養出那種直覺，那就設法把它維持在 40% 以下；如果到了 60%，就該想著收尾了。

[`26:15`](https://youtu.be/YwZR6tc7qYg?t=1575) 而且你可以一直在同一份文件上迭代。這也是這套做法好的地方：**我們不用內建的壓縮**，因為所有重要的東西都進了靜態產物，所以你永遠能從離開的地方接續，不必擔心自動壓縮或手動壓縮的品質。

[`26:32`](https://youtu.be/YwZR6tc7qYg?t=1592) 精彩，Dex。做得好，老兄。謝謝。大家給他掌聲。
