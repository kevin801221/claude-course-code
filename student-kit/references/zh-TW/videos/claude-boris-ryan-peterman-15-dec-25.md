## 逐字稿

[`0:02`](https://youtu.be/AmdLVWMdjOk?t=2) 模型進展太快了。如果你三個月或六個月後再問我這個問題，我的答案會完全不同。這位是 Boris Cherny。他是 Claude Code 的創造者，也是前 Meta principal engineer。我們聊了形塑他職涯的一切。你能解釋什麼是潛在需求（latent demand）嗎？

[`0:17`](https://youtu.be/AmdLVWMdjOk?t=17) 潛在需求我認為是產品上最重要的單一原則。

[`0:22`](https://youtu.be/AmdLVWMdjOk?t=22) 你說過那裡有明顯的文化差異，而且很困難。

[`0:26`](https://youtu.be/AmdLVWMdjOk?t=26) 天啊，「困難」太輕描淡寫了。那根本是惡夢。我們也聊了 Claude Code 以及 Anthropic 內部現在實際發生的事。即使 Anthropic 人數已經成長三倍，每位工程師的生產力因為 Claude Code 還成長了將近 70%。不要為今天的模型而建，要為六個月後的模型而建。那本對我身為工程師影響最大、我會推薦給所有人的技術書是什麼？你對 Codex 和 OpenAI 的競爭有什麼看法？我想從你故事的起點開始聊，也就是你在 Meta 升上 senior engineer。讓你升職的那些專案背後有什麼故事？你當時在什麼位置？

如果我沒記錯，那個專案是 chats and groups，目標是讓 Messenger 和 Facebook 更靠近一些。我在 Meta 最初幾個專案其實都跟 Messenger 和 Facebook 有關。第一個大概是 Zuck 有個想法，要同步 Messenger 聊天和 Facebook 社團。總之有好幾個這類專案都在試著讓 Messenger 和 Facebook 更靠近。動機是當時有種感覺：這種公開空間的社交產品正在消失，事情越來越往聊天、往那些比較隨性的即時空間移動。所以我們試了好幾個版本的產品，chats and groups 是成功的那個。我記得那是第三還第四個版本。我當時在 Facebook groups，而我大量跟 Messenger 合作，那在組織上非常遙遠。這個點子我想是當時的 PM Steve 提出的，他覺得這是我們該做的東西，我就接過來說：對，就做吧。於是我開始動手 hack。很快就有了一些生命跡象，所以我要了更多工程師，有三位加入：Shatambri、Crystal 和 Chaang，他們是最早加入的三位工程師。然後我們也拿到一些資料科學和設計的支援。一開始只做 web，後來也稍微做了行動版。我想我們就是證明了「Facebook 社團裡可以有聊天」這個點子，而且這種產品是可行的。老實說也有一堆東西完全不管用。以現代產品標準來看那是超級克難的體驗。以前大家都在 web 上做，各種 bug 都完全可以接受。現在我覺得標準 —— 老實說視覺標準、品質標準高太多了。總之產品成長起來，而我們團隊很小，每個人什麼都要做。我記得我們沒有使用者研究員，所以我會在午餐時間去員工餐廳，有新功能就拿去給餐廳員工看，說「嘿，你能找到怎麼開啟聊天嗎？」有時他們找得到，有時找不到。這就是一種觀察式使用者研究。你看人在特定情境下能不能完成任務，而且你不太提示他們。你不想洩漏太多，就看他們卡在哪裡、看他們抓到什麼。我們就這樣做，然後我把這套方法教給團隊。很快我們午餐都會去餐廳，開始去「騷擾」餐廳員工，把他們當代表性使用者問：這樣講得通嗎？

有趣的是，你當時所處的早期 Facebook 文化讓工程師能做這麼多程式碼以外的事。例如你在做 UXR，我記得你故事裡也做了一些設計，還教別人做設計。我覺得那是 Facebook 文化裡滿特別的一點。

我覺得這非常重要，而且到今天為止，在我現在所在的 Claude Code 團隊，我們真的很優先重視通才。我超愛跟通才一起工作。如果你是一位會寫程式、但也能做產品工作、也能做設計、有產品直覺、願意去跟使用者聊的工程師 —— 我很愛跟這種工程師合作。而這其實也是我們現在招募所有職能的方式。我們的產品經理會寫程式、資料科學家會寫程式、使用者研究員也會寫一點程式。我就是很愛這些通才，而且我覺得這真的是我成長的方式 —— 從一開始我 18 歲經營第一間新創時我什麼都得做，一直到進 Facebook 之前我都在小公司，什麼都得做。我有種感覺是：在大公司你會被逼進某條特定的泳道，但那只是「官方」劃分而已，因為什麼叫工程？那是個很窄的技能組，但你真正在做的事是打造產品或打造基礎設施，而要端到端完成那件事，除了寫程式之外還有太多東西了。能待在一個 —— 我覺得 Facebook 當時很獨特地獎勵這種做法的地方 —— 真的很棒。而且我想那半年結束時我升職了，然後下半年每一位工程師也都升職了。

在那些早期產品裡，你提過好幾次「潛在需求」這個概念，聽起來是很多產品方向的推動力。你能解釋什麼是潛在需求嗎？

[`5:42`](https://youtu.be/AmdLVWMdjOk?t=342) 潛在需求我認為是產品上最重要的單一原則，而且我覺得如果你看 Facebook 成功的產品，每一個都有潛在需求的成分。例如 Marketplace，它來自一個觀察：當時看 Facebook 社團，40% 的貼文是在買賣東西。Facebook 社團不是為了商務而設計的，但人們就是那樣用。所以很酷的是，你用一種「可以被 hack」的方式設計產品，使用者可以稍微濫用它，然後你看資料、看他們怎麼濫用，再圍繞它打造產品。所以先有 Facebook 社團，然後有買賣社團，那當然成功了，因為人們本來就想在 Facebook 社團買賣、做商務，接著 Marketplace 就來了。那是同一個意圖的自然延伸。我想 Facebook Dating 也很類似。那個觀察大概是：60% 的個人檔案瀏覽來自彼此不是好友的異性。就是那種傳統的「互相偷看」。我想對當時的 Nate 和 FMS 來說，那就是這件事可行的證據。我認為產品上的原則是：你永遠無法讓人們去做他們還沒在做的事。你能做的是找到他們已有的意圖，然後引導它，讓他們更能把那個意圖變現、更輕鬆地做他們想做的事。

我想在你故事的這個段落，你也提到你跨組工作，因為你在 Messenger 和很多社團工程工作之間搭橋。我很好奇，你說那裡有明顯的文化差異，而且很困難。你對跨非常不同文化的組織合作有什麼建議？

[`7:30`](https://youtu.be/AmdLVWMdjOk?t=450) 天啊，「困難」太輕描淡寫了。那根本是惡夢。當時對 Facebook 來說，我們想要出貨，我們就是想跑快、盡快推出很棒的產品。而 Messenger 全部都是關於可靠度與效能，他們只在乎那個。價值觀完全相反。而這不只是文化，不只是工程師對工程師的事。那個團隊的工程師對我們有戒心，因為我們會影響他們的效能指標。而且組織上，他們的部門被設計成「慢慢出貨但不讓指標退步」，我們被設計成「快速出貨」。然後目標完全不同，他們有 SLA 可用率，而我們只看日活躍使用者與互動。所以對我來說，學到的是：這些文化價值觀深入骨髓。那不只是人們嘴上講的東西，你真的能在組織設計、目標設計、在每一個部分裡看到它。老實說我覺得那個專案失敗的原因之一 —— 它最後其實演化成了成功的東西，但那個版本的專案失敗了 —— 就是這種價值觀差異。所以我認為，根本上如果你想讓價值觀差異很大的公司成功合作，你得找到某種共同目標、共同利益、共同信念，某個他們想一起驗證、而且若成立對雙方都會非常有趣的假說。而 chats and groups 這件事根本上對 Facebook 很酷，但基於很多理由，對 Messenger 沒那麼酷。

以你現在知道的，如果回到那個專案，你會怎麼改？

[`9:10`](https://youtu.be/AmdLVWMdjOk?t=550) 我大概會直接去找 Zuck 說：如果你真的認真看待這件事，我們應該把 Messenger 併進 Facebook 部門。我想這後來確實發生了，而且發生好幾次 —— Messenger 在部門裡，然後移出去，然後又移進來，又移出去。大公司嘛，這種事會發生。但我認為根本上，要讓這種事成功，共同匯報的那個人不能是 Chris Cox 這種層級，得再低一點。這樣你才能把組織結構安排得更適合協作。

[`9:39`](https://youtu.be/AmdLVWMdjOk?t=579) 我懂，讓誘因對齊，才不會一直拉扯。

[`9:44`](https://youtu.be/AmdLVWMdjOk?t=584) 對，正是。

在你職涯的這個時間點，我看到你有一堆很有趣的副專案，我好奇這類專案的蝴蝶效應是什麼？例如在你進 Meta 之前，你做了 Undux，那個 React 狀態管理框架。這對你的職涯有影響嗎？

[`10:07`](https://youtu.be/AmdLVWMdjOk?t=607) 對，對我來說支線任務太重要了，而且我招工程師時這絕對是我會看的東西。我想要有支線任務的人 —— 很酷的週末專案、很酷的副專案，甚至是那種很認真在釀康普茶的人也行。你想要的是那種普遍好奇、對本業以外的事物感興趣的人。那是比較全面的人，是我享受共事的那種人。對我來說，我很多成長都來自這類副專案。像 Undux，它的起源老實說是：React 狀態管理真的複雜得沒必要，當時最先進的是 Flux，然後有個叫 Redux 的東西，而我就是搞不懂 Redux。我覺得自己算是個普通工程師，我做產品，我不是那種了不起的系統工程師。所以當時 Redux 那些 reducer 之類的概念、那種你只是要更新一點點狀態就得走的超複雜流程，我就是想不通。所以我做了一個看起來能用的簡單版本。我當時在一個非營利組織做志工，他們開始用它，他們的工程師很喜歡。然後我進 Facebook 時，看到大家對 Redux 的使用有很多挫折感，因為有個內部社團是給用 Redux 的人用的，裡面都是跟我一樣的問題。當你身為工程師或產品人碰到一個問題時，有時只有你會碰到，但往往其他人也會。我覺得重要的是培養那種直覺：判斷這個問題是不是其他人也共有。而這個問題確實是大家共有的，我從支援貼文、從我團隊用 Redux 的困難看得出來。所以我在內部推出了 Undux。Undux 就還好，不是多厲害的產品，但至少比 Redux 好。在 Facebook 我其實不知道怎麼推廣採用。我就發文，少數人開始用。我記得通知團隊的 Jeff Case 是早期重度採用者，我們熬了幾個夜除掉一些跟通知有關的噁心 bug。我想要更多採用，所以我寫了個小腳本，爬了那個回報問題的社團，依團隊統計，然後我直接在聊天上聯絡每個團隊的 tech lead 和 manager，為那個團隊單獨排一場技術分享。總共大概在幾週內做了 20、30、40 場技術分享吧。

[`12:45`](https://youtu.be/AmdLVWMdjOk?t=765) 我記得就騎著腳踏車在 Meta 園區裡到處跑去講，很好玩，因為大家超投入，他們就是很興奮有人在乎解決他們真的碰到的這個問題。我想某個時間點 Undux 是 Facebook 最受歡迎的狀態管理框架，然後它很快被 Recoil 和更現代的替代品取代，現在則是 Relay 之類的。

那種副專案會出現在你的績效考核裡，還是以某種方式幫到你？

我想它有在我的績效考核裡。以 Meta 的標準來說它算是錦上添花，本身並不是那種會讓你升到下一級的東西。不過那段時間我還有很多其他支線任務。某個時間點我真的很迷 TypeScript，那是在前一家公司，我們在用它，但沒什麼好資源。所以我就開始寫一本關於它的書，因為我想「總該有人做這件事吧，它不存在太誇張了」。這個語言太出色了，設計好到令人震驚。它有一堆當時沒有其他語言有的想法 —— 像是當時還沒有條件型別，但像條件型別、對所有東西的字面型別、映射型別，這些根本是瘋狂的東西。就連最硬派的 Haskell 玩家都會對這種語言特性印象深刻，但沒人在寫這些，所以我就超級投入、寫了這本書，結果它吃掉我人生整整一年。（笑）不建議。但深入鑽進去真的很好玩。我後來還在舊金山辦了當時世界上最大的 TypeScript 聚會，那是很酷的機會去認識 —— 有 Node.js 的創造者 Ryan Dahl，還有一堆 JavaScript 界的名人。那讓我意識到，這些人就只是人，大家都在做很酷的東西，有些很酷、有些在特定時刻很酷，但全都只是人，任何人都能做這些事。

[`14:47`](https://youtu.be/AmdLVWMdjOk?t=887) 你後來在 Meta、甚至在 Anthropic 有用上 TypeScript 或那份技術深度嗎？

有啊，說來好笑。我以前其實不在乎語言，然後某個時間點，大概十年前，我騎機車出了一場滿嚴重的車禍，我手斷了。

[`15:05`](https://youtu.be/AmdLVWMdjOk?t=905) 天啊。

[`15:05`](https://youtu.be/AmdLVWMdjOk?t=905) 兩隻都斷。

[`15:06`](https://youtu.be/AmdLVWMdjOk?t=906) 兩隻都斷，對。我掛著兩個吊帶。

[`15:08`](https://youtu.be/AmdLVWMdjOk?t=908) 天啊，那你怎麼寫程式？

[`15:10`](https://youtu.be/AmdLVWMdjOk?t=910) 那就是難的地方。我大概有一個月完全不能寫，然後手還是會痛，所以我沒辦法寫 JavaScript —— 那是我當時寫的東西。所以我真的得分枝去學別的語言，因為它們字面上就是按鍵數比較少。我從 CoffeeScript 開始，因為括號之類的比較少。我想那語言現在大概已經不存在了，沒人在用。但那也是我開始接觸 Haskell 和函數式編程的原因，因為你能用更少按鍵做同樣的事 —— 當時的動機真的就是這個。後來某個時間點我在一家避險基金工作，那是進 Facebook 之前，我有位同事 Rick 非常迷 Scala，我當時完全不懂 Scala，是他把我拉進去、拉進函數式編程這一派的。到現在，那本對我身為工程師影響最大、我會推薦給所有人的技術書，就是《Functional Programming in Scala》。你今天大概永遠不會用到 Scala，但它教你思考程式問題的方式，跟大多數人在實務上或在學校裡編程的方式天差地遠，太厲害了，會徹底改變你寫程式的方式。所以對我來說，Haskell 和 CoffeeScript 這幾個關鍵語言是第一步，然後是 Scala，然後是 TypeScript。我覺得這改變了我的思考方式，因為現在我寫程式時是用型別在思考。程式碼裡最重要的東西是型別簽章，那比程式碼本身更重要。把這個弄對，就會導向非常乾淨的程式碼。所以即使在 Facebook 我主要寫 Flow 和 Hack，後來在 Instagram 寫 Python，這都非常有幫助。在 Anthropic 我主要寫 TypeScript 和 Python，所以其實相當相關。但我覺得更大的啟示就是：用型別思考。

[`17:07`](https://youtu.be/AmdLVWMdjOk?t=1027) 在你職涯的這個階段，你提過你進去時職級被低估了，即使你已經有很多經驗，你還是以 mid-level 工程師進去。你說事後看來，職級被低估是幸運的。這背後的想法是什麼？

[`17:23`](https://youtu.be/AmdLVWMdjOk?t=1043) 就是期待比較低。在大公司，每個層級都有關於專案影響力、人員影響力之類的特定期待，各公司的具體標準不太一樣。但其中很多是關於專案影響力，或打勾一堆框框，而這些都很花時間。所以我覺得以較低職級進去，給了我探索的空間，可以單純為了做很酷的東西而做很酷的東西。

當然。我也在想這是不是也有助於建立氣勢。我的意思是，如果你以 mid-level 或 E4 進去然後表現爆棚，大家都說「Boris 太強了，這太誇張了」，相較於你以某個高職級進去然後表現「還不錯」。我覺得當你進來就讓所有人驚艷時，那種強烈的第一印象對建立好名聲很有幫助，進而給你更多可信度、更多機會。

[`53:21`](https://youtu.be/AmdLVWMdjOk?t=3201) Unshipping 的概念是：如果你只是一直往 App 加功能，對一小部分使用者來說很酷，但對不用那個功能的大多數使用者其實是壞事。想像一個只加功能的 App，隨時間功能不斷累積疊加。如果每個功能只有 10% 的人用，平均使用者會看到一堆他們不用的功能，於是感覺雜亂又困惑，打開 App 不知道該做什麼。而軟體根本上螢幕大小是有限的，那是有限的空間，是所有功能在競爭的有限資源。所以加一個功能，就是從某個使用者可能用到的其他功能那裡奪走機會。Unshipping 的概念就是：你得達到某種使用門檻，若一個功能沒達到，我們就把它刪掉。一小部分使用者會不爽，但對大多數使用者其實很好，平均而言對所有人都很棒。

現在我走過坐在我們旁邊的資料科學家，每個人都同時開著一堆 Claude Code，不只一個了。他們在做各式各樣的事：寫 SQL、處理資料、寫 dbt pipeline、寫程式。所以我覺得寫程式以外有這麼多應用，看到人們把它用在各種事情上超酷的。甚至有完全非技術的使用者 —— Anthropic 大概一半的業務團隊用 Claude Code 做他們的工作，他們能把它接上 Salesforce、接上不同資料來源，然後用這種方式工作。看到這些很酷，因為這不是我們設計時的樣子，不是當初的意圖。

我聽到 Claude Code 也會想到 Codex，最大的競爭者之一。我好奇你對與 Codex 和 OpenAI 競爭的看法？Claude Code 哪裡做得更好？另外我也好奇這類 AI 產品的黏著度 —— 是什麼讓人留在 Claude Code 而不是 Codex？

[`1:17:46`](https://youtu.be/AmdLVWMdjOk?t=4666) 我不太確定耶。我個人不太用其他產品。（笑）

[`1:17:51`](https://youtu.be/AmdLVWMdjOk?t=4671) 對我來說，我跟團隊說的是：太容易因為看競品而偏離正軌了。我看過大公司很常掉進這個失敗模式 —— 因為競品太多，而光靠抄襲就能看到「你可以做的那個東西」太容易了；要想出新穎的、更能解決使用者需求的點子則比較難。所以我非常努力在做、也在推團隊做的是：不要被那些產品帶偏，永遠都會有一大堆，而它們越多，越是我們成功的徵兆。我們全神貫注的是解決我們自己的問題、解決 Anthropic 研究員的問題、解決使用者的問題。

對話接近尾聲，我想問幾個職涯反思。我在查資料時好奇的一件事是：你沒有 CS 學位，卻成為這麼強的軟體工程師。你職涯中有任何時候覺得這件事拖累你嗎？還是你覺得它不必要、不相關？

[`1:19:05`](https://youtu.be/AmdLVWMdjOk?t=4745) 我念的是經濟學，而且我其實輟學去做新創了。對我來說，你做的任何事都是在工作中學的，而我覺得程式設計就是一項非常實務的技能。我很難想像學校裡學的那些東西 —— 如果你在資料結構課上跑這些，但你從沒建過產品，那到底哪裡相關？所以我的建議會是：實務地學寫程式，那是非常實務的技能。之後如果你想回頭學理論，就去學。但我個人從沒覺得它拖累過我。

[`1:19:44`](https://youtu.be/AmdLVWMdjOk?t=4784) 那生產力技巧呢？我看到你說你大概每天 9 點到 6 點工作，而且只用兩隻手指打字（笑），但你的產出誇張得不得了 —— 一堆副專案，本業也不是鬧著玩的。你最推薦的生產力技巧是什麼？你怎麼維持？

我想我現在的技巧跟幾年前會講的非常不同。現在的技巧就是：學會怎麼用 Claude Code，學會怎麼同時跑一堆 Claude Code 去做事。我們幾週前推出外掛，做這件事的工程師之一 Daisy 就讓她的 Claude 去開一個 Asana 看板、建立任務，然後她放了一群大概 20 個 Claude 在週末一直建外掛。她在 docker container 裡用 dangerous 模式跑，幾天後就做完了。這就是工程的未來。

我想現在談生產力技巧，就是：學會用 Claude 自動化苦工，以及怎麼把一堆 Claude 一起用來完成工作。所以你是在編排，而不是手動寫程式。幾年前我的技巧會非常不同，會平淡得多 —— 像是把時間區塊劃出來之類的。

[`1:21:03`](https://youtu.be/AmdLVWMdjOk?t=4863) 對，Claude Code 這件事很有趣。我在想這對著名的「製造者行程 vs 管理者行程」有什麼影響。你剛說的感覺像是：軟體工程師變得更像管理者的工作方式，你有一支 Claude Code 艦隊，你不需要深度專注才能推進，你需要的是在 20 件不同的事之間切換脈絡。所以你不再有大塊的專注寫程式時間嗎？你怎麼看？

沒那麼多了。我傾向在週末寫程式，我很愛那種安靜的時間。但除此之外，我每天早上會打開 Claude Code 和手機 App —— Claude 現在有個 Code 分頁，我們這週剛推出，但我們已經用了一陣子。所以每天早上我醒來就啟動幾個代理，開始我這一天的程式。這很瘋狂，因為如果你六個月前問我會不會這樣寫程式，我會說：「不會吧，你瘋了嗎？怎麼可能這樣寫程式？」但它真的有效。它就在這裡，而且有效，這就是我現在寫很多程式的方式。

我會先啟動幾個代理，等我到電腦前再去看狀態。有時程式碼看起來不錯我就直接合併，有時我會把它拉到本機、teleport 過去稍微改一下。

我想你之後會跟 Fiona 聊，據她跟我說，她大概十年沒寫程式了，但她現在一週會寫好幾次，因為身為管理者，即使行程瘋狂，她還是能用手機 App、用網頁版，也還是能開個終端機讓它幫她寫程式。所以真的很瘋狂，我們正在經歷這個轉變 —— 我們做的事、我從小做到大的事，正在徹底改變。而且超酷的是，它正變得人人都能用。

[`1:23:00`](https://youtu.be/AmdLVWMdjOk?t=4980) 最後一個問題：以你現在職涯中知道的一切，如果能回到剛進業界的自己，你會給自己什麼建議？

就是用常識。（笑）我覺得有很多東西 —— 特別在大公司 —— 會把你從常識旁邊拉走。有很多組織慣性：事情是這樣，因為它們一直都是這樣。有很多錯置的誘因。當然也有很多好東西，但這些東西也存在。所以在這件事上用常識真的非常重要。我職涯早期開過幾家新創、也在很多新創工作過，我覺得那邊也一樣：用常識去搞清楚市場要什麼、使用者要什麼，然後去把它做出來。所以就是相信自己、培養你的常識。
