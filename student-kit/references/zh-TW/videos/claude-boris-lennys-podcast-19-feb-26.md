[`5:37`](https://youtu.be/We7BZVKbCVw?t=337) 好，那我順著「回到 Anthropic」這條線談你在那裡做的工作。這集播出時大約是 Claude Code 發布一週年，所以我想花點時間回顧你造成的影響。

最近有份 SemiAnalysis 的報告，我相信你看過，說現在 GitHub 上 4% 的 commit 是由 Claude Code 撰寫的，而且他們預測到年底會是 GitHub 全部 commit 的五分之一。他們的說法是：「我們一眨眼，AI 就吞掉了整個軟體開發。」我們錄這集的當天，Spotify 剛發了一則標題說他們最好的開發者自十二月以來因為 AI 一行程式碼都沒寫。越來越多最先進的資深工程師，包括你，都在說自己不再寫程式了，全部由 AI 生成，很多人甚至不再看程式碼。我們走到這一步，很大程度上要歸功於你開始的這個小專案，以及你的團隊過去一年把它規模化。我很好奇你對這一年、以及你的工作造成的影響有什麼反思？

這些數字真的太瘋狂了。全世界 4% 的 commit 遠超過我想像，而且就像你說的，這感覺仍然只是起點。而且這些只是公開的 commit，我們其實認為如果看私有 repository，比例會高不少。

對我來說最瘋狂的甚至不是現在的數字，而是我們成長的速度 —— 因為如果你看 Claude Code 在任何一個指標上的成長率，它都還在加速。所以不只是往上，而是越來越快地往上。

我最初開始做 Claude Code 時，它本來只是個小 hack。我們在 Anthropic 大致知道我們想出一個寫程式的產品。Anthropic 長期以來建模型的方式符合我們對「怎麼打造安全 AI」的心智模型：模型先變得很會寫程式，然後很會用工具，然後很會用電腦 —— 大致是這條軌跡。

我一開始加入的團隊叫 Anthropic Labs team。其實是 Mike Krieger 和 Ben Mann 把這個團隊重新啟動的，算第二輪。這個團隊做了一些很酷的東西：我們做了 Claude Code、做了 MCP、做了桌面 App。你可以看到這個想法的種子 —— 先是寫程式，然後是工具使用，然後是電腦使用。

這對 Anthropic 之所以重要，是因為安全。AI 越來越強大、越來越有能力。過去一年發生的事是：至少對工程師來說，AI 不只是寫程式、不只是對話夥伴，它真的會使用工具、在世界中行動。而我想現在有了 Cowork，我們開始看到非技術人員也在經歷這個轉變。對很多使用對話式 AI 的人來說，這可能是他們第一次使用「會行動」的東西 —— 它真的能用你的 Gmail、用你的 Slack、幫你做這些事，而且做得相當好。而且從這裡只會更好。

所以我想 Anthropic 長期以來有種感覺是我們想做點什麼，但不清楚是什麼。我加入 Anthropic 後花了一個月 hack，做了一堆奇怪的原型，大部分沒出貨、連接近出貨都談不上，那只是在理解模型能力的邊界。然後我花了一個月做後訓練，去理解研究那一側。老實說，我身為工程師覺得要把工作做好，你真的得理解你工作那一層底下的那一層。傳統工程工作中，如果你做產品，你會想理解基礎設施、執行期、虛擬機、語言，或任何你建構其上的系統。而如果你在做 AI，你就是得在某種程度上理解模型，才能做出好工作。所以我繞了一小段路去做那個，然後回來開始做原型，最後變成了 Claude Code。

最早的版本 —— 我有一段影片錄影，是那年夏天錄的 demo，我把它貼出來，當時叫 ClaudeCLI。我展示它怎麼用幾個工具，而讓我震撼的是：我給了它一個 bash 工具，它就能用那個工具寫程式碼，在我問「我在聽什麼音樂？」時告訴我答案。這太瘋狂了，因為我沒有指示模型「用這個工具做這件事」之類的。模型拿到這個工具，就自己想出怎麼用它來回答我這個問題 —— 一個我甚至不確定它能不能回答的問題。

於是我又多做了一點原型，寫了一篇貼文在內部宣布，拿到兩個讚。那就是當時反應的全部。因為我想內部的人想到寫程式工具時會想到 IDE、想到那些相當精巧的環境，沒人想過這東西可以是終端機式的。那是個怪異的設計方式，而且那其實不是刻意的 —— 我一開始就在終端機裡做，是因為頭幾個月只有我一個人，那是最容易的做法。

對我來說這其實是個很重要的產品教訓：你會想在一開始稍微「資源不足」一點。

後來我們開始想該做哪些其他形態，而我們其實決定繼續待在終端機一陣子，最大的原因是模型進步太快了。我們覺得沒有其他形態跟得上。老實說這只是我自己在掙扎該做什麼 —— 過去一年 Claude Code 就是我腦中唯一的事。深夜時我就在想：好，模型持續在進步，我們該做什麼？我們怎麼可能跟得上？而終端機老實說是我唯一想到的點子。

結果發布後它相當快就流行起來，在 Anthropic 內部成了熱門，日活躍使用者直接垂直上升。其實在我發布之前，Ben Mann 就推我做一張 DAU 圖表，我說「現在會不會有點早？」他說「做吧」。然後那張圖幾乎立刻就垂直上升。

接著二月我們對外發布。其實大家不太記得的是：Claude Code 剛發布時並不是個熱門產品。它有一批使用者、有很多早期採用者立刻就上手，但其實花了好幾個月大家才真正理解這東西是什麼。它就是太不一樣了。

我想 Claude Code 之所以行得通，一部分是「潛在需求」的概念 —— 我們把工具帶到人們已經在的地方，讓既有工作流變得容易一點。但也因為它在終端機裡，所以有點令人意外、有點外星感，你得抱持開放心態、得學著用它。

當然現在 Claude Code 在 iOS 與 Android 的 Claude App 裡都有、桌面 App 裡有、網站上有、有 IDE 擴充套件、在 Slack 與 GitHub 裡都有 —— 所有工程師在的地方。那比較熟悉，但那不是起點。

所以一開始，這東西居然有用這件事本身就滿意外的。隨著團隊成長、產品成長、它對人們越來越有用，世界各地的人 —— 從小新創到最大的 FAANG 公司 —— 開始使用它並給我們回饋。回頭看，這是一段非常讓人謙卑的經驗，因為我們不斷從使用者身上學習。而最令人興奮的是：我們其實都不知道自己在做什麼，我們只是跟大家一起摸索，而最好的單一訊號就是使用者的回饋。我被驚訝過太多次了。

[`13:59`](https://youtu.be/We7BZVKbCVw?t=839) 對，非常快。去年五月的 Code with Claude，那是我們 Anthropic 辦的第一場開發者大會。我做了一場短講，講完 Q&A 時有人問「你對年底的預測是什麼」。我在 2025 年五月的預測是：到年底你可能不再需要 IDE 來寫程式，我們會開始看到工程師不再這樣做。我記得全場倒抽一口氣，那是個瘋狂的預測。

但我想在 Anthropic，這就是我們思考事情的方式 —— 用指數思考，這深深刻在 DNA 裡。我們的共同創辦人中有三位是 scaling laws 論文的前三位作者。所以我們真的就是用指數思考。如果你看「Claude 寫的程式碼百分比」那條指數曲線，照著畫下去，很明顯年底會越過 100%，即使那完全不符合直覺。我做的只是把線延長。而十一月那件事對我個人就發生了，從此一直如此，我們也開始在很多客戶身上看到同樣的事。

我覺得你剛分享的這段旅程很有意思 —— 就是「玩玩看會發生什麼」。這在 OpenClaw 也常出現，Peter 就是在玩，然後某件事就發生了。感覺這是 AI 很多最大創新的核心成分：人們就只是坐在那裡試東西，把模型推得比大多數人更遠。

[`15:23`](https://youtu.be/We7BZVKbCVw?t=923) 創新這件事你沒辦法硬逼。創新沒有路線圖，你只能給人空間。你得給他們……也許「安全感」是那個詞 —— 心理安全感，失敗是可以的，80% 的點子很爛是可以的。但你也得讓他們有點當責：如果點子很爛，就止損、換下一個，而不是投入更多。

Claude Code 早期我完全不知道這東西會不會有用。即使二月我們發布時，它大概只寫我 20% 的程式碼，不會更多。即使到五月也大概只有 30%，我大部分程式碼還是用 Cursor 寫。它到十一月才越過 100%。所以花了一段時間。

但即使從最早的日子，就覺得我抓到了什麼。我每個晚上、每個週末都在弄這個，幸好我太太非常支持。就是感覺有東西在那裡，只是不清楚是什麼。有時候你找到一條線，就是得拉拉看。

[`16:53`](https://youtu.be/We7BZVKbCVw?t=1013) 100% 由 Claude Code 寫。自十一月以來我沒有手動編輯過任何一行。不過我還是會看程式碼。我不覺得我們已經到了可以完全放手的程度，特別是有很多人在跑這個程式時 —— 你得確保它是對的、是安全的。

我們也讓 Claude 對所有東西做自動 code review。在 Anthropic，Claude 審查 100% 的 pull request。之後仍然有一層人類審查，你還是會想要這些檢查點、還是想要有人看程式碼。除非那是純原型程式碼，不會跑在任何地方。

[`17:34`](https://youtu.be/We7BZVKbCVw?t=1054) 下一個前沿是什麼？現在你 100% 的程式碼由 AI 寫，軟體工程顯然都往這走。那曾經是個瘋狂的里程碑，現在變成「這就是現在的世界」。軟體寫作的下一個大轉變是什麼？你的團隊已經在做，或你認為會往哪走？

我想現在正在發生的一件事是：Claude 開始自己提出點子。Claude 會翻過回饋、看 bug 回報、看遙測資料，然後開始提出要修的 bug 與要出貨的東西。所以它開始變得更像個同事。

第二件事是我們開始從寫程式往外擴。我想現在可以安全地說：寫程式大致上已經被解決了。至少對我做的那種編程來說，它就是個已解決的問題，因為 Claude 做得到。所以我們開始想：接下來呢？這之外是什麼？有很多跟寫程式相鄰的事情，我想那些會來。

但也包括一般性的任務。我現在每天用 Cowork 做各種跟寫程式完全無關的事，而且是自動化地做。例如前幾天我得繳停車罰單，我就讓 Cowork 去做。我們團隊所有的專案管理也是 Cowork 在做 —— 在試算表之間同步東西、在 Slack 和 email 上傳訊給人等等。

所以我想前沿大概是那樣，而且我不認為是寫程式，因為寫程式基本上已經解決了。接下來幾個月我想我們會看到整個產業越來越把它解決掉 —— 對每一種 codebase、每一種技術堆疊。

[`47:30`](https://youtu.be/We7BZVKbCVw?t=2850) 可以談談這個嗎？解釋一下這個原則，以及當你解鎖這種潛在需求時會發生什麼。

潛在需求的概念是：如果你用一種「可以被 hack、可以被以非設計用途誤用」的方式打造產品，讓人們能拿它做他們想做的事，那這能幫助你這個產品打造者學到下一步該把產品帶去哪裡。

一個例子是 Facebook Marketplace。我們團隊的經理 Fiona 其實是 Marketplace 團隊的創始經理，她常談這個。Facebook Marketplace 起源於 2016 年左右的一個觀察：Facebook 社團裡 40% 的貼文是在買賣東西。這很瘋狂，人們在「濫用」Facebook 社團產品來買賣。這不是安全意義上的濫用，而是沒有人為此設計產品，但他們自己摸索出來，因為它就是對這件事很有用。所以很明顯：如果你做一個更好的買賣產品，他們會喜歡。Marketplace 會成功是顯而易見的。所以第一個產品是「買賣社團」—— 專門用途的社團，第二個產品才是 Marketplace。

Facebook Dating 我想起點也很類似。那個觀察是：看人們瀏覽彼此的個人檔案，60% 的檔案瀏覽來自彼此不是好友的異性。所以這是那種傳統的配對場景，只是人們在互相偷看。也許如果你為此做一個產品，它會行得通。

這個潛在需求的概念真的非常強大。例如 Cowork 也是這樣來的。我們看到過去六個月左右，很多用 Claude Code 的人根本不是拿來寫程式。Twitter 上有人用它來種番茄；有人用它分析自己的基因組；有人用它從損毀的硬碟救回照片 —— 是婚禮照片；還有人用它分析 MRI。就是一堆完全不技術的使用情境。

很明顯：人們為了做這件事不惜跳火圈去用終端機，也許我們該直接為他們做個產品。我們其實很早就看到了，大概去年五月。我記得走進辦公室，我們的資料科學家 Brendan 電腦上開著 Claude Code，就一個終端機，我超震驚：「Brendan，你在幹嘛？你居然搞懂怎麼開終端機？」那是個非常工程的產品，連很多工程師都不想用終端機，那是做事最底層的方式，真的很深入電腦的細枝末節。

而他搞懂了終端機、下載了 Node.js、下載了 Claude Code，然後在終端機裡做 SQL 分析。太瘋狂了。然後隔週所有資料科學家都在做同樣的事。

所以當你看到人們這樣「濫用」產品、用非設計用途來做對他們有用的事，那就是個非常強的指標：你該為此做個產品，而人們會喜歡那個專門用途的東西。

我想現在潛在需求還有個有趣的第二維度。傳統框架是：看人們在做什麼，讓它容易一點，賦能他們。而我過去六個月看到的現代框架有點不同：**看模型想做什麼，讓那件事容易一點**。

我們剛開始做 Claude Code 時，我想很多人設計 LLM 應用的方式是把模型放進一個盒子裡：「這是我想建的應用、這是我想做的事，模型你負責其中這一個元件，這是你跟這些工具與 API 互動的方式。」

而 Claude Code 把它反過來。我們說：**產品就是模型**。我們要把它暴露出來，在它周圍放最少的鷹架、給它最少的一組工具，讓它自己決定要跑哪些工具、以什麼順序跑。我想這很大程度上就是基於「模型想做什麼」的潛在需求。在研究上我們叫這個 on distribution（在分布上）—— 你要看模型想做什麼。用產品術語說，潛在需求就是同一個概念套用到模型上。

[`54:31`](https://youtu.be/We7BZVKbCVw?t=3271) 對。而在 Anthropic 作為一間安全實驗室，另一個維度是安全。談模型安全有好幾個層次：

最低層是對齊（alignment）與機制可解釋性（mechanistic interpretability）。我們訓練模型時要確保它安全。我們現在有相當精巧的技術去理解神經元裡發生什麼、去追蹤它。例如如果有個跟欺騙相關的神經元，我們開始能監控它、理解它正在激活。

你工作的領域真的很狂野 —— 有瘋狂的競爭與速度，同時又有「如果出問題、如果精靈跑出瓶子會造成傷害」的恐懼，要找到平衡一定很難。我聽到的是有三個層次：觀察模型的思考與運作、用測試/eval 告訴你它在做壞事、以及早點發布。第一個部分我沒聽過太多細節，那太酷了 —— 你們有可觀測性工具可以窺探模型的腦袋、看它怎麼思考、往哪走？

核心想法是：你的腦是什麼？就是一堆互相連接的神經元。在人腦或動物腦上，你可以在這種機制層次研究它、理解神經元在做什麼。結果令人意外地，很多東西也能轉譯到模型上 —— 模型神經元跟動物神經元不一樣，但在很多方面行為類似。

而且它用來做這件事的結構現在相當精巧 —— 模型變大後，不是單一神經元對應一個概念；單一神經元可能對應十幾個概念，而當它與其他神經元一起激活時（這叫疊加，superposition），它們共同表示一個更精巧的概念。這是我們一直在學習的東西。

一是**不要試著把模型框死**。我想很多人在模型上開發的直覺是試著讓它以非常特定的方式行事：「這是更大系統的一個元件。」例子包括在模型上疊很嚴格的工作流 —— 你必須做步驟一、然後步驟二、然後步驟三 —— 還有一個很花俏的編排器在管這些。但幾乎總是，如果你只是給模型工具、給它一個目標、讓它自己想辦法，結果會更好。

我想一年前你確實需要很多鷹架，但現在其實不太需要了。我不知道這個原則該叫什麼，大概是「不要問模型能為你做什麼」之類的。就想著：你要怎麼給模型工具去做事。不要過度策展它、不要把它放進盒子、不要一開始就塞一堆脈絡給它 —— 給它一個工具，讓它自己去取得需要的脈絡。你會得到更好的結果。

第二個，其實是這個原則更一般性的版本：**慘痛教訓（the bitter lesson）**。Claude Code 團隊 —— 希望聽眾讀過 —— Rich Sutton 大概十年前寫過一篇叫〈The Bitter Lesson〉的部落格文章。想法其實很簡單：更通用的模型永遠會勝過更特化的模型。對他來說他談的是自駕車之類的領域，但慘痛教訓有太多推論了。

對我來說最大的推論就是：永遠押注在更通用的模型上。長期來說，不要試著用小模型做事、不要試著 fine-tune、不要做這些事情。有些應用有理由這樣做，但幾乎總是，如果你有那個彈性，就押在更通用的模型上。

而這些工作流本質上就是「不是通用模型」—— 它是在模型外面套鷹架。我們一般看到的是：鷹架也許能提升 10%、20% 的表現，但這些增益往往會被下一個模型抹平。所以幾乎不如等下一個模型。

所以這是我給很多人、特別是做新創的人的建議。這會很不舒服，因為你的產品市場契合度在頭六個月不會很好。但如果你為六個月後的模型而建，當那個模型出來時，你會立刻上軌道，產品就會「卡嚓」一聲開始運作。

再講一本：劉慈欣的《流浪地球》。他就是寫《三體》的人，很多人因此認識他。我覺得《三體》很棒，但我其實更喜歡他的短篇。《流浪地球》是短篇集之一，裡面有些非常非常驚人的故事。而且讀中國科幻也很有意思，因為它的視角跟西方科幻非常不同，至少他作為作者思考事情的方式很不一樣。讀起來非常有趣，而且寫得很美。

科幻如何預備我們去思考事情的走向，這點很有意思 —— 它建立了心智模型，讓你覺得「我讀過這種世界」。

對，我想這其實就是我加入 Anthropic 的原因。像我說的，我當時住在鄉下，用長時間尺度思考，因為那裡一切都很慢 —— 至少相對於舊金山。你做的所有事都圍繞季節，圍繞那些要好幾個月的食物。社交活動是那樣組織的，你的時間也是那樣安排的。你去農夫市集，發現是柿子季，因為有 20 個柿子攤；下一週季節結束了，變成葡萄季。

所以就是這些長時間尺度。而我當時也讀了很多科幻。待在那個時刻，用這些長時間尺度思考，我覺得我知道這件事可能怎麼發展，我覺得我得貢獻一點讓它走得好一些。那其實就是我最後去了 Anthropic 的原因，Ben Mann 也在其中扮演很大的角色。
