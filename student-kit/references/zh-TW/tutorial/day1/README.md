# Day 1 —— 你與 Claude Code 的第一次對話

[回到 Day 0（安裝設定）](../day0/README.md)

> 英文原文：[`tutorial/day1/README.md`](https://github.com/kevin801221/claude-code-best-practice/blob/main/tutorial/day1/README.md)

---

你已經裝好 Claude Code 了。然後呢？本指南帶你走過使用它的三個層級 —— 每一層都讓你對 Claude **怎麼**做事有更多控制。

把它想成雇人：
1. **Prompting** = 在路上問陌生人怎麼走
2. **Agents** = 雇用一位總是用固定方式做事的專家
3. **Skills** = 那位專家針對特定任務受過的特定訓練

---

## 第 1 層：Prompting（直接問）

> 🧠 **把它想成**傳訊息給一個懂很多的朋友。你問「喀拉蚩天氣如何？」他們會給你*一個*答案 —— 但你不知道他們是查了天氣 App、望了一眼窗外，還是憑記憶猜的。

打開終端機輸入 `claude`。你現在在一場對話中了。試著輸入：

```
what is the weather in Karachi?
```

Claude 會回答 —— 但它**怎麼**回答是不可預測的。它可能：
- 從訓練資料裡撈（可能已過時）
- 搜尋網路（如果有網路工具）
- 給你一個籠統答案而不是即時資料

對快速提問來說這完全沒問題！但如果你需要**一致、可靠的結果**，光靠 prompt 是不夠的。

### Prompting 很好用的時候

- 問你 codebase 的問題（「這個檔案在做什麼？」）
- 寫或編輯文件（「把這封信改寫得更專業」）
- 腦力激盪（「給我 5 個這個活動的信件標題」）
- 解釋東西（「用非工程師也懂的方式解釋這個錯誤訊息」）

### 限制

每次你問「天氣如何？」，Claude 可能用不同方式抓資料 —— 或根本沒抓真實資料。沒有任何保證它兩次會用同一個來源或方法。

## 第 2 層：Agents（專家）

**代理（agent）**就是 Claude 扮演某個特定角色 —— 像是指派一個職稱。

> 🧠 **把它想成**餐廳廚房。沒有代理時，你走進隨便一間廚房大喊「做義大利麵給我！」—— 聽到的人可能煮泡麵，也可能端出五道式義式大餐。有代理時，你雇了一位**義大利麵主廚**，他的工作說明寫著：*「永遠用新鮮食材、永遠煮到彈牙、永遠用同樣方式擺盤。」* 現在你每一次都清楚知道會拿到什麼。

同樣的概念套用到 Claude：

> **沒有代理：** 你問 Claude「杜拜天氣如何？」
> 它可能查訓練資料、搜網路，或做最佳猜測。你不知道它會怎麼做。
>
> **有代理：** 一個 `weather-agent` 有明確的工作說明：
> *「永遠查 Open-Meteo API 的杜拜資料。永遠用特定格式回傳溫度。」*
> 同樣的問題、同樣的做法，每一次都一樣。

### 這個 Repo 中的真實範例

這個 repo 有一個 `weather-agent` —— 它的全部工作就是抓杜拜的溫度。它與單純 prompt 的差別：

| | Prompting | Agent |
|---|---|---|
| **來源** | 可能是任何地方 | 永遠是 Open-Meteo API |
| **地點** | Claude 隨便挑 | 永遠是杜拜（lat: 25.2, lon: 55.3） |
| **格式** | 隨機的一段文字 | 乾淨的溫度 + 單位 |
| **一致性** | 每次都不同 | 同樣的方法，每一次 |

### 重點

代理給你的是**可預測性**。同樣的問題 → 同樣的做法 → 同樣的品質。這才是優勢 —— 不是代理比較聰明，而是它們**一致**。

## 第 3 層：Skills（訓練）

**Skill** 是代理（或 Claude 自己）能使用的特定能力。

> 🧠 **把它想成**新員工的訓練手冊。有人加入你的團隊時，他們有一個角色（代理），但也要走過特定的訓練模組 —— 怎麼用 CRM、怎麼寫提案、怎麼開站立會議。每個訓練模組就是一個 **skill**。角色告訴他們*是什麼*；skills 告訴他們*怎麼*做特定的事。

再想想一個真實的人：

> **Shayan** 有很多 skill：
> - 工程 skill —— 會寫程式
> - 遊戲 skill —— 懂遊戲機制
> - 閱讀 skill —— 能消化並摘要長文件
>
> 每個 skill 有自己的知識與方法。Shayan 會為對的任務用對的 skill。

Claude 運作方式一樣。`weather-agent` 有一個叫 `weather-fetcher` 的 skill：

- **代理**（`weather-agent`）= 那個職稱是「天氣播報員」的人
- **Skill**（`weather-fetcher`）= 關於*如何*抓天氣資料的特定訓練

這個 skill 包含精確的指令：
1. 呼叫這個特定的 API URL
2. 從回應中這個特定欄位抽出溫度
3. 用這個特定格式回傳

### 為什麼要把 Agents 和 Skills 分開？

因為**一個代理可以有多個 skill**，而**一個 skill 可以被多個代理使用**。

例如，想像你建立了：
- 一個 `daily-report-agent` 摘要你的一天
- 它可以用 `weather-fetcher` skill（天氣）+ `calendar-reader` skill（會議）+ `email-summarizer` skill（信件重點）

Skills 是可重用的積木。代理是使用它們的人。

## 把全部串起來

完整圖像：

```
第 1 層：PROMPTING
你 → 「天氣如何？」 → Claude 用某種方式搞定
                       （不可預測的方法）

第 2 層：AGENTS
你 → 天氣代理 → 永遠用同樣的做法
                （可預測的方法）

第 3 層：SKILLS
你 → 天氣代理 → 使用 weather-fetcher skill
                （帶特定指令的可預測方法）
```

每一層都增加更多控制：

| 層級 | 你控制什麼 | 最適合 |
|-------|-----------------|----------|
| **Prompting** | 問題本身 | 快速的一次性提問 |
| **Agents** | 問題 + 誰來回答 | 可重複的任務 |
| **Skills** | 問題 + 誰來回答 + 他們怎麼做 | 關鍵工作流 |
