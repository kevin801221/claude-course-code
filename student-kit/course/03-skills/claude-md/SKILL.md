## 使用者輸入

```text
$ARGUMENTS
```

你**必須**先參考使用者輸入的內容（如果不是空的）再繼續。使用者可能會指定：
- `create` - 從零建立新的 CLAUDE.md
- `update` - 改善現有的 CLAUDE.md
- `audit` - 分析並回報目前 CLAUDE.md 的品質
- 要建立／更新的特定路徑（例如 `src/api/CLAUDE.md`，用於目錄專屬的指示）

## 核心原則

**LLM 是無狀態的**：CLAUDE.md 是唯一會自動納入每個對話的檔案。它是 AI 代理融入你程式碼庫的主要引導文件。

### 黃金原則

1. **少即是多**：前沿 LLM 大約能遵循 150-200 條指示。Claude Code 的系統提示詞本身就用掉約 50 條。讓你的 CLAUDE.md 保持聚焦與精簡。

2. **通用適用性**：只納入每一個工作階段（session）都會用到的資訊。特定任務的指示應該放在另外的檔案中。

3. **不要把 Claude 當 linter 用**：風格規範會讓上下文膨脹，並降低指令遵循度。改用確定性的工具（prettier、eslint 等）。

4. **絕不自動產生**：CLAUDE.md 是 AI 執行環境中槓桿效益最高的地方。要親自仔細琢磨撰寫。

## 執行流程

### 1. 專案分析

首先，分析目前的專案狀態：

1. 檢查現有的 CLAUDE.md 檔案：
   - 根目錄層級：`./CLAUDE.md` 或 `.claude/CLAUDE.md`
   - 目錄專屬：`**/CLAUDE.md`
   - 全域使用者設定：`~/.claude/CLAUDE.md`

2. 辨識專案結構：
   - 技術堆疊（語言、框架）
   - 專案類型（monorepo、單一應用程式、函式庫）
   - 開發工具（套件管理器、建置系統、測試執行器）

3. 檢視現有文件：
   - README.md
   - CONTRIBUTING.md
   - package.json、pyproject.toml、Cargo.toml 等

### 2. 內容策略（WHAT、WHY、HOW）

圍繞三個面向來組織 CLAUDE.md：

#### WHAT - 技術與結構
- 技術堆疊總覽
- 專案組織方式（對 monorepo 特別重要）
- 主要目錄及其用途

#### WHY - 目的與情境
- 這個專案做什麼
- 為什麼做出某些架構決策
- 每個主要元件負責什麼

#### HOW - 工作流程與慣例
- 開發工作流程（bun 還是 node、pip 還是 uv 等）
- 測試流程與指令
- 驗證與建置方式
- 關鍵的「眉角」或不明顯的要求

### 3. 漸進式揭露策略

對於較大的專案，建議建立一個 `agent_docs/` 資料夾：

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

在 CLAUDE.md 中，用像這樣的說明引用這些檔案：
```markdown
詳細的建置說明請參考 `agent_docs/building_the_project.md`
```

**重要**：用 `file:line` 的方式引用，而不是貼程式碼片段，以避免內容過時。

### 4. 品質限制

在建立或更新 CLAUDE.md 時：

1. **目標長度**：控制在幾百行以內；愈短愈好
2. **不放風格規則**：移除任何 linting／格式化相關的指示
3. **不放特定任務的指示**：移到獨立的檔案中
4. **不放程式碼片段**：改用檔案參照
5. **不放冗餘資訊**：不要重複 package.json 或 README 裡已經有的內容

### 5. 必要章節

一份結構完善的 CLAUDE.md 應該包含：

```markdown
# 專案名稱

一句話簡短說明。

## 技術堆疊
- 主要語言與版本
- 主要框架／函式庫
- 資料庫／儲存方式（如果有）

## 專案結構
[僅限 monorepo 或複雜結構]
- `apps/` - 應用程式進入點
- `packages/` - 共用函式庫

## 開發指令
- 安裝：`command`
- 測試：`command`
- 建置：`command`

## 關鍵慣例
[僅列出不明顯、高影響力的慣例]
- 慣例 1，附簡短說明
- 慣例 2，附簡短說明

## 已知問題／眉角
[持續會讓開發者卡關的事]
- 問題 1
- 問題 2
```

### 6. 應避免的反模式

**不要納入：**
- 程式碼風格規範（改用 linter）
- 說明如何使用 Claude 的文件
- 對顯而易見模式的冗長解釋
- 直接複製貼上的程式碼範例
- 空泛的最佳實踐（例如「寫乾淨的程式碼」）
- 特定任務的指示
- 自動產生的內容
- 大量的 TODO 清單

### 7. 驗證清單

定稿前，請確認：

- [ ] 已控制在幾百行以內；愈短愈好
- [ ] 每一行都適用於所有工作階段
- [ ] 沒有風格／格式化規則
- [ ] 沒有程式碼片段（改用檔案參照）
- [ ] 指令都已驗證可正常運作
- [ ] 較複雜的專案有用漸進式揭露
- [ ] 關鍵的眉角都有記錄下來
- [ ] 與 README.md 沒有重複內容

## 輸出格式

### 對於 `create` 或預設情況：

1. 分析專案
2. 依照上述結構起草一份 CLAUDE.md
3. 呈現草稿供審閱
4. 核准後寫入適當的位置

### 對於 `update`：

1. 讀取現有的 CLAUDE.md
2. 依最佳實踐進行稽核
3. 找出：
   - 應移除的內容（風格規則、程式碼片段、特定任務內容）
   - 應精簡的內容
   - 缺少的必要資訊
4. 呈現變更供審閱
5. 核准後套用變更

### 對於 `audit`：

1. 讀取現有的 CLAUDE.md
2. 產生一份報告，內容包含：
   - 目前行數與目標行數的比較
   - 通用適用內容所佔的比例
   - 找到的反模式清單
   - 改善建議
3. 不要修改檔案，只回報結果

## AGENTS.md 的處理方式

如果使用者要求建立／更新 AGENTS.md：

**Claude Code 不會直接讀取 AGENTS.md**。要讓它生效，得透過 `@AGENTS.md` 從 CLAUDE.md 匯入，或把 `CLAUDE.md` 建立成指向它的 symlink。這是關於這個檔案最常見的誤解。

AGENTS.md 是一個跨工具的專案情境檔案——和 CLAUDE.md 屬於同一*類別*的文件，而不是代理定義格式。它的存在是為了讓多個 coding agent 共用同一套專案慣例：
- 建置、測試、lint 指令
- 程式碼風格與架構慣例
- 儲存庫結構與各項內容的所在位置

子代理（Subagents）是在 `.claude/agents/*.md` 中另外定義的——不是在 AGENTS.md 裡。

套用類似的原則：
- 保持聚焦與精簡
- 使用漸進式揭露
- 引用外部文件，而不是把內容直接嵌進來

## 備註

- 納入指令前，務必先驗證它們真的能用
- 有疑慮時就不要放進去——少即是多
- 系統提醒會告訴 Claude，CLAUDE.md「可能相關，也可能不相關」——雜訊越多，就越容易被忽略
- Monorepo 從清楚的 WHAT/WHY/HOW 結構中獲益最多
- 目錄專屬的 CLAUDE.md 檔案應該更加聚焦
