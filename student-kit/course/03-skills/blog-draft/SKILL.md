## 使用者輸入

```text
$ARGUMENTS
```

你**必須**先參考使用者輸入的內容再繼續。使用者應該要提供：
- **構想／主題**：部落格文章的主要概念或主題
- **資料來源**：要研究的網址、檔案或參考資料（非必要但建議提供）
- **目標讀者**：這篇部落格文章是寫給誰看的（非必要）
- **語氣／風格**：正式、輕鬆、技術性等（非必要）

**重要**：如果使用者是要求更新**現有的部落格文章**，請跳過步驟 0-8，直接從**步驟 9** 開始。先讀取現有的草稿檔案，再進行反覆修改流程。

## 執行流程

依序執行以下步驟。**不要跳過步驟，也不要在需要使用者核准的地方未經核准就繼續。**

### 步驟 0：建立專案資料夾

1. 用 `YYYY-MM-DD-short-topic-name` 的格式產生資料夾名稱
   - 使用今天的日期
   - 從主題產生簡短、適合放進網址的 slug（小寫、連字號、最多 5 個字）

2. 建立資料夾結構：
   ```
   blog-posts/
   └── YYYY-MM-DD-short-topic-name/
       └── resources/
   ```

3. 在繼續之前，先跟使用者確認資料夾已建立。

### 步驟 1：研究與資料蒐集

1. 在部落格文章目錄中建立 `resources/` 子資料夾

2. 針對每個提供的資料來源：
   - **網址**：擷取關鍵資訊並以 Markdown 檔案存到 `resources/`
   - **檔案**：讀取並在 `resources/` 中摘要
   - **主題**：用網路搜尋蒐集最新資訊

3. 針對每個資料來源，在 `resources/` 中建立一份摘要檔案：
   - `resources/source-1-[short-name].md`
   - `resources/source-2-[short-name].md`
   - 依此類推

4. 每份摘要都應包含：
   ```markdown
   # 資料來源：[標題／網址]

   ## 重點
   - 重點 1
   - 重點 2

   ## 相關引言／數據
   - 引言或統計數據 1
   - 引言或統計數據 2

   ## 與主題的關聯
   簡短說明其相關性
   ```

5. 將研究摘要呈現給使用者。

### 步驟 2：腦力激盪與釐清

1. 根據構想與研究到的資料，提出：
   - 從研究中歸納出的**主要主題**
   - 這篇文章可能的**切入角度**
   - 應該涵蓋的**重點**
   - 需要釐清的**資訊缺口**

2. 提出釐清問題：
   - 你希望讀者讀完後得到的主要收穫是什麼？
   - 有沒有研究中特別想強調的重點？
   - 目標長度是多少？（短：500-800 字；中：1000-1500 字；長：2000 字以上）
   - 有沒有想排除的內容？

3. **等待使用者回應後再繼續。**

### 步驟 3：提出大綱

1. 建立包含以下內容的結構化大綱：

   ```markdown
   # 部落格文章大綱：[標題]

   ## 基本資訊
   - **目標讀者**：[對象]
   - **語氣**：[風格]
   - **目標長度**：[字數]
   - **主要收穫**：[核心訊息]

   ## 建議結構

   ### 開場／引言
   - 開場鉤子構想
   - 情境鋪陳
   - 論點陳述

   ### 第 1 節：[標題]
   - 重點 A
   - 重點 B
   - 來自 [資料來源] 的佐證

   ### 第 2 節：[標題]
   - 重點 A
   - 重點 B

   [依需要繼續列出其他小節……]

   ### 結論
   - 重點總結
   - 行動呼籲或結尾感想

   ## 需引用的資料來源
   - 資料來源 1
   - 資料來源 2
   ```

2. 把大綱呈現給使用者，**請對方核准或提出修改意見**。

### 步驟 4：儲存已核准的大綱

1. 使用者核准大綱後，將其存成部落格文章資料夾中的 `OUTLINE.md`。

2. 向使用者確認大綱已儲存。

### 步驟 5：提交大綱（如果在 git 儲存庫中）

1. 檢查目前目錄是否為 git 儲存庫。

2. 若是：
   - 加入暫存區：部落格文章資料夾、資料來源檔案與 `OUTLINE.md`
   - 建立提交，訊息為：`docs: Add outline for blog post - [topic-name]`
   - 推送到遠端

3. 若不是 git 儲存庫，跳過此步驟並告知使用者。

### 步驟 6：撰寫草稿

1. 根據已核准的大綱，撰寫完整的部落格文章草稿。

2. 完全依照 `OUTLINE.md` 的結構撰寫。

3. 內容須包含：
   - 有吸引力的開場與鉤子
   - 清楚的小節標題
   - 來自研究的佐證與範例
   - 段落之間流暢的轉折
   - 有力的結論與收穫總結
   - **引用**：所有比較、統計數據、資料點與事實陳述都**必須**引用原始出處

4. 將草稿存成部落格文章資料夾中的 `draft-v0.1.md`。

5. 格式：
   ```markdown
   # [部落格文章標題]

   *[選填：副標題或標語]*

   [完整內容，含行內引用……]

   ---

   ## 參考資料
   - [1] 資料來源 1 標題 - 網址或引用出處
   - [2] 資料來源 2 標題 - 網址或引用出處
   - [3] 資料來源 3 標題 - 網址或引用出處
   ```

6. **引用要求**：
   - 每個資料點、統計數據或比較都**必須**附行內引用
   - 使用編號引用 [1]、[2] 等，或具名引用 [資料來源名稱]
   - 將引用連結到文末的參考資料區
   - 範例：「研究顯示，65% 的開發者偏好 TypeScript [1]」
   - 範例：「React 的渲染速度比 Vue 快 20%[React Benchmarks 2024]」

### 步驟 7：提交草稿（如果在 git 儲存庫中）

1. 檢查是否在 git 儲存庫中。

2. 若是：
   - 加入草稿檔到暫存區
   - 建立提交，訊息為：`docs: Add draft v0.1 for blog post - [topic-name]`
   - 推送到遠端

3. 若不是 git 儲存庫，跳過並告知使用者。

### 步驟 8：呈現草稿供審閱

1. 把草稿內容呈現給使用者。

2. 請對方回饋：
   - 整體印象如何？
   - 哪些段落需要擴充或精簡？
   - 需要調整語氣嗎？
   - 有沒有缺漏的資訊？
   - 有沒有具體的修改或改寫需求？

3. **等待使用者回應。**

### 步驟 9：反覆修改或定稿

**如果使用者要求修改：**
1. 記下所有要求的修改
2. 回到步驟 6，並做以下調整：
   - 遞增版本號（v0.2、v0.3 等）
   - 納入所有回饋
   - 存成 `draft-v[X.Y].md`
   - 重複步驟 7-8

**如果使用者核准：**
1. 確認最終草稿版本
2. 若使用者要求，可選擇改名為 `final.md`
3. 總結整個部落格文章的建立過程：
   - 總共建立了幾個版本
   - 各版本之間的關鍵變化
   - 最終字數
   - 建立的檔案清單

## 版本追蹤

所有草稿都會以遞增版號保留：
- `draft-v0.1.md` - 初始草稿
- `draft-v0.2.md` - 第一輪回饋後
- `draft-v0.3.md` - 第二輪回饋後
- 依此類推

這樣可以追蹤部落格文章的演進過程，也方便在需要時還原到之前的版本。

## 輸出檔案結構

```
blog-posts/
└── YYYY-MM-DD-topic-name/
    ├── resources/
    │   ├── source-1-name.md
    │   ├── source-2-name.md
    │   └── ...
    ├── OUTLINE.md
    ├── draft-v0.1.md
    ├── draft-v0.2.md（若有反覆修改）
    └── draft-v0.3.md（若有更多次修改）
```

## 品質小訣竅

- **鉤子**：以問題、令人意外的事實，或有共鳴的情境開場
- **流暢度**：每個段落都要能銜接到下一段
- **佐證**：用研究資料支持論點
- **引用**：務必為以下內容附上出處：
  - 所有統計數據與資料點（例如：「根據 [資料來源]，75% 的……」）
  - 產品、服務或做法之間的比較（例如：「X 比 Y 快 2 倍 [資料來源]」）
  - 有關市場趨勢、研究結果或基準測試的事實陳述
  - 使用行內引用格式：[資料來源名稱] 或 [作者、年份]
- **語調**：全文維持一致的語氣
- **長度**：符合目標字數
- **易讀性**：段落簡短，適當使用條列
- **CTA**：以明確的行動呼籲或發人深省的問題作結

## 備註

- 在標出的檢查點（Checkpoints）務必等待使用者核准
- 保留所有草稿版本以供追溯
- 提供網址時，使用網路搜尋取得最新資訊
- 若資料來源不足，向使用者詢問更多資料，或建議額外的研究方向
- 依目標讀者調整語氣（技術性、一般性、商業性等）
