# LLM Wiki

一種用 LLM 建立個人知識庫的模式。

這是一份**理念文件**，設計來複製貼上給你的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode/Pi 等）。它的目標是傳達高層次的概念，至於具體實作會由你的 agent 跟你協作建構出來。

---

## 核心理念

多數人接觸 LLM 與文件的方式是 RAG：上傳一堆檔案，提問時讓 LLM 撈相關片段、生成答案。這個方式行得通，但 LLM 在每次提問時都是**從零開始重新發現知識**。沒有任何累積。問一個微妙、需要綜合 5 份文件才能回答的問題，LLM 每次都要重新撈片段、重新拼湊。什麼都沒被建立起來。NotebookLM、ChatGPT 上傳檔案、大多數 RAG 系統都是這個運作方式。

這份文件提出的想法**不一樣**。與其在 query 時才從原始文件撈內容，不如讓 LLM **逐步建構並維護一個持續存在的 wiki**——一個由 markdown 檔案組成、有結構、彼此互相連結的知識庫，介於你和原始來源之間。當你新增一份來源時，LLM 不只是把它索引起來等以後檢索；它會**閱讀那份來源、提取關鍵資訊、整合進現有的 wiki**——更新實體頁面、修訂主題摘要、標記新資料與舊論點的衝突、強化或挑戰逐漸演進的綜合分析。**知識被編譯一次，然後持續維護更新**，而不是每次 query 都重新推導一次。

這就是關鍵差異：**wiki 是一個會持續複利累積的工件**。交叉引用早就在那裡了。矛盾早就被標記了。綜合分析已經反映了你讀過的一切。Wiki 隨著你新增每一份來源、問出每一個問題，而越長越豐富。

你（幾乎）不會親手寫 wiki——LLM 會寫並維護所有內容。你負責的是：**找來源、做探索、問對問題**。LLM 負責所有雜事——摘要、交叉引用、歸檔、簿記，這些是讓知識庫真正有用的工作，但人類維護起來會崩潰。在實務上，我會一邊開著 LLM agent、一邊開著編輯器（VSCode、Cursor、Antigravity 都行——任何能即時預覽 markdown、有檔案總管的工具）。LLM 根據對話編輯內容，我即時瀏覽結果——在側邊欄點 markdown 檔案、順著 wiki link 跳到相關頁面（VSCode 裝個 markdown 擴充就能 cmd+click 跳）、看更新後的頁面、用 `git diff` 看哪裡被改了。**編輯器是 IDE，LLM 是程式員，wiki 是 codebase。**

這個模式可以套用到很多情境，舉幾個例子：

- **個人**：追蹤自己的目標、健康、心理、自我成長——歸檔日記、文章、podcast 筆記，慢慢建立關於自己的結構化全貌。
- **研究**：在某個主題上深耕數週數月——讀 paper、文章、報告，並逐步建構一份完整的 wiki，論點隨著閱讀演化。
- **讀一本書**：每讀一章就歸檔一次，建立角色、主題、情節線、彼此連結的頁面。讀完整本書時，你就有了一份豐富的伴讀 wiki。想想看 Tolkien Gateway 這種書迷 wiki——上千個彼此連結的頁面涵蓋角色、地點、事件、語言，是一群志工花了好幾年累積出來的。你也可以一邊讀書、一邊靠 LLM 做交叉引用與維護，個人也能建出那種 wiki。
- **業務／團隊**：由 LLM 維護的內部 wiki，餵給它 Slack 對話、會議逐字稿、專案文件、客戶通話。可以人類在迴圈中審核更新。Wiki 持續最新，因為 LLM 做了沒人想做的維護工作。
- **競品分析、盡職調查、旅行規劃、課程筆記、興趣鑽研**——任何「你會隨時間累積知識並希望它被組織而非散落」的場景。

## 架構

有三層：

**原始來源（Raw sources）**——你精選的來源文件集合。文章、論文、圖片、資料檔。這層**不可修改**——LLM 只讀取，永不寫入。這是你的事實源頭（source of truth）。

**Wiki**——一個由 LLM 生成的 markdown 檔案目錄。摘要、實體頁面、概念頁面、比較分析、總覽、綜合論點。這層完全由 LLM 擁有。它建立頁面、在新來源到達時更新它們、維護交叉引用、保持整體一致性。**你讀，LLM 寫**。

**Schema**——一份說明文件（例如給 Claude Code 的 `CLAUDE.md`、給 Codex 的 `AGENTS.md`），告訴 LLM 這份 wiki 的結構、約定俗成的慣例、以及在 ingest、查詢、維護 wiki 時要遵守的工作流程。這是**關鍵設定檔**——它讓 LLM 變成一個有紀律的 wiki 維護者，而不是一個泛用聊天機器人。你跟 LLM 會隨著時間共同演化這份 schema，慢慢摸索出最適合你領域的做法。

---

## 操作

**Ingest（載入）**。你把新來源放進 raw 目錄，告訴 LLM 處理它。一個範例流程：LLM 讀取來源、跟你討論關鍵重點、在 wiki 寫一頁摘要、更新索引、更新 wiki 中相關的實體與概念頁面、在 log 加入一筆紀錄。**一份來源可能會碰到 10–15 個 wiki 頁面。** 我個人偏好一次 ingest 一份，全程參與——讀摘要、檢查更新、引導 LLM 強調哪些重點。但你也可以一次批次 ingest 多份、放手讓 LLM 自己跑。發展出適合你風格的工作流，並把它記在 schema 裡留給未來的 session 參考。

**Query（查詢）**。你對 wiki 提問。LLM 搜尋相關頁面、讀取它們、綜合出帶引用的回答。回答可以是不同形式——markdown 頁面、比較表、Marp 簡報、matplotlib 圖表、canvas。**關鍵洞察**：好的回答可以被歸檔回 wiki 變成新頁面。一份你要的比較、一個分析、一個你發現的連結——這些有價值的東西不該消失在對話記錄裡。如此一來你的探索也會像 ingest 進來的來源一樣，在知識庫裡複利累積。

**Lint（健檢）**。定期請 LLM 對 wiki 做健康檢查。找出：頁面之間的矛盾、被新來源推翻但未更新的舊論點、沒有任何反向連結的孤立頁面、被多次提及但沒有自己頁面的重要概念、缺失的交叉引用、可以靠網路搜尋補上的資料缺口。LLM 很擅長建議「下一個該調查的問題」與「該找的新來源」。這讓 wiki 在成長過程中保持健康。

## 索引與日誌

兩個特殊檔案幫助 LLM（以及你）導航逐漸變大的 wiki，它們各有用途：

**`index.md`** 是**內容導向**的。它是整個 wiki 的目錄——每一頁都有連結、一行摘要、選用的元資料（日期、來源數量等），按類別組織（entities、concepts、sources 等）。LLM 在每次 ingest 時都會更新它。回答 query 時 LLM 會先讀 index 找出相關頁面，再深入。**這在中等規模（約 100 份來源、數百個頁面）已經夠用了**，免去 embedding-based RAG 的基礎建設。

**`log.md`** 是**時序導向**的。它是 append-only 的紀錄——ingest、query、lint 何時發生了什麼。**小撇步**：如果每筆紀錄都用一致的開頭（例如 `## [2026-04-02] ingest | 文章標題`），這份 log 就能用簡單的 unix 工具解析——`grep "^## \[" log.md | tail -5` 就能拿到最近 5 筆。Log 給你 wiki 的演化時間軸，也幫 LLM 了解最近做了什麼。

## 選用：CLI 工具

某個時間點你會想做小工具讓 LLM 操作 wiki 更有效率。最明顯的是 wiki 頁面的搜尋引擎——小規模時 index 檔已經夠了，但 wiki 變大後就需要正規搜尋。

**qmd** 是個不錯的選擇：本地 markdown 檔案的混合搜尋（BM25 + 向量）+ LLM rerank，全部在裝置上跑。它有 CLI（LLM 可以 shell 呼叫）也有 MCP server（LLM 可以當原生工具用）。

你也可以自己做更簡單的——LLM 可以幫你 vibe-code 一個土炮搜尋 script，看需要而定。

## Tips & Tricks

- **把網路文章轉 markdown**：用 [MarkDownload](https://github.com/deathau/markdownload) 這類瀏覽器擴充，把網頁一鍵存成 markdown 直接丟進 `raw/`。要批次或自動化的話用 [single-file-cli](https://github.com/gildas-lormeau/single-file-cli)、[monolith](https://github.com/Y2Z/monolith)，或 Firecrawl / Reader API 之類的服務。
- **本地下載圖片**。clip 文章時連圖片一起抓下來放 `raw/assets/`，這樣 LLM 可以直接看與引用，不用依賴可能會壞掉的 URL。`monolith` 會把整頁打包成單檔（含圖）；或請 LLM 寫個小 script 掃 markdown 把所有 image URL 下載到本地、改寫成相對路徑。注意：LLM 沒辦法一次讀「帶圖 markdown」的全部——變通方式是先讓 LLM 讀文字，再單獨「看」幾張關鍵圖補脈絡。
- **看 wiki 的形狀**：你會想看到「什麼連到什麼、哪些頁面是樞紐、哪些是孤立節點」。用 [markmap](https://markmap.js.org/) 把 markdown 轉成互動 mind map（CLI / VSCode 擴充都有）；或在 `index.md` 用 mermaid `graph TD` 畫頁面關係（GitHub、VSCode、大多 markdown viewer 都直接渲染）；或單純跑 `tree wiki/` 看目錄結構。LLM 可以幫你定期掃 wiki，自動產出 mermaid 圖、列出反向連結為 0 的孤兒頁面、標出 inbound link 最多的樞紐頁，更新到 `index.md`。
- **Marp** 是基於 markdown 的投影片格式，VSCode 有 Marp 擴充可以即時預覽、輸出 PDF / HTML / PPTX。可以從 wiki 內容直接生成簡報。
- **Frontmatter + 小 script 取代 Dataview**：給每個 wiki 頁面加 YAML frontmatter（`tags`、`date`、`source_count` 等），請 LLM 寫一個 Python script 用 `python-frontmatter` 套件掃整個 wiki，動態產出「最近更新」「孤立頁面」「按 tag 分類」等清單。比 Dataview 通用——不綁特定編輯器、輸出可以直接 commit 進 repo。
- **Wiki 就是一個 git repo 的 markdown 檔案集合**。版本歷史、分支、協作——全部免費。`git log --since`、`git blame` 還能當「這個事實是什麼時候加進來的、來自哪份來源」的查詢工具。

## 為什麼這個模式行得通

維護知識庫的辛苦不在「讀」或「想」——在於**簿記**。更新交叉引用、保持摘要最新、標記新資料推翻舊論點之處、跨數十個頁面維持一致性。人類會放棄 wiki，因為**維護成本成長得比價值還快**。LLM 不會無聊、不會忘記更新交叉引用、可以一次碰 15 個檔案。**Wiki 能持續被維護，是因為維護成本接近零。**

人類的工作是：**精選來源、引導分析、問好問題、思考意義**。
LLM 的工作是：**其他所有事**。

這個概念精神上跟 Vannevar Bush 的 Memex（1945）類似——個人的、精選的知識儲存，文件之間有「聯想軌跡」連結。Bush 的願景比現在的網路更接近這個——私密、主動策展、文件之間的連結與文件本身一樣有價值。他沒能解決的部分是：誰來做維護？**LLM 來做。**

## 註記

這份文件**故意保持抽象**。它描述的是**模式**，不是某個具體實作。確切的目錄結構、schema 慣例、頁面格式、工具——這些都會依你的領域、你的偏好、你選的 LLM 而異。上面提到的一切都是**選用且模組化**的——挑有用的用，沒用的略過。例如：你的來源可能只有純文字，那就不需要圖片處理；你的 wiki 可能小到只需 index 檔，不用搜尋引擎；你可能不在乎簡報，只想要 markdown 頁面；你可能想要完全不同的輸出格式集合。

**正確的用法**：把這份文件分享給你的 LLM agent，跟它一起為你的需求**實例化出一個版本**。這份文件唯一的工作是**傳達模式**，剩下的你的 LLM 會搞定。
