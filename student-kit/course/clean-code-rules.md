# AI 程式碼生成的簡潔程式碼規則

這些規則引導程式碼生成，產出可維護、專業水準的程式碼。

## 有意義的命名
- 使用能揭露意圖的名稱，說明某個東西為什麼存在
- 避免誤導性資訊與無意義的區分（例如 `data`、`info`、`manager`）
- 使用可唸出、可搜尋的名稱
- 類別名稱：使用名詞（例如 `UserAccount`、`PaymentProcessor`）
- 方法名稱：使用動詞（例如 `calculateTotal`、`sendEmail`）
- 避免心理對應與編碼（匈牙利命名法、前綴）

## 函式
- 讓函式保持精簡（理想情況下少於 20 行）
- 只做一件事——單一職責原則
- 每個函式只維持一個抽象層級
- 限制參數數量：理想為 0 到 2 個，最多 3 個，避免旗標參數
- 沒有副作用——函式應該做到名稱所說的事
- 將指令（改變狀態）與查詢（回傳資訊）分開
- 優先使用例外，而非錯誤碼

## 註解
- 程式碼應該自我說明——盡可能避免使用註解
- 好的註解：法律資訊、警告、TODO、公開 API 文件
- 不好的註解：多餘、誤導，或用來解釋糟糕的程式碼
- 不要把程式碼註解掉——直接刪除（版本控制會保留歷史紀錄）
- 如果需要寫註解，考慮改為重構程式碼

## 格式化
- 保持檔案精簡且聚焦
- 垂直格式：相關概念放在一起，用空行區隔不同概念
- 水平格式：限制行長（80 到 120 個字元）
- 使用一致的縮排與團隊風格
- 將相關函式群組在一起

## 物件與資料結構
- 物件：把資料隱藏在抽象之後，透過方法公開行為
- 資料結構：公開資料，行為極少
- 迪米特法則：只與直接的朋友溝通，避免 `a.getB().getC().doSomething()` 這種寫法
- 不要盲目地透過 getter/setter 公開內部結構

## 錯誤處理
- 使用例外，而非回傳碼或錯誤旗標
- 當程式碼可能失敗時，先寫好 `try-catch-finally`
- 在例外訊息中提供上下文
- 不要回傳 `null`——回傳空集合，或使用 Optional/Maybe
- 不要把 `null` 當作參數傳入

## 類別
- 小型類別：以職責衡量，而非行數
- 單一職責原則：只有一個改變的理由
- 高內聚：類別變數被多個方法使用
- 低耦合：類別之間的相依性降到最低
- 開放封閉原則：對擴充開放，對修改封閉

## 單元測試
- 快速、獨立、可重複、能自我驗證、即時（F.I.R.S.T.）
- 每個測試一個斷言（或一個概念）
- 測試程式碼的品質應等同於正式程式碼
- 可讀的測試名稱，說明測試的內容
- Arrange-Act-Assert 模式

## 程式碼品質原則
- **DRY（不要重複自己）**：不要重複
- **YAGNI（你不會需要它）**：不要為了假設的未來而建置
- **KISS（保持簡單）**：避免不必要的複雜度
- **童子軍法則**：讓程式碼比你發現時更乾淨

## 應避免的程式碼異味
- 過長的函式或類別
- 重複的程式碼
- 死程式碼（未使用的變數、函式、參數）
- 特性依戀（方法對其他類別的興趣更高）
- 不當親密（類別之間互相知道太多）
- 過長的參數列表
- 基本型別偏執（過度使用基本型別而非小型物件）
- Switch/case 敘述（考慮改用多型）
- 暫時性欄位（只在部分情況下使用的類別變數）

## 並行處理
- 讓並行程式碼與其他程式碼分開
- 限制同步／鎖定資料的範圍
- 使用執行緒安全的集合
- 讓同步區塊保持精簡
- 熟悉你使用的執行模型與基礎元件

## 系統設計
- 將建構與使用分開（依賴注入）
- 使用工廠、建構器來建立複雜物件
- 針對介面撰寫程式，而不是針對實作
- 優先使用組合而非繼承
- 只在能簡化問題時套用設計模式，而不是為了炫技

## 重構
- 持續重構，而非一次大改
- 重構前後都要確保測試通過
- 小步前進：一次只改一件事
- 常見重構手法：Extract Method（抽取方法）、Rename（重新命名）、Move（搬移）、Inline（內聯）

## 文件
- 自我說明的程式碼 > 註解 > 外部文件
- 公開 API 需要清楚的文件
- 在文件中附上範例
- 讓文件與程式碼保持接近（理想情況下直接寫在程式碼中）

---

**核心理念**：程式碼被閱讀的次數是被撰寫次數的 10 倍。以可讀性與可維護性為最佳化目標，而不是炫技。
