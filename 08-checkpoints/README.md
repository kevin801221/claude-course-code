# 檢查點與回溯（Checkpoints and Rewind）

檢查點（Checkpoints）能讓你儲存對話狀態，並回溯到 Claude Code 工作階段（session）中先前的時間點。這在探索不同做法、從錯誤中復原，或比較替代方案時非常有價值。

## 總覽

檢查點能讓你儲存對話狀態並回溯到先前的時間點，讓你能安全地實驗並探索多種做法。它們是對話狀態的快照，包含：
- 所有交換過的訊息
- 所做的檔案修改
- 工具使用紀錄
- 工作階段上下文

在探索不同做法、從錯誤中復原，或比較替代方案時，檢查點非常有價值。

## 核心概念

| 概念 | 說明 |
|---------|-------------|
| **檢查點（Checkpoint）** | 對話狀態的快照，包含訊息、檔案與上下文 |
| **回溯（Rewind）** | 回到先前的檢查點，捨棄之後的變更 |
| **分支點（Branch Point）** | 用來探索多種做法的檢查點 |

## 存取檢查點

你可以透過兩種主要方式存取與管理檢查點：

### 使用鍵盤快捷鍵
按兩次 `Esc`（`Esc` + `Esc`）即可開啟檢查點介面，瀏覽已儲存的檢查點。

### 使用斜線指令
使用 `/rewind` 指令（別名：`/checkpoint`）可快速存取：

```bash
# 開啟回溯介面
/rewind

# 或使用別名
/checkpoint
```

## 回溯選項

回溯時，會出現包含六個選項的選單：

1. **還原程式碼與對話**——將檔案與訊息都還原到該檢查點
2. **還原對話**——只回溯訊息，保留目前的程式碼不變
3. **還原程式碼**——只還原檔案變更，保留完整的對話歷史
4. **從這裡開始摘要**——將從這個時間點開始的對話壓縮（compact）成 AI 產生的摘要，釋放上下文視窗空間。所選時間點之前的訊息維持不變。硬碟上的檔案不會被更動。原始訊息會保留在工作階段逐字稿中。你可以選擇提供指示，讓摘要聚焦在特定主題上。
5. **摘要到這裡為止**——反向的做法：將所選時間點*之前*的所有內容壓縮成 AI 產生的摘要，並保留這個時間點之後的訊息不變。搭配「從這裡開始摘要」，就能對上下文視窗進行雙向、有針對性的壓縮。硬碟上的檔案不會被更動，原始訊息會保留在工作階段逐字稿中。
6. **算了**——取消並回到目前狀態

> **備註**：還原對話或摘要之後，所選訊息的原始提示詞會被還原到輸入欄位中，方便你重新傳送或編輯。

> **`/clear` 不再是硬性邊界（v2.1.191+）**：`/rewind` 可以從你執行 `/clear` *之前*所建立的檢查點繼續。清除對話不再會永久捨棄之前的狀態——如果你需要更早的程式碼或上下文，可以回溯到清除之前。

## 自動檢查點

Claude Code 會自動為你建立檢查點：

- **每一次使用者提示** - 每次使用者輸入都會建立一個新的檢查點
- **持久保存** - 檢查點會跨工作階段保留
- **自動清除** - 檢查點會在 30 天後自動清除

這代表你隨時都能回溯到對話中先前的任何時間點，不論是幾分鐘前還是幾天前。

## 使用情境

| 情境 | 工作流程 |
|----------|----------|
| **探索不同做法** | 儲存 → 嘗試 A → 儲存 → 回溯 → 嘗試 B → 比較 |
| **安全重構** | 儲存 → 重構 → 測試 → 若失敗：回溯 |
| **A/B 測試** | 儲存 → 設計 A → 儲存 → 回溯 → 設計 B → 比較 |
| **錯誤復原** | 發現問題 → 回溯到最後一個正常狀態 |

## 使用檢查點

### 檢視與回溯

按兩次 `Esc` 或使用 `/rewind` 即可開啟檢查點瀏覽器。你會看到所有可用檢查點的清單，附帶時間戳記。選取任一檢查點即可回溯到該狀態。

### 檢查點詳細資訊

每個檢查點都會顯示：
- 建立時的時間戳記
- 被修改的檔案
- 對話中的訊息數量
- 使用過的工具

## 實際範例

### 範例 1：探索不同做法

```
User: 我們幫 API 加一層快取吧

Claude: 我會為你的 API 端點加上 Redis 快取……
[在檢查點 A 進行變更]

User: 其實，我們改用記憶體內快取試試看

Claude: 我會回溯來探索不同的做法……
[使用者按下 Esc+Esc，回溯到檢查點 A]
[在檢查點 B 實作記憶體內快取]

User: 現在我可以比較這兩種做法了
```

### 範例 2：從錯誤中復原

```
User: 把驗證模組重構成使用 JWT

Claude: 我會重構驗證模組……
[進行大量變更]

User: 等等，這樣把 OAuth 整合弄壞了，我們回去吧

Claude: 我來幫你回溯到重構之前的狀態……
[使用者按下 Esc+Esc，選擇重構之前的檢查點]

User: 這次我們試試更保守一點的做法
```

### 範例 3：安全實驗

```
User: 我們試試用函式化風格重寫這段程式碼
[在實驗前建立檢查點]

Claude: [進行實驗性變更]

User: 測試失敗了，我們回溯吧
[使用者按下 Esc+Esc，回溯到該檢查點]

Claude: 我已經把變更回溯掉了，我們試試別的做法。
```

### 範例 4：分支做法

```
User: 我想比較兩種資料庫設計
[記下這個檢查點——稱它為「起點」]

Claude: 我來建立第一種設計……
[實作 Schema A]

User: 現在讓我回去試試第二種做法
[使用者按下 Esc+Esc，回溯到「起點」]

Claude: 現在我來實作 Schema B……
[實作 Schema B]

User: 太好了！現在我有兩種結構可以選了
```

## 檢查點保留機制

Claude Code 會自動管理你的檢查點：

- 檢查點會隨每次使用者提示自動建立
- 舊的檢查點最多保留 30 天
- 檢查點會自動清除，避免儲存空間無限成長

## 工作流程模式

### 探索用的分支策略

探索多種做法時：

```
1. 從初始實作開始 → 檢查點 A
2. 嘗試做法 1 → 檢查點 B
3. 回溯到檢查點 A
4. 嘗試做法 2 → 檢查點 C
5. 比較 B 與 C 的結果
6. 選擇最佳做法並繼續
```

### 安全重構模式

進行重大變更時：

```
1. 目前狀態 → 檢查點（自動）
2. 開始重構
3. 執行測試
4. 若測試通過 → 繼續工作
5. 若測試失敗 → 回溯並嘗試不同做法
```

## 最佳實踐

由於檢查點是自動建立的，你可以專注於工作，不必擔心手動儲存狀態。不過，請留意以下做法：

### 有效使用檢查點

✅ **建議做法：**
- 回溯前先檢視可用的檢查點
- 想探索不同方向時使用回溯
- 保留檢查點以便比較不同做法
- 了解每個回溯選項的作用（還原程式碼與對話、還原對話、還原程式碼，或摘要）

❌ **避免做法：**
- 只靠檢查點來保存程式碼
- 期待檢查點能追蹤外部檔案系統的變更
- 把檢查點當成 git commit 的替代品

## 設定

檢查點是 Claude Code 內建的預設行為，不需要任何設定即可啟用。每次使用者提示都會自動建立一個檢查點。

有兩個設定會影響檢查點行為——是否要拍攝快照，以及要保留多久：

```json
{
  "fileCheckpointingEnabled": true,
  "cleanupPeriodDays": 30
}
```

| 設定 | 預設值 | 效果 |
|---------|---------|--------|
| `fileCheckpointingEnabled` | `true` | 在每次編輯前為檔案拍攝快照，讓 `/rewind` 可以還原。需要 v2.1.119+。在 `/config` 中顯示為 **Rewind code (checkpoints)**。對應的環境變數：`CLAUDE_CODE_DISABLE_FILE_CHECKPOINTING` |
| `cleanupPeriodDays` | `30` | 保留工作階段歷史與檢查點的天數 |

Claude Code 只會保留**最近 100 個檢查點**的快照；即使還在保留期限內，更舊的也會被捨棄。

> **v2.1.117 更新**：`cleanupPeriodDays` 現在不只管理檢查點的保留，還會管理四種硬碟快取：
>
> - 工作階段檢查點
> - `~/.claude/tasks/` — 持久化任務清單
> - `~/.claude/shell-snapshots/` — 擷取的 shell 環境快照
> - `~/.claude/backups/` — 滾動式設定／CLAUDE.md 備份
>
> 現在只要一個設定，就能在相同天數後統一清理這四個目錄。

## 限制

檢查點有以下限制：

- **不追蹤 Bash 指令造成的變更** - 像 `rm`、`mv`、`cp` 這類檔案系統操作不會被檢查點記錄
- **不追蹤外部變更** - 在 Claude Code 之外（例如編輯器、終端機等）所做的變更不會被記錄
- **不能取代版本控制** - 程式碼的永久、可稽核變更請使用 git

> **v2.1.216 更新**：`/rewind` 不再透過受追蹤路徑上的符號連結或硬連結來還原或刪除檔案。如果受追蹤的路徑是透過符號連結或硬連結解析的，回溯會跳過它而不是跟隨連結，並回報因此跳過了多少個路徑。

## 疑難排解

### 找不到檢查點

**問題**：找不到預期的檢查點

**解決方法**：
- 檢查檢查點是否已被清除
- 檢查磁碟空間
- 確認 `cleanupPeriodDays` 設定得夠高（預設：30 天）

### 回溯失敗

**問題**：無法回溯到檢查點

**解決方法**：
- 確認沒有未提交的變更造成衝突
- 檢查檢查點是否損毀
- 嘗試回溯到其他檢查點

## 與 Git 整合

檢查點是 git 的補充（而非取代）：

| 功能 | Git | 檢查點 |
|---------|-----|-------------|
| 範圍 | 檔案系統 | 對話 + 檔案 |
| 持久性 | 永久 | 以工作階段為準 |
| 粒度 | Commit | 任意時間點 |
| 速度 | 較慢 | 即時 |
| 可分享 | 可以 | 有限 |

兩者搭配使用：
1. 用檢查點進行快速實驗
2. 用 git commit 記錄定案的變更
3. 在 git 操作前建立檢查點
4. 把成功的檢查點狀態提交到 git

## 快速開始指南

### 基本工作流程

1. **正常工作** - Claude Code 會自動建立檢查點
2. **想要回去？** - 按兩次 `Esc` 或使用 `/rewind`
3. **選擇檢查點** - 從清單中選取要回溯的檢查點
4. **選擇要還原的內容** - 從還原程式碼與對話、還原對話、還原程式碼、從這裡開始摘要、摘要到這裡為止，或取消中選擇
5. **繼續工作** - 你已經回到那個時間點

### 鍵盤快捷鍵

- **`Esc` + `Esc`** - 開啟檢查點瀏覽器
- **`/rewind`** - 存取檢查點的另一種方式
- **`/checkpoint`** - `/rewind` 的別名

## 知道何時該回溯：上下文監控

檢查點能讓你回到過去——但你怎麼知道*什麼時候*該這麼做？隨著對話變長，Claude 的上下文視窗會逐漸填滿，模型品質也會在不知不覺中下降。你可能在不知情的狀況下，用一個「半盲」的模型交付程式碼。

**[cc-context-stats](https://github.com/luongnv89/cc-context-stats)** 透過在 Claude Code 狀態列加入即時**上下文區間**來解決這個問題。它會追蹤你目前在上下文視窗中的位置——從 **Plan**（綠色，適合規劃與寫程式碼）經過 **Code**（黃色，避免開始新的規劃）到 **Dump**（橘色，該收尾並回溯了）。當你看到區間變化時，就知道該建立檢查點、重新開始，而不是在品質下降的情況下硬撐下去。

## 摘要

檢查點是 Claude Code 的自動化功能，讓你能安全地探索不同做法，不必擔心工作成果遺失。每次使用者提示都會自動建立新的檢查點，因此你可以回溯到工作階段中任何先前的時間點。

主要好處：
- 大膽嘗試多種做法
- 快速從錯誤中復原
- 並列比較不同的解決方案
- 安全地與版本控制系統整合

請記住：檢查點不能取代 git。快速實驗用檢查點，永久的程式碼變更用 git。
