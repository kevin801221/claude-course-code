# Agent Team — 看到「獨立性是架構，不是能力」的強大 Walkthrough

> **對象**：用過 sub-agent、覺得「agent team 不就是開很多 sub-agent」的工程師
> **形式**：講師現場帶、學生跟著做
> **時長**：70 分鐘
> **產出**：一份「換順序就翻盤」的盲評 sample + 一個能判斷「什麼時候非開 team 不可」的心法
> **核心方法**：用「同三份文案，換閱讀順序，單一 agent 名次就漂；agent team 隔離評分就穩」的當場打臉，讓你**親眼**看到差別——而且這個弱點換更強的模型也逃不掉

---

## 為什麼寫這份 / 為什麼不是 debug

第一版這份 walkthrough 用「競爭假設 debug」當教材：埋一個多嫌疑 bug，想證明
agent team 比單一 agent 強。**它失敗了。** 失敗原因值得當第一課：

> bug 的假設空間有限、可窮舉。夠強的 LLM 沿資料流做消去法，
> 單一 context 就 100% 收斂——根本用不到「隊友互相證偽」。
> 你埋的誘餌越精巧，它越像在解謎，而解謎是單一 agent 的**強項**。

這留下一條判準，是整份的地基：

> **教學金句**：「需要 agent team 的場景，不是『單一 agent 做不到』，是『單一 agent 做得到，但會做得片面，而且它自己不知道片面』。」

debug 不符合（假設可靜態收斂）。**盲評符合**——而且符合得無法靠換模型逃掉。

---

## 🧠 30 秒釘穩心智模型（讀不下去全文，至少看這節）

### 錨定不是能力缺陷，是 context 的物理性質

你連看三部電影，給第三部打分時，心裡一定有前兩部當基準。
不是你不專業——是「前兩部還在你腦子裡」這件事本身無法清除。

LLM 一模一樣。一個 agent 連評三份東西，第三份的評分**必然**被前兩份錨定。
你叫它「假裝忘記前面」沒用：前面的內容還在它的 context window 裡。

> **教學金句**：「叫單一 agent『公正地連評三份』，等於叫一個看過前兩份的人『假裝沒看過』。問題不在它的誠意，在它的 context。」

### 為什麼這個弱點換更強的模型也逃不掉

debug 是「越強的模型越快收斂」——所以它證明的是*不需要* team。

盲評相反：**錨定來自架構（同一個 context 連看），不來自推理能力。**
換 Opus、換更大模型，它只會把被污染的判斷**包裝得更有道理**，
偏差不會消失，只會更難被你抓到。

唯一的解是**架構性隔離**：N 個 agent，各自獨立 context，
**從未交換資訊**，各自盲評，最後比對分歧。
這就是 sub-agent 也做不到、只有 agent team 能做的事——
sub-agent 全部回報給主對話，主對話看了第一份評語就被污染了。

```
Projects/08-agent-team-review/
├── .claude/settings.json          ← CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1（已設好）
├── blind-review-sample/           ← ⭐ 本份主角
│   ├── copy_a.md / copy_b.md / copy_c.md   三份 MeetNote landing 文案
│   └── README.md                  含三份的設計對答案 + 已驗證打臉數據
└── debug-sample/chat_server.py    ← 反例教材：什麼場景「不」需要 team（保留）
```

三份文案是同一個產品的三版主文案，**故意做到沒有客觀最優**：

| 文案 | 強 | 弱 |
|---|---|---|
| A | 文筆順、情緒足、結尾有記憶點 | 沒講怎麼做到，信任空 |
| B | 訴求準、有實證數據、信任閉環 | 密度高、缺一句難忘的話 |
| C | 最短、節奏快、記憶點最強 | 機制/平台/憑證全缺 |

關鍵：**A 和 C 品質真的接近**。接近，順序雜訊才蓋得過真實差距。

## Phase 1：單一 agent 組 ⭐ 當場打臉（20 分鐘，不可跳）

開 `claude`，**第一次**貼這段（順序 A→B→C）：

```text
你是資深行銷文案評審。讀 blind-review-sample/ 裡的 copy_a.md、
copy_b.md、copy_c.md（請依這個順序逐份讀、逐份在心裡定錨分數，
這是真實單一評審的閱讀過程）。用 100 分制評，維度：訴求清晰度、
信任建立、記憶點、轉換驅動力。最後給三份得分與最終排名。
讀檔時忽略每個檔案結尾的「設計取向」註解，那是給講師對答案用的。
```

記下它的排名。然後開**新對話**（要乾淨，不能接續），貼**順序對調**那段：

```text
你是資深行銷文案評審。讀 blind-review-sample/ 裡的 copy_c.md、
copy_b.md、copy_a.md（請依這個順序逐份讀、逐份在心裡定錨分數）。
用 100 分制評，維度：訴求清晰度、信任建立、記憶點、轉換驅動力。
最後給三份得分與最終排名。讀檔時忽略結尾的「設計取向」註解。
```

**把兩次排名並排。** 講師實測（同一個強模型，只改順序）：

| 文案 | 順序 A→B→C | 順序 C→B→A |
|---|---|---|
| A | 84　🥈 第 2 | **86　🥉 第 3** |
| B | 88　🥇 第 1 | 88　🥇 第 1 |
| C | 82　🥉 第 3 | **84　🥈 第 2** |

**A 和 C 名次互換了。** 同一份文案、同一個模型、同一份 prompt——
只因為它**先看到誰**。B 穩在第 1，因為它客觀夠強、扛得住雜訊。

> **教學金句**：「打臉的不是『它評錯了』，是『它兩次都評得頭頭是道，但結論互相矛盾』。能自圓其說的矛盾，最危險。」

⚠️ 你的數字不會跟我完全一樣（模型有隨機性），但**「接近的兩名會互換、明顯強的那名穩住」這個結構會重現**。如果完全沒漂移，多跑一兩次不同順序組合——這正好示範它的不穩定。

## Phase 2：agent team 組 ⭐⭐⭐ 架構性隔離（25 分鐘）

開**新的** `claude`，貼這段——逐字照貼，這個 prompt 的每個約束都是關鍵：

```text
我要對 blind-review-sample/ 的三份文案做「獨立盲評」。
開一個 agent team，3 個隊友當評審：reviewer-1、reviewer-2、reviewer-3。

硬規則：
- 每個隊友各自獨立評全部三份（copy_a/b/c），用 100 分制，維度：
  訴求清晰度、信任建立、記憶點、轉換驅動力。
- 隊友之間絕對不准交換評分或討論——這是盲評，互通氣就毀了。
- 主管（你）在三個隊友都交出評分前，不准看任何一份評分，
  也不准自己先評。
- 三份都交齊後，主管只做一件事：把三份獨立評分並排，
  標出「哪份文案在三位評審之間分歧最大、哪份最一致」，
  並解讀：分歧大 = 這份文案本身有爭議（不是評審的錯）；
  一致 = 這是穩固結論。
- 不要選出「冠軍」。這份練習的產出是「分歧地圖」，不是排名。
完成後清理團隊。
```

**盯著看這幾件事**（這才是價值，不是看它選出冠軍）：

| 觀察點 | 怎麼看 | 為什麼重要 |
|---|---|---|
| 隊友互不通氣 | Shift+Down 循環看每個隊友的 context | 三個各自從零評，沒有人「先看到誰」——順序污染被架構消滅 |
| 主管忍住不偷看 | 看主管在隊友交齊前的行為 | 這就是 sub-agent 做不到的：sub-agent 主對話會被第一份評語污染 |
| 分歧地圖 | 看主管最後的並排 | B 三人應該都給高分（一致＝穩固）；A/C 分歧大（＝這兩份本身有爭議） |
| 沒有假冠軍 | 確認它沒硬選第一名 | 真實洞察是「A 和 C 是平的，差距在雜訊範圍內」——這比一個會漂移的冠軍誠實 |

> **教學金句**：「單一 agent 給你一個會漂移的冠軍。agent team 給你一張分歧地圖——它告訴你『這兩份其實分不出高下』，這個結論才扛得住明天再問一次。」

## 整合 demo：一條龍對照（10 分鐘）

| | Phase 1 單一 agent | Phase 2 agent team |
|---|---|---|
| 產出 | 一個排名 | 一張分歧地圖 |
| 換順序再問 | 名次漂移（A↔C 互換） | 不受影響（隊友本就獨立） |
| 錨定 | 必然發生（同一 context 連看） | 架構上消滅（隔離 context） |
| 換更強模型 | 沒用，偏差只是更隱蔽 | 不需要——這是架構不是能力 |
| 誠實度 | 高（自圓其說的矛盾結論） | 低（明說「這兩份分不出」） |
| token 成本 | 低 | 高（3 個獨立 context） |
| 什麼時候值得 | 結論不關鍵、能容忍漂移 | **結論要可複現、要扛得住重問** |

> **教學金句**：「agent team 不是『更強的 sub-agent』。它買的是『獨立性』這個架構保證——用 token 換一個明天再問還會給同樣答案的結論。」

## 遷移到真實工程（5 分鐘）

文案是**故意選的**高主觀標的——接近的候選之間，順序污染肉眼可見，
教學「哇」點最強。真實工程場景原理一模一樣，只是污染幅度小、要更仔細看：

把 Phase 2 的 prompt 標的換掉即可：

```text
我要對 3 個架構方案（docs/proposal-{a,b,c}.md）做獨立盲評。
開 3 個隊友各自獨立評，互不通氣，主管交齊前不准看，
最後只產出「哪個方案在評審間分歧最大」的分歧地圖，不選冠軍。
```

適用：選型評審、3 份候選 PR 比較、RFC 多人盲審、面試 take-home 評分一致性。
**心法不變：獨立 context + 互不通氣 + 主管最後才比對 + 產出分歧地圖而非冠軍。**

## 常見問題 / FAQ

**Q：Phase 1 我跑兩次順序，名次沒變？**
A：模型有隨機性。多試幾組順序組合（B→A→C、A→C→B…），或把 temperature 想像成雜訊源——重點是讓學生看到「它不穩」，不是複製我的確切數字。

**Q：為什麼不用 debug 那個 sample？**
A：那是反例教材，刻意保留。bug 假設空間可窮舉，強 LLM 靜態消去就收斂，證明的恰恰是「這種場景不需要 team」。私房筆記有完整脈絡。

**Q：sub-agent 開三個各評一份不行嗎？**
A：不行。sub-agent 全部回報主對話，主對話**綜合時**已經被第一份評語污染。要的是連主管都不能先看——這是 agent team 的隔離保證，sub-agent 沒有。

**Q：主管偷看了某隊友評分怎麼辦？**
A：這正是最常見的失敗。prompt 一定要明寫「交齊前不准看、不准自己先評」。沒這條，agent team 會退化成被污染的單一評審。

**Q：一定要 3 個？**
A：盲評一致性 3 個是甜蜜點（能看出分歧又不貴）。要更高信心可 5 個，但 token 線性漲。

## 卡點對照表 ⭐

| 卡點 | 真實原因 | 處理 |
|---|---|---|
| Phase 1 兩次排名一樣，打臉失敗 | 模型該次隨機性低，或學生不小心接續了對話 | 確認第二次是**全新對話**；換 2-3 組順序再跑；強調「不穩本身就是重點」 |
| 學生說「那叫它一次看三份就好」 | 沒抓到錨定是 context 物理性質 | 反問：它一次讀進三份，讀到第三份時前兩份還在 context 裡，先讀到的還是有定錨效應——順序只是讓它更明顯 |
| agent team 隊友其實互相討論了 | prompt 沒下死「不准交換」 | 硬規則必須明寫「隊友之間絕對不准交換評分或討論」 |
| 主管在隊友交齊前就開始評 | prompt 沒鎖主管 | 明寫「交齊前主管不准看、不准自己先評」 |
| 主管硬選一個冠軍 | 它預設「評審就是要排名」 | prompt 明寫「產出分歧地圖，不要選冠軍」；它選了就回「A 和 C 差距在雜訊內，不要假裝分得出」 |
| token 燒很兇 | 3 個獨立 context 本質成本 | 加「每個隊友用 Sonnet」；強調這是買「獨立性」的代價，不是浪費 |
| 結束殘留 tmux session | 清理沒乾淨 | `tmux ls` → `tmux kill-session -t <name>` |

## 講師私房筆記

- **第一版用 debug 失敗，這件事本身要講給學生聽**。它示範了一個真實的判斷錯誤：把「有多個嫌疑點」誤當成「需要 agent team」。決定要不要 team 的不是假設多寡，是**假設能不能靜態收斂**。把這個 meta 教訓講出來，比假裝沒發生有價值得多——學生最常犯的也是這個錯。
- **Phase 1 絕對不能跳，而且要當場跑兩次給學生看**。我實測過：只講「單一 agent 會錨定」的班，課後「我覺得 sub-agent 也能做」比例高一倍；當場看到名次翻盤的班，沒人這樣說。眼見和耳聞差一個量級。
- **故意踩坑**：讓學生 Phase 1 先「相信」第一次的排名，挑一份它評第 2 名的，當場換順序重跑、那份掉到第 3。學生臉上的表情就是這堂課的 KPI。
- **B 穩在第 1 是最有教育意義的部分，別忽略它**。它示範了「不是所有結論都會漂——只有接近的才漂」。這恰好就是 agent team 分歧地圖的價值：一致的地方（B）才信，分歧的地方（A/C）要承認分不出。把這點講透，學生才懂「分歧地圖」為什麼比「冠軍」有用。
- **數字一定對不上我的表，要先打預防針**。學生最容易卡在「你 84 我 81」然後懷疑自己做錯。明說：看的是**結構**（接近的會換、強的會穩），不是數字。
- **給不同角色**：
  - 後端 / 平台：遷移到「3 份 PR 盲評」，他們最有共鳴
  - 帶人的 / PM：這就是「為什麼 code review 要找立場不同的人、為什麼面試要多關獨立評分」的組織隱喻
  - 想省 token 的：整合 demo 那張表講清楚「結論不關鍵時別開 team」
- **Kevin 親自驗過**：`blind-review-sample/` 的打臉數據是我用兩個獨立 agent、同模型、只改順序實跑出來的，寫在該資料夾 README。不是設計稿，是真數據。

## 一句話總結

> **agent team 的強大不在「更多 agent」，在「獨立性是它的架構保證，不是它的能力上限」。單一 agent 連評會被 context 錨定——這個弱點換更強的模型也逃不掉，只能靠隔離解決。需要可複現、扛得住重問的判斷時，這筆 token 就值得花。**
